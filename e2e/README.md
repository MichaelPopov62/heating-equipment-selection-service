# Регрессионный набор персон

Здесь зафиксированы проверки, которые 23.08.2026 выполнялись вручную четырьмя персонами
в браузере. Набор отвечает на один вопрос: **сколько персон из пяти доходят до сметы
и забирают её**. Это условия `GA-01` и `GA-02` из `docs/qa/TEST_PLAN.md`.

Полные баг-репорты со скриншотами — `docs/qa/heatcalc-audit.html`.
Исходные протоколы ручных проходов — `docs/qa/research/U1..U5`.

---

## Фактический результат прогона

Прогон 23.08.2026 против локального стенда (backend на файловом каталоге, frontend `npm run dev`):

**Персоны — 3 из 4 дошли до сметы, 0 из 4 забрали PDF.** Совпадает и с ручным аудитом,
и с прогоном против прода. Персона `interrupted` дополнительно **прошла** проверку
продолжения после перерыва — это разрешает расхождение протоколов U3 и U4 о сохранении
текущего шага в пользу U3: шаг сохраняется.

**Регрессии — 10 воспроизвели дефект, 2 пропущены, 1 прошёл.**

| Результат | Что означает |
|---|---|
| 10 падений | дефект воспроизводится, диагноз в тексте падения |
| `BUG-05`, `BUG-10` — пропуск | локальный стенд без авторизации; дефект там физически не возникает. Нужен стенд с `PROJECTS_AUTH_ENABLED=true` **и** задеплоенными `data-testid` |
| `BUG-12` — прошёл | локально ошибка сети пользователю показывается, вопреки ручному замеру на проде. **Закрытым не считать** до перепроверки на проде |

Зелёный регресс-тест здесь означает «дефект не воспроизвёлся», а не «дефект починен».
Разница принципиальна, и три случая выше — ровно она.

Тесты описывают **целевое** состояние, а не текущее. Они станут зелёными после Фазы A —
и это будет доказательством, что фаза закончена. Красный тест здесь означает
«дефект ещё не починен», а не «набор сломан».

При отладке набора четыре падения оказались его собственными дефектами, а не продукта:
неверная сигнатура пропуска теста; ожидание `domcontentloaded` в SPA; подпись кнопки шага
(«Об'єкт», а не «Параметри об'єкта»); апостроф в двух вариантах (U+0027 и U+2019).
Все четыре — следствие привязки к тексту. После перехода на `data-testid` таких
поломок не было ни одной.

Правило: **не подгонять ожидания под текущее поведение**. Если тест мешает — чинят продукт
или спорят с формулировкой, но не переписывают ассерт под баг.

## Запуск

```bash
cd e2e
npm install
npm run install:browsers
```

Против живого стенда (ничего поднимать не нужно):

```bash
TARGET=prod npm run personas       # пять персон, табло проходимости
TARGET=prod npm run regressions    # по тесту на каждый баг-репорт
TARGET=prod npm test               # всё вместе
npm run report                     # HTML-отчёт с трассами и видео
```

Локально:

```bash
# из корня репозитория, в отдельном терминале
cp backend/test_data.json.example backend/test_data.json
npm run dev:full

# затем
cd e2e && npm test
```

Артефакты падений — `e2e/.artifacts/`: трассы, скриншоты, видео.
Трасса открывается через `npx playwright show-trace <файл>` и показывает
каждый шаг, сеть и состояние DOM в момент падения.

## Почему оракул слушает сеть, а не читает экран

Отличить настоящий расчёт от подделки по тексту на экране **нельзя**, и это два
подтверждённых дефекта:

- **BUG-01** — когда расчёт не запускался, экран показывает таблицу с подписью
  «Джерело: швидка оцінка (100 Вт/м²)», внешне неотличимую от результата;
- **BUG-04** — после ошибки на экране остаётся **предыдущий** результат
  с правильной подписью «розрахунок API» над неправильными числами.

Поэтому `CalcOracle` считает запросы расчёта и требует успешный ответ **после последнего
изменения данных**. Это работает сегодня, без единой правки продукта.

**Маркеры добавлены, и сверка включена.** `assertMarkersHonest()` сопоставляет
`data-source` с сетевым оракулом и падает при расхождении. Это не паранойя:
`data-source` выводится из того же признака, что и подпись «Джерело: …», то есть
не является независимым источником истины. Унаследуй он дефект подписи — зелёным
стал бы весь набор, и падения перестали бы что-либо значить. Сеть подделать
интерфейс не может, поэтому она и остаётся арбитром.

## Селекторы: атрибуты, а не тексты

Набор адресуется по `data-testid` — 28 атрибутов добавлены во фронтенд отдельной
задачей, манифест в `TESTIDS.md`. Плюс машиночитаемые маркеры состояния
`data-source` (`api` | `quick`) и `data-calc-phase` (`idle` | `pending` | `ok` | `error`)
на панели результата.

До этого набор держался на украинских подписях и сломался четыре раза подряд —
см. список выше. Ни одна поломка не была дефектом продукта.

**Важно про порядок работ:** чистка текстов интерфейса (`BUG-19`) теперь безопасна,
потому что набор от текстов не зависит. Если бы порядок был обратным, восстанавливать
пришлось бы вслепую.

Осталось два места, где атрибута нет и сравнение идёт по тексту, — они обёрнуты
в `apos()`, устойчивый к обоим вариантам апострофа.

## Чего этот набор не проверяет

Браузер не отличит правдоподобное число от верного. Поэтому **вне** набора остаются:

- **BUG-14** — вентиляция считается плоским коэффициентом;
- **BUG-15**, **BUG-16** — котёл подбирается по горячей воде, запас считается неверно;
- **BUG-20** — одноэтажный дом считается как этаж посреди многоэтажки.

Их единственный оракул — **ручной расчёт живого теплотехника** по эталонным объектам.
Автотест здесь бесполезен принципиально: он закрепит текущий коэффициент как ожидаемый
и будет зелёным годами. См. раздел «Межі звіту» в отчёте.

## Как добавить персону

1. Дописать объект в `personas/index.ts` с полем `baseline` — что было при ручном проходе.
2. Ничего больше: `personas.spec.ts` итерирует список сам.
3. Если персона проверяет новое поведение (как `interrupted`) — добавить ей отдельный тест
   в том же файле под флагом.

Менять данные существующих персон можно **только вместе с протоколами** в
`docs/qa/research/U*.md`. Персона — это воспроизведение реального прохода,
а не удобный для теста набор значений.
