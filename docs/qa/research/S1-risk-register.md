# S1 — Единый риск-реестр

> Сведение `_ORCH-NOTES.md`, `U1`–`U5`, `R1`–`R6` в один инструмент приоритизации.
> Правила разрешения конфликтов соблюдены: живой проход (U1–U5) > код-ресёрч; `_ORCH-NOTES` > отчёты субагентов.
> Все спорные места перепроверены автором S1 **лично по коду**; новые якоря помечены «(проверено S1)».
> Где проверить не удалось — «НЕ ПРОВЕРЕНО» явным текстом (раздел 6).

## Резюме

HeatCalc — инженерный подборщик отопления, который **не падает и почти всегда врёт**. За 118 атак
U4 не получено ни одного белого экрана, ни одного JS-исключения, ни одного 5xx. Вместо этого
продукт молча теряет данные, молча нормализует ввод и молча выдаёт правдоподобный, но физически
неверный результат. Это худший из возможных профилей риска для сервиса, за который берут деньги:
дефект невидим ни пользователю, ни CI.

Состояние по трём слоям.

**Проходимость (слой 0).** Из четырёх живых персон до сметы дошли трое, **забрать её не смог
ни один**. Отказов ровно два и они независимы: (A) значение вне схемы даёт `400` с единственной
строкой «Некоректні вхідні дані» — фронт выбрасывает `details`/`code`; (B) незаполненная
«Площа, м²» у «Стіна №1» останавливает расчёт вообще, а экран подменяет его заглушкой
«швидка оцінка (100 Вт/м²)». Отказ B опаснее: ошибка хотя бы честна, заглушка врёт молча.

**Физика и подбор (слой 1).** Вентиляция подменена плоским коэффициентом 1.3 (занижение до 4×),
верхняя граница комнаты для дома всегда «тепле приміщення» (крыша не считается), расчётная
наружная по умолчанию −5 °C. Смещения мультипликативны и **все в одну сторону — в занижение**:
U2 получил 2.02 кВт на 158 м² при −19 °C вместо реалистичных 5–6. Одновременно подбор котла
насыщен пиком ГВС и **не реагирует на теплопотери вообще**: объект на 9 кВт и на 40 кВт получают
один и тот же котёл. Лимит температуры поверхности тёплого пола делится на сопротивление финиша
вместо сопротивления теплоотдачи — для плитки ограничение не срабатывает никогда.

**Деньги (слой 2).** Гидравлика перехватывает любое исключение, подставляет нули и возвращает
`HTTP 200` со сметой без труб и без насоса. Трубы ролей `trunk`/`dhw` выпадают из сметы и из базы
40 %/15 %. Труба без цены становится 0 грн. После ошибки `400` на экране остаётся прежняя смета,
и её можно выгрузить.

**Тестируемость.** Тестовых файлов ноль, `data-testid` ноль, 68 verify-скриптов из которых
3 мёртвых, а в CI реально исполняется **61** (проверено S1: workflow не гоняет 4 из 5 корневых
скриптов, включая `verify:language-policy`). Подбор котла — 1164 строки, 20 порогов — не имеет
ни одного прямого ассерта.

**Вердикт.** Продукт нельзя выпускать на живых мастеров без закрытия ТОП-20 и нельзя брать за него
деньги без закрытия физики вентиляции, подбора котла и целостности сметы.

**Распределение реестра:** **P0 — 42**, **P1 — 99**, **P2 — 69**. Всего **210** записей
после дедупликации (UX 36, MATCH 35, CALC 32, INFRA 19, HYDR 18, MONEY 17, DATA 17, API 14,
AUTH 9, SEC 7, PERF 6).

## 3. Разрешённые противоречия между отчётами

Каждый вердикт получен **перепроверкой по коду автором S1**, а не сопоставлением текстов.

### 3.1 Число труб в стальной ветке шероховатости: R6 — 23, оркестратор — 27

**Кто что утверждает.** R6 §1.6: «23 из 30 труб попадают в ветку `steel`». `_ORCH-NOTES` N-25: «27 из 30 (R6 заявил 23 — уточнено)».

**Проверка.** Прогнал логику `resolveRoughnessMm` (`backend/src/hydraulics/pipeHydraulics.js:81-89`) с реальной картой `roughnessMmByMaterial = {pex: 0.007, metal_plastic: 0.007, steel: 0.15}` (`backend/data/appliances.json`) по всем 30 позициям `products.pipes` из `backend/test_data.json.example`.

**Вердикт: прав оркестратор — 27 из 30.** В ветку `pex` попадают ровно три позиции: `p-01 'PEX-a'`, `p-28` и `p-29` (`'PE-XA EVOH-PEX-B'`). Остальные 27 — включая все 4 `'Металопластик'` (кириллица не ловится `includes('metal')`), все 4 `'PE-XA EVOH'` (дефис между `pe` и `xa`), 18 позиций полипропилена и `'PE- RT'` — уходят в `steel = 0.15 мм`.

**Дополнительно (не заметил никто).** R6 процитировал условие как `key.includes('ал')`; фактически в коде `key.includes('pex-al')` (`:85`). Условие `'ал'` живёт в другом файле — `hydraulics/pickPipe.js:57`, в фильтре `pipeMaterialPreference`. Два похожих, но разных предиката в двух модулях — самостоятельный риск рассинхрона.

### 3.2 Ущерб от шероховатости: R6 — 20-кратное завышение, оркестратор — ~12 %

**Проверка.** `pipeHydraulics.js:62-63`: `relRough = (roughnessMm/1000)/D_м`; `lambda = frictionFactor(re) · (1 + relRough·10)`. Абсолютная шероховатость завышена в 21.4 раза (0.15/0.007), но в потери входит только через множитель `(1 + relRough·10)`. Для наименьшего D_вн = 11.6 мм: сталь → 1.129, PEX → 1.006; отношение **1.122**. Для D_вн = 42 мм: 1.036 / 1.0017 → **1.034**.

**Вердикт: прав оркестратор. Фактическое завышение потерь на трение — 3…12 % в зависимости от диаметра, максимум на Ø16.** Вывод R6 о «20 кратах» **отклонён**: он относится к абсолютной шероховатости, а не к перепаду давления. Приоритет — **P1** (RISK-HYDR-02), не P0.

**Существеннее смежный вопрос:** сама формула `λ·(1 + relRough·10)` не является ни Колбруком, ни Альтшулем (RISK-HYDR-03). Она — источник большей неопределённости, чем ошибка классификации материала.

### 3.3 `POST /api/v1/projects/import` в dev: HS256-в-рантайме (R6) против JWKS-стаба (R4)

**Кто что утверждает.** Оба согласны, что `requireRole` (`auth/requireRole.js:21-28`) отдаёт `403` при **выключенной** auth. Расходятся в обходе.
R6 §4.3, вариант 1: «HS256 + `PROJECTS_AUTH_ENABLED=true` — **работает**; `validateAuthConfiguration` вызывается только из `scripts/verifyProjectsAuth.js` и **не блокирует старт**».
R4 §2.2: «сервер физически не стартует с HS256 + включённой auth».

**Проверка.**
```
backend/src/index.js:26-30
  assertAuthConfiguredForProduction();
  assertAuthConfiguredWhenEnabled();
  if (process.exitCode === 1) { process.exit(1); }
```
`assertAuthConfiguredWhenEnabled()` (`auth/projectsAuthConfig.js:155-166`) при `isAuthEnforcedByConfig()` зовёт `validateAuthConfiguration({ production: false, authEnforced: true })`, а та при `mode === 'hs256' && authEnforced` безусловно добавляет ошибку (`:119-124`) и выставляет `process.exitCode = 1`.

**Вердикт: прав R4, R6 ошибся.** Утверждение R6 «`validateAuthConfiguration` вызывается только из verify-скрипта» **опровергнуто**: она вызывается из `index.js:27` через `assertAuthConfiguredWhenEnabled`. Симметрично в production `assertAuthConfiguredForProduction` даёт тот же результат. **HS256 при включённой auth не запускает сервер ни в dev, ни в prod.** Пункт R6 §6.5 («нужен один живой прогон») закрыт чтением кода — прогон не нужен.

**Оценка обоих вариантов.**
- *HS256-в-рантайме (R6)* — **нерабочий**, вычеркнуть из плана. Даже если бы работал, это конфигурация, которую прод-код объявляет ошибкой; тесты стояли бы на запрещённом режиме.
- *Локальный JWKS-стаб (R4 §2.3)* — **единственный рабочий путь**: `jose.generateKeyPair('RS256')` + мини-сервер `/.well-known/jwks.json` + `AUTH_JWKS_URI`/`AUTH_ISSUER`/`AUTH_AUDIENCE`/`AUTH_PROVIDER=clerk`/`PROJECTS_AUTH_ENABLED=true`. Проходит **ровно тот же прод-путь** (`verifyAccessToken.js:58-59`), не требует ни одной правки прод-кода и попутно закрывает HTTP-тесты авторизации и IDOR (RISK-AUTH-03), которые в dev-обходе непроверяемы в принципе. Ограничение: `remoteJwks` кэшируется на модуль — порт стаба фиксировать на процесс.
- *Прямой seed в Mongo* (R6 вариант 3) — допустим как ускоритель подготовки состояния, но теряет покрытие самого импорта; держать как запасной.

**Решение для плана:** JWKS-стаб — обязательный элемент инфраструктуры, а не опция. Остаётся открытым (RISK-AUTH-10, §6): требуется ли предварительно создать пользователя в Mongo, чтобы `PLATFORM_ADMIN_EMAILS` дал `role: 'admin'`.

### 3.5 «Товщина несучої стіни»: R2 — «гонка детерминирована», U4 — «воспроизводимость плавающая»

**Кто что утверждает.** U4 Инцидент #6: сброс воспроизведён на 300 и 500, а на 400 один раз сохранилось → «гонка». R2 §7 F-09(б) и §8.7: «это не плавающая гонка, а детерминированная последовательность, воспроизводится 100 %», и явно поправляет U5.

**Проверка.** `frontend/src/hooks/useRoomsOrchestration.ts:177-205`. Ключевая деталь, которую R2 не разобрал: строка `lastWallPresetIdRef.current = presetId` стоит **выше** и раннего выхода `if (!presetChanged && current != null) return;`, и выхода `if (next == null) return;`. Поэтому:
- если эффект впервые отрабатывает **до** прихода `GET /presets/envelope`, `wallPresets` пуст → `preset === null` → `options === null` → `next == null` → **выход без изменения**, но ref уже «сожжён»; на следующем проходе `presetChanged === false` и `current != null` → ранний выход → **значение пользователя выживает**;

**Вердикт: правы оба, но по-разному, и живой проход остаётся приоритетным.** Механизм найден верно (R2), но вывод «детерминировано 100 %» **неточен**: исход зависит от того, успел ли эффект отработать до ответа API. Практический вывод для теста: **сценарий обязан фиксировать оба исхода**, а ассерт формулировать как «значение пользователя не изменилось», без ожидания стабильного `200`. **Записано как RISK-PERF-05, P0.** Требует либо повышения prod-лимита, либо отказа от автопересчёта в пользу явной кнопки, либо и того и другого.

## 5. Проверено и работает (не тратить усилия)

Здесь то, что исследование признало корректным. Проектировщикам тестов — не вкладывать сюда приоритетные усилия; критикам следующей фазы — не открывать эти вопросы заново без нового факта.

**Физика и расчёт**
1. **Пересчёт мощности радиатора при ΔT.** `baseWatts·(targetΔT/baseΔT)^1.3`, `targetΔT = (supplyC+returnC)/2 − insideC` — арифметический напор EN 442-2. Показатель 1.3 сверен с самим каталогом (Global Vox 125/193 → n=1.291; Korado 22-K 673/1315 → n=1.311), погрешность ≤3 %. `matching/radiatorSizingHelpers.js:83-102`. (N-23, R5-rad-01)
2. **`R_CONV_UP_M2KW = 0.1` в расчёте самого потока вверх** применён верно (`ufhRoomHeatFlux.js:158`) — неверен только лимит и обратный пересчёт температуры (RISK-SEC-01). Формулу `q↑ = (t_ср − t_возд)/R_вверх` менять не надо.
3. **Схема слоёв стены** `R = R_пов + d/λ + d_ут/λ_ут` верна как одномерный расчёт; отсутствует только коэффициент однородности (RISK-CALC-08). (R5 §Резюме)
4. **Расчётная температура санузла** (пол 24 °C) корректно доходит до теплопотерь, подбора радиатора и ТП; согласованность проверена `verifyRoomDesignAirTemp.js` и `verifyUniboxMatching.js`. `shared/roomDesignAirTemp.js:14,46-73`
5. **Одновременность ГВС и объём БКН** — в разумном инженерном коридоре. (R5 §Резюме)
6. **Арифметика сметы сходится.** `labor = round(equipment·0.40)`, `consumables = round(equipment·0.15)`, обе от одной базы, расходники не входят в базу монтажа; `grandTotal` = сумма трёх. Проверено построчно U2 (расхождение 1 грн на округлении) и по коду R5-bom-09. `report/buildFinancialBom.js:13-14,612-617` (проверено S1: константы 40/15 на `:13-14`)
7. **Расчёт детерминирован.** `Math.random` / `randomUUID` в `report`, `matching`, `hydraulics` — 0 попаданий. Единственные недетерминированные поля — `meta.generatedAt` и `meta.referenceBundleLoadedAt`; их достаточно вырезать для golden. (R4 §5.4)

**Данные**
8. **Целостность каталога чистая.** Прогон реального нормализатора по всем 10 группам: 0 позиций без цены, 0 цен ≤ 0, 0 дублей `id`/`article`/`catalogKey`/`model` внутри группы, битых межгрупповых ссылок нет (каталог плоский). (R6 §5.2)

10. **Характеристические кривые есть у 100 % насосов** (32 режима, `{a,b,c}` + `qMin`/`qMax`), геометрия валидируется на входе `assertPumpModeCurveGeometry`. (R6 §1.7)

**Безопасность и авторизация**
