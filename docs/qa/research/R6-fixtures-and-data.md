## Резюме

1. **Каталог = 126 SKU** (+ 7 вариантов объёма у электроводонагревателей). Ссылочная целостность
   чистая: нет позиций без цены, нет нулевых/отрицательных цен, нет дублей `id`/`article`/`model`
   ни в одной из 10 групп.
2. **Главная находка R6 — верхняя граница каталога недостижима не из-за размера дома, а из-за ГВС.**
   На схеме по умолчанию `SCHEME_BOILER_MAX_COMBI` требуемая мощность котла определяется пиком ГВС
   (`peakThermalPowerKw`), который при `coldWaterDesignC.winter=5`, `hotWaterC=60` (ΔT=55 K) и
   `fixtureHotFlowLps.shower=0.18` даёт **41.4 кВт для квартиры с одним душем** и **85.3 кВт для
   типового дома**. Максимальный котёл в каталоге — 32 кВт (дом) / 28 кВт (квартира).
   Результат: **любой** реальный объект на схеме по умолчанию получает самый мощный котёл каталога
   и мягкое предупреждение о проливе, а теплопотери на подбор котла **не влияют вообще**
   (Q=9 кВт и Q=40 кВт дают один и тот же `Luna Duo-Tec E 40`). Это прямая механика симптома P0.
3. **Схема «1К + БКН» в доме почти всегда даёт каскад.** `hotWaterPowerKw` в накопительном сценарии
   зажат снизу `storage.boilerDhwPowerMinKw = 24` кВт, формула — сумма. Дом 9 кВт →
   `requiredKw = 35.89` → каскад **2 × 24 кВт = 48 кВт** на дом 9 кВт.
4. **Электрокотлов в каталоге нет вообще** (все 24 котла `fuel = "Газ"`), хотя
   `validateCatalog.js:263` допускает `"Электричество"`. Сценарий «электрокотёл» физически
   неподбираем — «электрический» во всех схемах означает только бак ГВС.
5. Три разрыва модельного ряда, которые обязаны быть в тестах: **1К котлы 12 → 24 кВт (+100 %)**,
   **ЭВН 100 → 300 л (+200 %)**, **панельные радиаторы 1315 → 3154 Вт (+140 %)**.
6. **`POST /api/v1/projects/import` как загрузчик фикстур ломается на auth**: `requireRole('admin')`
   (`backend/src/auth/requireRole.js:21-28`) отдаёт `403 ADMIN_REQUIRED` **именно тогда, когда
   `PROJECTS_AUTH_ENABLED` выключен** — то есть в «герметичном» dev-режиме из брифинга импорт
   недоступен. Рабочий обходной путь есть (HS256 + `PROJECTS_AUTH_ENABLED=true` фактически работает
   в рантайме, хотя `.env.example:45` это запрещает) — детали в разделе 4.
7. `generatedAt: 2026-04-21` — метаданные, которые **нигде не проверяются**; при загрузке из Mongo
   поле переписывается текущим временем (`loadCatalog.js:253`). Тестов на устаревание цен строить
   не на чем — нужен собственный guard.

**Каталог гетерогенный по формату.** Часть котлов записана «плоско» (`powerKw: {min,max}`,
`efficiencyPercent`, `fuel`), часть — «расширенно» (`specs.power.{min_kw,max_heating_kw}`,
`specs.efficiency.nominal_80_60`, `tags`). Приведение делает
`normalizeBoilerFromExtendedFormats` (`backend/src/catalog/validateCatalog.js:54-120`), туда же
подставляются дефолты: `fuel = 'Газ'` при пустом поле (`:73`), `isDoubleCircuit` из
`circuitsCount` / тегов / регэкспа по модели (`:93-108`). То же для радиаторов:
`material` при отсутствии становится `"разное"` — **10 из 13 радиаторов** приходят в matching
с материалом `"разное"`, реальные `Алюміній`/`Біметал` есть только у 3.
**Тест на нормализацию обязателен для обоих форматов** — это единственное место, где расходящиеся
источники данных сходятся.

**Общее правило поведения matching при отсутствии SKU** (проверено по коду):
подбор **никогда не возвращает ошибку** — он деградирует. Пять разных стратегий:

| Модуль | Стратегия при отсутствии подходящего SKU | Якорь |
|---|---|---|

| ЭВН / БКН | максимальный объём каталога + предупреждение о недоборе | `waterHeater.js:73-97`, `indirectWaterHeater.js:137-150` |
| Коллектор ТП | **каскад** по 12 выходов | `manifold.js:125-143` |
| Коллектор радиаторный / котловой | максимальный из пула + предупреждение о дефиците | `manifold.js:210-220`, `:277-297` |
| Труба | `catalogPoolExhausted` — **позиция отсутствует** в результате + предупреждение | `pickPipe.js:190-204`, `:353-359` |
| Насос | **`null`** + предупреждение, без fallback | `pickPump.js:200-212` |
| Радиатор комнаты | `skippedRoomEmitter` с `radiatorModel: '—'` + предупреждение | `pickRadiatorsCore.js:723` |
| Унибокс | петля без унибокса + предупреждение | `unibox.js:460`, `:475` |

### 4.1 Структура бандла

SSOT версии: `PROJECT_EXPORT_SCHEMA_VERSION = 1` в двух местах —
`frontend/src/types/projectExport.ts:10` и `backend/src/projects/projectExportConstants.js`.
Тип — `frontend/src/types/projectExport.ts:12-34`, схема API —
`components/schemas/ProjectImportBody.yaml` (`additionalProperties: true`).

```jsonc
{

  "exportedAt": "…ISO…",             // информационное, не валидируется
  "source": {                        // опционально
    "projectId": "…",                // → лог project.import.sourceProjectId
    "calculationsTotal": 2
  },
  "project": {                       // ОБЯЗАТЕЛЕН, должен быть plain-object
    "clientName": "…",               // ОБЯЗАТЕЛЕН, 1…200 симв. после sanitize
    "label": "…",                    // опционально, ≤ 200

    "lastCalcInput": { … }           // JSON ≤ 512 000 симв.

    {
      "calcInput": { },              // ОБЯЗАТЕЛЕН, plain-object, JSON ≤ 512 000

      "sourceCreatedAt": "…ISO…"     // опционально; задаёт порядок импорта
    }

```

Что внутри `calculations[]` (`backend/src/projects/validateProjectImportBody.js:57-93`):
- `calcInput` и `report` — **только проверка «это объект»**, содержимое не сверяется ни с AJV,
  ни с текущей версией отчёта. Расчёт при импорте **не перезапускается**
  (`importProjectBundle.js:2-3`: «создаёт project + calculations без runCalculation»).
- `summary` при отсутствии выводится из `report` через `extractCalculationSummary`
  (`importProjectBundle.js:69-72`), при наличии — санитизируется.
- Порядок записи задаёт `sortCalculationsForImport`; `lastCalcInput` проекта, если его нет
  в бандле, берётся из последнего расчёта (`importProjectBundle.js:85-93`).
- Служебные поля Mongo вырезаются `stripMongoExportFields` / `stripCalculationImportFields`
  до валидации (`validateProjectImportBody.js:67-69`, `:187`).

**Legacy-ветка.** Бандл **без** `exportSchemaVersion` принимается как SurveyDraft, если у него
есть непустой `clientName` **и** (`typeof schemaVersion === 'number'` **или** `Array.isArray(rooms)`
**или** `isPlainObject(objectMeta)`) — `normalizeLegacySurveyImport.js:14-24`. Весь объект
становится `survey`, а `lastCalcReport` (если объект) превращается в один `calculation` с
`calcInput = report.input ?? { building: { temps: { insideC: 20 } } }` (`:51-58`).

### 4.3 Права: admin-only — и почему это ловушка

```
router.post('/api/v1/projects/import', projectsWriteRateLimiter, requireRole('admin'), …)
                                                                 ^ backend/src/api/projectsRoutes.js:245-247
```

`requireRole` (`backend/src/auth/requireRole.js:21-28`) **первым делом** отдаёт
`403 ADMIN_REQUIRED`, если `isProjectsAuthRequired() === false`. То есть герметичный dev-режим
из брифинга (`PROJECTS_AUTH_ENABLED` выключен + `PROJECTS_DEV_OWNER_ID`) **закрывает импорт
наглухо**: работают все остальные ручки проектов, а фикстурная — нет.

Что с этим делать (три варианта, по возрастанию цены):

1. **HS256 + `PROJECTS_AUTH_ENABLED=true` — работает.** `resolveAuthJwtMode`
   (`backend/src/auth/projectsAuthConfig.js:46-54`) возвращает `'hs256'` при заданном
   `AUTH_JWT_SECRET` без `AUTH_JWKS_URI`, и `verifyAccessToken` (`:60-70`) в этом режиме
   честно проверяет HS256-токен. `validateAuthConfiguration` объявляет такую пару ошибкой
   (`projectsAuthConfig.js:120-127`, `.env.example:45`), **но она вызывается только из
   `scripts/verifyProjectsAuth.js` и не блокирует старт приложения** — проверено grep'ом.
   Значит, для тестового окружения достаточно: `PROJECTS_AUTH_ENABLED=true`,
   `AUTH_JWT_SECRET=<local>`, `PLATFORM_ADMIN_EMAILS=<test-admin@…>`, локально подписанный
   JWT с этим email. **Риск:** конфигурация формально «запрещённая», при ужесточении старта
   тесты сломаются — зафиксировать в плане как долг.
2. **Локальный fake-JWKS** (мини-сервер с `/jwks.json` + `AUTH_ISSUER`/`AUTH_AUDIENCE`) —
   легально, но требует поднимать процесс и генерировать пару ключей.
3. **Обход API целиком: seed напрямую в Mongo** через `Project.create` / `Calculation.create`.
   Быстрее и без auth, но теряется покрытие самого импорта и валидации.

**Рекомендация:** вариант 1 для E2E-подготовки состояния + отдельная группа контрактных тестов
на сам импорт (коды из таблицы 4.2), где auth-режим переключается специально.

### 4.4 Механизм загрузчика фикстур (без кода)

**Где хранить.** `backend/tests/fixtures/projects/FIX-<NN>-<slug>.bundle.json` — по одному
бандлу на эталонный объект из раздела 3. Рядом — `backend/tests/fixtures/inputs/FIX-<NN>.calcInput.json`
(чистый вход для юнит-тестов расчётного ядра, без обёртки проекта). Разделение обязательно:
входы нужны и без Mongo, бандлы — только для E2E/проектных сценариев.

**Как генерировать.** Одна npm-задача-генератор (`fixtures:build`), которая:
1. читает `FIX-<NN>.calcInput.json`;
2. поднимает `getReferenceBundle()` с `CATALOG_SOURCE=file` и `test_data.json` из
   `test_data.json.example` (тот же путь, что в `.github/workflows/verify.yml`);
3. гоняет `buildReport({ input, ctx })` **локально, в процессе**, без HTTP и без сети
   (`temps.outsideC` в фикстуре обязателен — см. предупреждение в разделе 3);
4. собирает бандл руками по форме 4.1: `exportSchemaVersion: 1`, фиксированный
   `exportedAt` (не `new Date()` — иначе бандл меняется при каждом прогоне и не годится
   для golden-диффа), `project.survey` = соответствующий SurveyDraft v4,
   `calculations: [{ calcInput, report, summary: extractCalculationSummary(report),
   sourceCreatedAt }]`;
5. пишет файл детерминированно (стабильная сортировка ключей, фиксированное округление).

**Как загружать в тесте.** `POST /api/v1/projects/import` с admin-JWT (раздел 4.3) →
из ответа берётся `project.id` → все последующие шаги E2E работают с этим `projectId`.
Важное свойство: импорт **не пересчитывает** отчёт, значит состояние детерминировано и не
зависит от сети, Meteostat и текущего каталога.

**Как чистить состояние.** `DELETE /api/v1/projects/:id` существует
(`backend/src/api/projectsRoutes.js:387`) — вызывать в teardown по сохранённому `projectId`.
Для полной изоляции — отдельная база на прогон (`MONGODB_URI` с суффиксом job id) и
`drop` после сьюта. Дополнительно между тестами, меняющими справочники, —
`POST /api/v1/system/invalidate-reference-cache` с `SYSTEM_INTERNAL_TOKEN`.
Учитывать квоты: 200 проектов на владельца и 100 расчётов на проект
(`projectAccess.js:193-217`) — без teardown сьют из 200+ прогонов упрётся в
`PROJECT_QUOTA_EXCEEDED`.

**Как версионировать при изменении формата отчёта.** Бандл содержит **замороженный** `report`,
который импорт не валидирует. Значит при изменении формата отчёта старые бандлы будут
молча грузиться и молча расходиться с реальностью. Механизм:
1. Ввести в имени файла ревизию отчёта: `FIX-01-house-radiators.r3.bundle.json`,
   где `r3` — версия схемы отчёта (сейчас в отчёте есть только `meta.schemaVersion`).
2. Хранить `fixtures/MANIFEST.json` со списком `{ fixtureId, reportRevision, catalogSha }`,
   где `catalogSha` — хеш `test_data.json.example`. Отдельный verify-шаг сравнивает текущий
   хеш каталога с записанным и **красит сьют в жёлтый**, если каталог менялся, а бандлы — нет.
3. `fixtures:build --regenerate` перегенерирует все бандлы одной командой; diff бандлов
   в PR — это и есть ревью изменения расчётного ядра (по сути golden-тест).
4. При bump `exportSchemaVersion` до 2 — бандлы v1 обязаны продолжать грузиться (проверить
   `UNSUPPORTED_EXPORT_VERSION` не срабатывает); добавить в набор один **намеренно старый**
   бандл v1 и один legacy-`heatcalc-*.json` как регресс-кейсы обратной совместимости.

## 5. Актуальность и целостность данных

### 5.1 `generatedAt: 2026-04-21` и валюта UAH при текущей дате 2026-08-23

- Каталогу **4 месяца**. Поле `generatedAt` **не читается ни одной проверкой**: в
  `validateCatalog.js` оно не упоминается, а при `CATALOG_SOURCE=mongo` envelope собирается
  заново с `generatedAt: new Date().toISOString()` (`backend/src/catalog/loadCatalog.js:253`).
  Механизма «каталог устарел» в продукте нет.
- Валюта захардкожена: `currency: 'UAH'` в `loadCatalog.js:254` и в смете
  (`buildFinancialBom.js:711`). Мультивалютности нет, конвертации нет.
- Смета строится напрямую от `price` из каталога: `equipmentTotalUah` → монтаж **40 %**
  (`FINANCIAL_LABOR_PERCENT`, `buildFinancialBom.js:13`) → расходники **15 %**
  (`FINANCIAL_CONSUMABLES_PERCENT`, `:14`) → `grandTotalUah` (`:718`).

**Что это значит для тестов цен:**
1. **Ассерты на абсолютные суммы запрещены.** Любое обновление прайса ломает такой тест, и
   ломает по причине, не связанной с кодом. Абсолютные числа допустимы **только** внутри
   golden-фикстур с зафиксированным `catalogSha` (раздел 4.4).
2. **Ассертить надо инварианты, а не суммы:**
   - `laborTotalUah === round(equipmentTotalUah × 0.40)`,
     `consumablesTotalUah === round(equipmentTotalUah × 0.15)`,
     `grandTotalUah === equipmentTotalUah + laborTotalUah + consumablesTotalUah`;
   - смесительный узел ТП при `isMixingNodeRequired` — строка `kind: 'note'` **без суммы**
     (`buildFinancialBom.js:15`), не влияет на `equipmentTotalUah`;
   - встроенный насос котла (`pumpSource: 'boiler_builtin'`) в смету **не входит**;
   - одинаковые позиции схлопываются (проверять `quantity`, а не число строк);
   - в смету попадает **только основная линия** matching, не `proposalEconomy`/`proposalEfficient`.
3. **Нужен отдельный guard-тест на свежесть каталога**, которого сейчас нет:
   «`generatedAt` не старше N месяцев» — жёлтый, не красный, чтобы не блокировать CI.
4. Отдельный smoke на монотонность цены по мощности внутри группы — сейчас она **нарушена**:
   `Orion Condensing KC 12` (12 кВт) стоит 83 710 грн, дороже 32-киловаттного
   `Luna Duo-Tec E 40` (62 500 грн). Формально это не ошибка данных, но линия «Економ»
   (`filterBoilersForEconomyLine`) в такой ситуации ведёт себя неинтуитивно — кейс нужен.

## 6. НЕ ПРОВЕРЕНО

1. **Полный `buildReport` ни разу не прогонялся.** Проверены изолированно
   `validateAndNormalizeCatalog`, `calculateHotWaterDemand`, `pickBoiler` (с вручную собранным
   `CalcRuntimeContext`). `heatlossByRooms`, `warmFloorCalc`, `hydraulics/*`,
   `buildFinancialBom` **не запускались** — `node_modules` не установлены, а `buildReport`
   тянет `bson`/`mongoose`/AJV. Все оценки теплопотерь в разделе 3 — **инженерные прикидки
   по Вт/м²**, не результат расчёта.
2. **Границы насосов (B-16, B-17) и труб (B-14, B-15) выведены из кода и данных, но не
   подтверждены прогоном.** `pickPump`/`pickPipe` требуют собранного графа гидравлики.
   Числа 5.53 м³/ч и ≈7.1 м — расчётные.
3. **Потолки радиаторов на комнату (12.7 / 15.4 кВт)** — произведение констант
   `maxUnitsPerRoom × max(outputWatts)`; не проверено, срабатывает ли раньше
   `maxSectionsHeuristic = 80` или правило 70 % ширины окна.
4. **Число петель ТП в FIX-06 / FIX-12** (≈ 19) посчитано из формулы `ufhPipeMetersPerSqM`
   при шаге 150 мм и `layoutFactor = 1.1`; фактический шаг подбирается автоматически
   (`ufhPipeSpacingResolve.js`) и может отличаться.
5. **Не проверено фактически, что HS256 + `PROJECTS_AUTH_ENABLED=true` действительно
   пропускает admin-запрос.** Вывод сделан по коду (`projectsAuthConfig.js:46-54`,
   `verifyAccessToken.js:60-70`, отсутствие вызова `validateAuthConfiguration` на старте) —
   но приложение не поднималось. Перед тем как строить на этом фикстурный загрузчик,
   нужен один живой прогон.
6. **`PLATFORM_ADMIN_EMAILS` → `role: 'admin'`** — цепочка `mapJwtPayload` → `resolveUser` →
   Mongo `users` не прослежена до конца; неизвестно, требуется ли предварительно создать
   пользователя в Mongo, чтобы `requireRole('admin')` прошёл.
7. **Разрывы модельного ряда для `manifold` по пропускной способности не посчитаны** —
   в данных нет ни `kv`, ни `maxFlowM3h`; ограничение только по числу выходов.
8. **Не проверено поведение при `CATALOG_SOURCE=mongo`** — весь анализ сделан по
   файловому каталогу. Возможны расхождения нормализации (`mongoDocToCatalogProductDoc`,
   `uniboxMongoDocToCatalogRow`).
9. **Тексты UI-предупреждений** взяты из исходников backend (украинский, дословно). Их
    соответствие тому, что видит пользователь во фронте, не сверялось.
