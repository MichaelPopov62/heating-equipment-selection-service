### 1.3 Что покрывается и почему

**Покрывается полной клеткой `A·H` по всем 13 фикстурам.** Это прямой ответ на приоритет
владельца №0 («проходимость анкеты»): аноним — самая массовая персона, и ровно она
воспроизводит главный симптом. Каждая фикстура прогоняется до сметы ровно один раз.

**Клетка `M·H` покрыта только на FIX-01…FIX-04.** Различия между фикстурами живут в расчётном
ядре, а не в связке «проект ↔ share ↔ PDF». Гонять сохранение проекта на всех 13 объектах —
чистое умножение времени без прироста покрытия риска.

**Клетка `C` (клиент по share) покрыта тремя кейсами.** Share-страница —
read-only `SharePresentationPage.tsx`, её поверхность не зависит от сетапа объекта:
одни и те же «Клієнт:», «Об'єкт:», «Опубліковано:», «Кошторис», «Завантажити PDF».
Достаточно одного happy-пути, одного PDF и одного битого токена.

### 1.4 Клетки, сознательно оставленные пустыми

| Клетка | Почему не покрываем |
|---|---|
| `AD·H` на фикстурах | Админ отличается от мастера **только** доступом к чужим проектам и к `/admin/**` (`projectAccess.js:123-128`). Прохождение анкеты у него идентично `M`. Проверяем разницу, а не повтор. |
| `A·I` на FIX-02…FIX-13 | Механика черновика (`heatcalc:survey-draft:v1`) не зависит от содержимого анкеты. Двух фикстур (FIX-01, FIX-04 — дом и квартира, разные ветки `migrateDerivedState`) достаточно. |
| `C·I` (клиент прерывает) | Share-страница не имеет состояния: ни черновика, ни мутаций, ни localStorage. Прерывание = перезагрузка = тот же `GET /api/v1/public/shares/{token}`. |
| FIX-05…FIX-13 × `E` | Ошибочные пути живут в валидации входа и в шапке, они не зависят от фикстуры. Ошибочные ветки вынесены в `NEG` и параметризованы по полям (D-01…D-30 из R2 §4), а не по объектам. |
| `AD` × смена тарифа с гейтом | Гейтов по `subscription` нет: `authorizationPolicy.js:2` — «role/subscription без quota-gates». Единственный видимый эффект — бейдж и контакт публикатора на share (`buildPublisherPresentation.js:14`). Покрыт ADMIN-001; всё остальное — отложенный блок §10. |
| Любая клетка с климатом по геолокации | Из UI недостижимо: фронт всегда шлёт `outsideC` и никогда `location` (`buildCalcRequestPayload.ts:198-199`), поля «Місто» в анкете нет (RISK-UX-24). Покрытие — unit/API, §10. |

## 2. Предусловия и стратегия селекторов

### 2.1 Общие предусловия окружения

| Переменная | Значение | Зачем |
|---|---|---|
| `CATALOG_SOURCE` | `file` | детерминированный каталог `backend/test_data.json.example`, без Mongo (R4 §1.4, §5.1) |
| `RATE_LIMIT_DISABLED` | `true` | **обязательно**, иначе набор упрётся в 20 запросов/15 мин (RISK-PERF-05). Читается на импорт-тайме (`rateLimiters.js:70-110`) ⇒ менять между кейсами нельзя, только рестартом процесса |
| `NODE_ENV` | не `production` | при `production` `RATE_LIMIT_DISABLED` игнорируется (`projectsAuthConfig.js:197-199`) |
| `PROJECTS_AUTH_ENABLED` | `false` для уровня 1, `true` + JWKS-стаб для уровня 2 | при `false` `requireRole` отдаёт `403 ADMIN_REQUIRED` **всем** (`requireRole.js:21-28`) ⇒ админка и импорт недоступны |
| `PROJECTS_DEV_OWNER_ID` | `000000000000000000000001` | владелец проектов без Clerk |
| `MONGODB_URI` | `mongodb-memory-server` либо сервис `mongo:7` | нужен для `PROJECT`, `SHARE`, `PDF`, `FEEDBACK`, `ADMIN`, `AUTH` |
| `METEOSTAT_*`, Nominatim | **мок не нужен** | браузерные E2E климат не задевают by construction (N-09, R4 §4.7) |
| `PDF_REQUIRE_BROWSER` | `1` | иначе пропажа Chromium даёт тихий SKIP (`verifyProjectPdf.js:144-146`) |

**Общий `beforeEach`:** очистка `localStorage['heatcalc:survey-draft:v1']`, закрытие
cookie-баннера («Ми використовуємо необхідні cookie…» → кнопка «Зрозуміло»,
`AppRouter.tsx:89`), `context.grantPermissions(['clipboard-read','clipboard-write'])` для
кейсов share, `acceptDownloads: true` для PDF.

### 2.3 Где `getByLabel` / `getByRole` работают

**Работают надёжно и сегодня:**
- шаг «Об'єкт» — все 14 контролов имеют уникальные `id` + `<label htmlFor>`;
- три температурных поля используют обёртывающий `<label>`: `getByLabel('Всередині, °C')`,
  `getByLabel('Зовні, °C')`, `getByLabel('Повітря в санвузлі, °C')` — уникальны на странице;
- шаги «Котел», «Радіатори», «Водонагрівач», «Гаряча вода» — уникальные `id` на страницу;
- шапка: `getByRole('textbox', { name: "Ім'я клієнта" })`, кнопки по тексту «Проєкти»,
  «Зберегти», «Посилання», «PDF / Завантажити», «Вийти з проєкту»;
- меню PDF: `getByRole('menuitem', { name: 'Фінансовий підсумок (PDF)' })` и
  `{ name: 'Фінанси + технічний розрахунок (PDF)' }`;
- левое меню: `getByRole('navigation', { name: 'Етапи анкети' })` →
  `getByRole('button', { name: 'Приміщення' })`; текущий шаг — `aria-current="step"`;
- карточка комнаты: `getByRole('article', { name: 'Приміщення 1' })`;
- радиогруппа режима ТП: `getByRole('radiogroup', { name: 'Режим опалення' })`;
- группа сезона ХВ: `getByRole('group', { name: 'Розрахункова температура холодної води' })`.

### 2.4 Требуемые атрибуты: конвенция и адреса

**Конвенция именования:** `data-testid="<область>-<сущность>[-<уточнение>]"`, kebab-case,
только латиница, шаблонизация по стабильным id: `room-<roomId>-area`,
`room-<roomId>-wall1-area`, `window-<roomId>-<index>-width`. Область — из фиксированного
словаря: `step`, `object`, `room`, `window`, `hw`, `ufh`, `boiler`, `rad`, `wh`, `hyd`,
`result`, `bom`, `header`, `share`, `dev`, `admin`.

**Атрибуты состояния (не `testid`, а семантика) — минимум, без которого набор недостоверен:**

### E2E-AUTH-001 — вход и появление персональных возможностей
- **Приоритет:** P0 · **smoke** · **Персона:** аноним → мастер-user
- **Предусловия:** уровень 1 — `VITE_PROJECTS_BEARER_TOKEN` / `localStorage['projectsApiBearerToken']`
  через `context.addInitScript`; уровень 2 — JWKS-стаб. **НЕ ПРОВЕРЕНО**, пропускает ли

  1. Открыть `/` анонимом, нажать «Проєкти».
  2. Убедиться в редиректе на `/login?returnTo=%2Fprojects` и заголовке
     «Вхід до HeatCalc Pro».
  3. Установить Bearer-токен, перейти на `/projects`.
  4. Прочитать `GET /api/v1/me`.
  5. Вернуться в анкету, довести до сметы, нажать «Зберегти».
- **Ожидаемый результат:** шаг 2 — редирект корректен (единственная кнопка шапки,
  которая ведёт себя правильно у анонима); шаг 3 — страница «Проєкти клієнтів» открыта;
  шаг 4 — `200` с профилем, в шапке виден бейдж тарифа («Free» / «Pro» / «Marketplace»,
  `aria-label="Тариф облікового запису"`); шаг 5 — `POST /api/v1/projects` → `201`,
  а не `401`.
- **Чем ассертить:** URL редиректа дословно; код `/api/v1/me`; текст бейджа;
  `201` вместо `401`.
- **Почему может сломаться:** `ProtectedRoute` смотрит на состояние `AuthProvider`, а не на
  наличие токена; Clerk грузится лениво по маршруту (`shouldLoadClerkForPath`) — при живом

  выключен, иначе флейк по чужому аптайму. Дополнительно: прод работает на
  **development-ключах Clerk** (RISK-SEC-04) — не тащить это в тестовую конфигурацию.
- **Источник:** RISK-SEC-04, R2 §9 п.1, U4 группа D, брифинг «вход/выход».

### E2E-AUTH-004 — IDOR: чужой `projectId` даёт 404, а не 403
- **Приоритет:** P1 · **Персона:** мастер-user (чужой ресурс). **Заблокирован B4.**
- **Предусловия:** уровень 2, два пользователя `userA` и `userB`, у каждого свой проект.
- **Шаги:** от имени `userB` выполнить `GET`, `PUT`, `DELETE` `/api/v1/projects/{idA}`,
  `POST /api/v1/projects/{idA}/calc`, `GET /api/v1/projects/{idA}/calculations`,
  `GET /api/v1/projects/{idA}/pdf`, `POST /api/v1/projects/{idA}/share`.

## 7. NEG / BOUND — негативные и граничные

### E2E-NEG-001 — 429 при автопересчёте: прод-лимит 20 запросов / 15 мин по IP
- **Приоритет:** P0 · **Персона:** аноним. **DevPanel запрещён** (обходит дебаунс).
- **Предусловия:** **отдельный процесс бэкенда** с `RATE_LIMIT_CALC_PER_15M=20` и
  **без** `RATE_LIMIT_DISABLED` — лимитеры создаются на импорт-тайме, менять в рантайме
  бессмысленно. Кейс запускается в изолированном проекте Playwright, чтобы не «съесть»
  лимит остальным.
- **Шаги:**
  1. Пройти анкету FIX-01 обычным темпом: каждое изменение поля триггерит авторасчёт
     с дебаунсом 700 мс.
  2. Считать `POST /api/v1/calc`.
  3. Продолжать заполнение, пока не придёт `429`.
  4. Прочитать заголовки ответа и экран.
- **Ожидаемый результат:** **21-й запрос → `429`**, тело
  `{"message":"Забагато запитів","code":"CALC_RATE_LIMIT_EXCEEDED"}`;
  на экране — та же единственная строка ошибки без объяснения, что это лимит;
  дальнейшее заполнение анкеты бессмысленно. Дом на 8–12 комнат уверенно даёт 20+ пересчётов,
  то есть **реальный пользователь упирается в лимит в середине анкеты**.
  Целевое (продуктовое решение, S1 §6 п.10): поднятый лимит, либо явная кнопка
  «Розрахувати», либо ключ по сессии вместо IP.
- **Чем ассертить:** номер запроса, на котором пришёл `429`; `error.code`;
  наличие `Retry-After` либо `RateLimit-*` (**НЕ ПРОВЕРЕНО**, какой draft отдаёт
  `express-rate-limit@8` при `standardHeaders: true`).
- **Почему может сломаться:** **это риск не только продукта, но и самих тестов** —
  весь набор без `RATE_LIMIT_DISABLED=true` упрётся в тот же лимит на третьем кейсе.
  Второй риск: `rateLimiters.js:40` использует опцию `max`, которая в v8 могла быть заменена
  на `limit`; если так, лимит молча стал библиотечным дефолтом и кейс никогда не покраснеет.
  Проверить первым же интеграционным тестом после `npm ci` (блокер **B6**).
- **Источник:** RISK-PERF-05 (ТОП-20 #15), RISK-API-08, RISK-INFRA-10, S1 §3.10.

## 8. Организация прогона, флейки, CI-слои

### 8.1 Двухуровневая архитектура набора

| Уровень | Против чего | Кейсов | Оракул | Зачем |
|---|---|---|---|---|
| **Уровень 1 — быстрый** | `npm run dev` (Vite dev + backend) | ≈ 72 (82 %) | DevPanel: «Report», «CalcInput», «Модули», «POST /api/v1/calc» без дебаунса | основная масса функциональных проверок; экономия ≈20–35 ч на построении собственных оракулов |
| **Уровень 2 — доверенный** | `vite build` + `vite preview` | ≈ 16 (18 %) | только DOM-маркеры `data-calc-phase` / `data-source` / `data-error-code` | гарантия production-артефакта: dev-билд включает ветки, которых в проде нет (`WarmFloorSection.tsx:122-129`, React Query Devtools) |

**Весь smoke идёт уровнем 2.** Иначе PR-гейт проверяет не тот артефакт, который едет в прод.
Уровень 2 **невозможен без маркеров** из §2.4 (14–25 ч) — до их появления smoke стоит
на слое «id» с тегом `@fragile-id`.

**Почему мобильных кейсов ровно три.** U4 прошёл 375×812 и зафиксировал: горизонтального
скролла нет (`scrollWidth === clientWidth === 375`), меню корректно превращается в блок из
11 кнопок, все поля и кнопки доступны, кнопки шапки переносятся без обрезки
(S1 §5 п.17 — «мобильная вёрстка держится»). Дублировать на мобильном все 88 кейсов —
удвоение времени прогона ради проверки того, что уже проверено вручную и признано рабочим.
Мобильный проект существует ради **трёх** вещей: две таблицы результата шире контейнера,
обрезка подписей `<select>`, тач-таргеты подвала 17–19 px.

**Почему WebKit и Firefox только на smoke.** Приложение не использует ничего браузерно-
специфичного, кроме `download` по blob-URL и Clipboard API; оба покрыты одним кейсом каждый.
Полный кросс-браузерный прогон утроил бы время без нового риска.

### 8.3 Политика по флейкам и quarantine

**Запреты (проверяются линтером тестов):**
1. `page.waitForTimeout` — **запрещён полностью**. Ожидания только по `data-calc-phase`,
   `data-report-epoch`, `waitForResponse`, `waitForFunction` на `localStorage`.
2. `waitForResponse('**/api/v1/calc')` без страховки — **запрещён**: при dedup POST законно
   не уходит и ожидание зависает (CALC-002). Всегда с `Promise.race` против смены фазы.
3. Ассерты на абсолютные денежные суммы и модели SKU — только внутри golden-фикстур
   с `catalogSha`.
4. Ассерты по текстам, которые правит F-11, — только с тегом `@fragile-text`.

**Классификация и quarantine:**

| Состояние | Критерий | Что происходит |
|---|---|---|
| `stable` | 20 ночных прогонов подряд без падений, стоит на слое «атрибут» | допускается в smoke и в PR-гейт |
| `@fragile-id` / `@fragile-text` | стоит на слое «id» или «текст» | только ночной прогон, в PR-гейт не входит |
| `@quarantine` | ≥ 2 падения в 20 ночных прогонах **без** изменения продукта | исключается из гейта, заводится тикет с владельцем, **SLA 10 рабочих дней** |
| `@expects-defect` | кейс фиксирует текущее дефектное поведение | обязателен комментарий с `RISK-*` и ожидаемой датой переписывания; **зелёный такой кейс не означает, что продукт исправен** |

**Ретраи:** в CI `retries: 1`, локально `retries: 0`. Кейс, прошедший со второй попытки,
автоматически помечается как flaky-кандидат; два таких раза за неделю → `@quarantine`.
**Ретраи не лечат** ни одну из известных причин: дебаунс 700 мс, дебаунс записи черновика
400 мс, dedup, гонка пресетов, SSE-таймауты. Все они закрываются детерминированными
ожиданиями, а не повторами.

**Выход из quarantine:** 3 подряд зелёных ночных прогона после фикса + перевод кейса
на слой «атрибут».

## 10. Что сознательно НЕ покрываем E2E и почему

### 10.1 Физика расчёта — golden и unit, не E2E

**RISK-CALC-01 (вентиляция плоским `kVent` 1.3/1.1 вместо `0.34·L·ΔT`), RISK-SEC-01
(лимит температуры поверхности ТП делится на `rFinish` вместо `R_CONV_UP_M2KW = 0.1`),
RISK-SEC-02 (применяется технический максимум 35 °C вместо комфортных 29),
RISK-CALC-07…-31.**

Причина одна: **E2E не может отличить неверное число от верного.** Продукт отдаёт
правдоподобный результат — U2 получил 2.02 кВт на 158 м² при −19 °C, и ни один браузерный
ассерт не покажет, что это в 2.5–3 раза меньше правды. Нужен эталон ручного расчёта, а не
прохождение анкеты. E2E здесь даёт только `heatLossKw > 0` — иллюзию покрытия.
**Куда: golden-набор на FIX-01…FIX-06 против ручного расчёта + unit на матрицу
`topBoundary × bottomBoundary` (D2).**

### 10.2 Целостность сметы — property, не E2E

**RISK-MONEY-01 (трубы `trunk`/`dhw` вне сметы и вне базы 40 %/15 %),
RISK-MONEY-02 (`price ?? 0`), RISK-MONEY-03, -04, -07, -08.**

E2E видит только итоговую сумму, а дефект состоит в **отсутствии позиции**, которую
пользователь не знает как искать. Проверять «в смете нет строки, которой не должно не быть» —
это инвариант над структурой отчёта, а не сценарий. BOUND-006 покрывает **один** видимый
случай (магистраль при PEX); остальное — property-тесты над `buildFinancialBom`.
**Куда: property-набор (D2).**

### 10.3 Контракт API и таксономия ошибок

**RISK-API-01…-14, RISK-UX-03 в полном объёме (48 путей ошибки, из них 1 несёт адрес поля),
RISK-AUTH-04…-09, 18 расхождений OpenAPI ↔ код.**

NEG-005 покрывает 15 представительных случаев из UI. Проверять все 60+ кодов через браузер —
это часы прогона ради того, что HTTP-тест делает за секунды.
**Куда: контрактный слой (D3), плюс guard «каждый `VALIDATION_ERROR` несёт непустой
`details[]` с `instancePath`».**

### 10.4 Миграции черновика в полном объёме

**RISK-DATA-11.** 18 преобразований `migrateSurveyDraft` теряют данные молча
(неизвестный `ufhPresetId` → `null`, `wiringLayoutV3` чужой версии → полная пересборка,
`externalWalls` без `presetId` → подстановка газобетона, `Number(x) || 20` съедает честный `0`).
E2E проверяет один round-trip (PROJECT-002, NEG-009); проверять 18 преобразований кликами
бессмысленно.
**Куда: golden-снимки v1/v2/v3 → v4 по каждому мигратору + компонентные тесты (D2).**

### 10.5 Климат

**RISK-CALC-13…-16, RISK-UX-24.** Подсистема `climate/*` написана и работает, но
**из UI недостижима by construction**: фронт всегда шлёт `outsideC` и никогда `location`,
поля «Місто» нет. Это хорошая новость для E2E — браузерные тесты герметичны **без единого
мока внешнего HTTP**. NEG-003 вынесен на API-уровень намеренно.
**Куда: unit с подменой `globalThis.fetch` + 3 города фикстур (< 100 КБ) (D2/D3).**

### 10.6 UX-качество, которое нельзя выразить ассертом

**RISK-UX-13 (дефолты `20`, `−5`, `300`, `2.7` неотличимы от пользовательского ввода),
RISK-UX-16 (шаг «Котел» не даёт выбрать котёл), RISK-UX-17 (шаг «Приміщення» съедает 40 %
времени: 12–15 полей на комнату, площадь стены в м² вместо длины),
RISK-UX-27 (дублированный заголовок «Водонагрівач і сценарій ГВП», схемы ГВС абзацами
внутри `<option>`), RISK-UX-28 («Унітаз» в точках горячей воды),
RISK-UX-29 (нет кнопки «Далі» ни на одном шаге), RISK-UX-36 («Довідник даних» внутри анкеты),
RISK-MATCH-28 (объём БКН и время нагрева задать нельзя),
RISK-MONEY-06 / -12 / -13 (в смете нет фитингов, даты, НДС, расшифровки работ).**

Всё это — дефекты, которые видит человек и не видит ассерт. Автотест зафиксирует, что
поле существует и принимает значение; он не зафиксирует, что пользователь не понимает,
что вводить. Живой проход четырьмя персонами уже дал эту информацию — повторять её
автоматом нечем.
**Куда: UX-метрики и повторный модерируемый проход после F-01…F-12 (D5).**

### 10.7 Состояния, недостижимые из UI

- **`bootstrapMode === 'error'`** — единственный путь `retryBootstrap()` после сбоя resolve,
  но `resolveInitialBootstrapSnapshot` ловит все исключения. **Практически непокрываемо**;
  не тратить на это время.
- **`HEATING_SYSTEM_INVALID`** — проверка стоит после безусловной перезаписи `supplyC`/`returnC`
  пресетом, `returnC`/`supplyC` в UI отсутствуют вовсе. Код практически мёртв.
- **`UFH_MODE_FINISH_MISMATCH`** — объявлен в документации, функции в `backend/src` нет.
- **Электрокотлы (B-02)** — в каталоге 0 SKU с `fuel = 'Электричество'`, фильтра по топливу
  в `pickBoiler` нет вообще. Сценарий «подобрать электрокотёл» **исключён из плана**
  до появления SKU; вместо E2E — guard на состав каталога (сейчас падает).
- **Гейты по тарифу** — их нет (`authorizationPolicy.js:2`). ADMIN-001 проверяет только
  наблюдаемый эффект. **Отложенный блок** ниже.

### 10.9 Проверено и работает — не тратить усилия E2E

Из S1 §5, чтобы следующие фазы не открывали эти вопросы заново:
XSS невозможен в «Ім'я клієнта» и «Назва» (React экранирует, проверено обоими векторами);
IDOR закрыт сужением Mongo-фильтра, TOCTOU закрыт повторным применением фильтра
в `findOneAndUpdate`/`findOneAndDelete`; арифметика сметы сходится (40 %/15 % от одной базы,
расхождение 1 грн на округлении); расчёт детерминирован (`Math.random` в `report`/`matching`/
`hydraulics` — 0 попаданий); каталог детерминируем при `CATALOG_SOURCE=file`;
мобильная вёрстка 375×812 держится; шаг «Гаряча вода» клампит корректно все поля;
«Вийти з проєкту» спрашивает подтверждение и сохраняет данные при отмене;
«Проєкти» у анонима корректно редиректит на `/login?returnTo=%2Fprojects`;
восстановление черновика из `localStorage` работает, битый JSON удаляется без падения;
ни одного белого экрана, JS-исключения или 5xx за 118 атак и четыре полных прохода.

**Единственные позитивные регрессии, которые всё же оставлены в наборе** (потому что дёшевы
и защищают дорогое свойство): REGR-028 (мобильная вёрстка); устойчивость к XSS, символам нулевой ширины и мусорному
вводу проверяется внутри REGR-016 и NEG-011; AUTH-003 (публичные поверхности остаются публичными), NEG-008 (битый черновик не роняет).
