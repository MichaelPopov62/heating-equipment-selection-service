## Резюме (сколько претензий, пересчитанная оценка плана)

**23 претензии:** 6 блокеров, 10 существенных, 7 желательных.

**Пересчитанная оценка: 228–416 человеко-дней против плановых 163–304.** Перерасход
**+40 % по обоим краям диапазона.** Он не размазан ровным слоем — он сидит в четырёх местах:

1. **Порядок работ создаёт гарантированную переделку.** §12.5 п.4 прямо предписывает делать
   физику (A-3) **после** unit-волны 1 (A-5) и golden (A-7). Это значит: сначала написать
   282 характеризационных кейса и 30 снапшотов, которые фиксируют дефект, потом дефект
   исправить, потом всё переписать. **80–150 ч в Фазе A и 40–80 ч в Фазе B, забюджетировано 0.**
   Это самая дорогая строка критики и самая дешёвая для исправления — переставить два блока.
2. **Оценка написания кейсов взята из нормы для проекта, у которого есть фикстуры.** У этого их
   ноль: `data-testid` = 0 (проверено: `grep -rn data-testid frontend/src | wc -l` → **0**),
   тестов нет ни одного, `node_modules` не установлены ни в одном из четырёх пакетов, ни один
   verify-скрипт никогда не запускался в этой ветке.
3. **Бюджеты CI занижены в 2–3 раза** и противоречат числам самого плана (§C2-02).
4. **Правок прод-кода не одна, а минимум четыре** (§C2-03).

**Прогноз флейков: 14 кейсов из 88 имеют структурную причину флейка, 5 из них — в PR-smoke.**
При `retries: 1` это даёт **15–30 % ложно-красных PR** — уровень, на котором гейт перестают
уважать через месяц.

**Хорошая новость.** Технических невозможностей в плане нет. Все шесть блокеров — это
недооценка или порядок, а не «не взлетит». Если принять все 23 альтернативы, объём падает до
**≈180–300 человеко-дней при ~60 % заявленного scope** — то есть плановое число достижимо,
но не для планового набора.

## Ранжированный список претензий

### C2-01 — Физика чинится после того, как её зафиксировали в 312 тестах

- **Серьёзность:** блокер
- **Что не взлетит:** §12.5 п.4: «**A-3 (физика) — только после A-5/A-7**, а не до: без
  характеризационных тестов исправление физики нельзя отличить от новой ошибки». §12.4, вторая
  цепочка: «A-3 Физика P0 (56–112 DEV) → (после правок — **перепрогон A-5/A-7/A-8**)».
  Строка «перепрогон» в таблице оценок §12.1 отсутствует — на неё выделено **0 часов**.
- **Почему:** «перепрогон» — эвфемизм. A-3 меняет `resolveKVent` на `0.33·L·ΔT`, формулу
  `requiredKwFromHeatingAndDhw`, базу `nominalReservePercent`, лимит потока через
  `R_CONV_UP_M2KW`. Это ровно те величины, по которым построены группы A1 (78 кейсов), A2 (62),
  A3 (96), A6 (84) — **320 из 282 кейсов волны 1 попадают под удар минимум частично**, а все
  три среза `G-A`/`G-B`/`G-C` × 5 объектов = 15 снапшотов переписываются полностью и требуют
  подписи владельца-теплотехника. План сам это описывает механикой «`it.fails` + ЗАМОК»: каждый
  такой кейс по определению обязан быть переписан в момент фикса. Плюс слой Г: §7.3 п.2 требует,
  чтобы «эксперт подтвердил, что новое значение **ближе** к ручному расчёту» — то есть повторная
  экспертная сверка после каждого блока правок физики.
- **Цена по плану / реальная цена:** 0 ч / **80–150 ч QA в Фазе A + 40–80 ч в Фазе B**
  (переписать ~180 кейсов × 0.25–0.5 ч, пере-принять 15–30 снапшотов, повторить 42 сверки).
- **Более дешёвая альтернатива:** **переставить порядок.** Сначала A-3 (DEV чинит физику),
  и только потом A-5/A-7 пишут тесты на **уже правильное** поведение. Аргумент плана
  («нельзя отличить фикс от новой ошибки») закрывается втрое дешевле: перед A-3 сгенерировать
  **машинный характеризационный слепок** — прогнать `buildReport` на 14 фикстурах и сохранить
  полный отчёт как один JSON на объект (**4–8 ч на генератор, не 120 ч на кейсы**). Слепок и есть
  «замок»: после фикса диффы читаются построчно, каждый диффнутый показатель обсуждается один
  раз, затем слепок принимается заново. Кейсы слоя А пишутся **после** и сразу как гейты, без
  режима X.
- **Что теряем, приняв альтернативу:** между A-3 и A-5 остаётся окно (1–3 недели), в котором
  регресс в `logic/`/`matching/` ловится только слепком (грубее: диффом, а не именованным
  ассертом с номером порога). Плюс на время A-3 нет «покрытия решений числом» — метрика §7.6
  «110 из 193 к концу волны 1» сдвигается на конец фазы.

### C2-02 — `e2e-smoke ≤ 8 мин` противоречит арифметике самого плана

- **Серьёзность:** блокер
- **Что не взлетит:** §9.3 «e2e-smoke · каждый PR · 23 кейса, **уровень 2**, 4 shard'а ·
  **≤ 8 мин** · блокирующий». §6.0: «Smoke — ≤ 8 мин на 4 shard'ах (последовательно ≈ **26 мин**)».
- **Почему:** два независимых счёта, оба против.
  1. **Тестовое время.** §6.0 сам пишет: «Один полный проход `FIX-01` — 60–90 с с DevPanel и
     **150–200 с без него**». Весь smoke идёт уровнем 2 (§6.4: «Весь smoke идёт уровнем 2»), а
     на уровне 2 DevPanel запрещён. В smoke пять полных проходов (`E2E-SURVEY-001…004`, `-006`)
     = **12.5–16.7 мин**; `E2E-BOUND-003` — это **два** полных прогона = ещё 5–7 мин; восемь
     `E2E-REGR` требуют заполнения анкеты до расчёта; `PROJECT-001/002`, `SHARE-001`, `PDF-001`,
     `AUTH-001` — цикл «заполнить → рассчитать → сохранить → открыть». Реалистичный
     последовательный smoke — **40–55 мин**, а не 26. На 4 shard'ах = 10–14 мин чистого теста.
  2. **Фиксированные накладные на shard.** GitHub Actions `ubuntu-latest` — 2 vCPU. На каждом
     shard'е: `npm ci` в четырёх пакетах (текущий `verify.yml` устанавливает shared, backend,
     frontend; корневой добавляет П5); скачивание Chromium для Playwright (`--with-deps` — это
     ещё и `apt install`, 60–120 с); **отдельное** скачивание Chrome для `puppeteer` (он в
     `dependencies` бэкенда, `renderPdfFromHtml.js:35` резолвит bundled-бинарь); бинарь mongod
     для `mongodb-memory-server`; **`vite build`** для уровня 2 — это `tsc -b` по 291 файлу
     (28 869 строк) плюс `prebuild`/`postbuild` скрипты. **4–8 мин на shard даже с кэшами,
     до первого теста.**
  Итог: **15–22 мин** вместо ≤ 8. Ночной ≤ 60 мин (§9.3) при 88 кейсах ≈ 3 ч 10 мин
  последовательно / 6 shard'ов = 32 мин чистого теста + непараллелизуемые проекты
  `pdf-serial` / `sse-serial` / `ratelimit-isolated` + property 5 000 + golden 14 + Stryker
  (§C2-11) → **2.5–5 ч**. Пре-релиз ≤ 90 мин — тем более.
- **Цена по плану / реальная цена:** ≤ 8 / **15–22 мин**; ночной ≤ 60 / **150–300 мин**.
- **Более дешёвая альтернатива:** три шага, все дешёвые.
  1. **Сборку вынести в отдельный job** и передавать `frontend/dist` артефактом — четыре
     shard'а перестают собирать фронт четыре раза (−2–4 мин × 4).
  2. **PR-smoke сократить с 23 до 8 кейсов**: `E2E-REGR-001`, `-003`, `-005`, `E2E-SURVEY-001`,
     `E2E-CALC-001`, `E2E-PROJECT-001`, `E2E-PDF-001`, `E2E-BOUND-003`. Это оба отказа живого
     прохода, обе точки отказа мастеров, один полный проход, дедупликация, сохранение, PDF и
     главный доменный дефект. **≈ 12–15 мин последовательно, 2 shard'а, ≤ 8 мин wall-clock.**
  3. Остальные 15 «бывших smoke» перевести в **merge-queue tier** (гоняется на очереди слияния,
     не на каждый push) — компромисс между PR и ночью.
- **Что теряем, приняв альтернативу:** между пушем и мержем есть окно, в котором `SURVEY-002/003/
  004/006`, `SHARE-001`, `AUTH-001`, `FEEDBACK-001`, `NEG-006/008`, `REGR-004/006/007/010/021`
  красные незамеченными. Для команды «1 QA + 1 DEV» это часы, не дни.

### C2-03 — «Одна минимальная правка прод-кода» — их минимум четыре

- **Серьёзность:** блокер
- **Что не взлетит:** §9.2 объявляет прод-кодом только П1 `createApp()` (3–6 ч) и П6 маркеры.
  §9.1 отдельно гордится «**ноль правок прод-кода**» для мока внешнего HTTP.
- **Почему:** проверено по исходникам, три дополнительные правки обязательны.
  1. **`OverwriteModelError`.** `mongoose.model(...)` зовётся на импорт-тайме в девяти файлах
     `backend/src/models/`, и **в четырёх из них нет guard'а `mongoose.models.X ??`**:
     `Appliance.js:39`, `WaterNorms.js:25`, `Recommendation.js:42`,
     `UnderfloorHeatingPreset.js:21`. При этом §7.7 прямо предписывает `vi.resetModules()` для
     сброса модульных кэшей, а §9.1 — `pool: 'forks', isolate: true`. Второй импорт модели в том
     же процессе бросит `OverwriteModelError`. **Правка прод-кода в четырёх файлах.**
  2. **`retryWrites=true` + `w=majority` навязываются принудительно** —
     `utils/mongoConnectionConfig.js:49-54`. Retryable writes требуют реплика-сета; на standalone
     `mongod`, который поднимает `MongoMemoryServer` по умолчанию, поведение в лучшем случае
     недетерминировано. Либо правка `normalizeMongoUri` (прод-код), либо `MongoMemoryReplSet`
     (см. C2-05).
  3. **`data-error-code` — это не атрибут, а рефакторинг канала ошибок.** Блокер B3 оценён в
     «1–2 ч (внутри F-01a)». По коду: ошибки живут как **строки** через `useSurveyCalc.ts:95,110,
     144-149` → `runSurveyMutationPipeline.ts` → `AppSurveyContent.tsx`; кода ошибки нет **ни в
     одном слое**. Чтобы вывести `data-error-code` в DOM, нужно протащить типизированную ошибку
     через `apiError.ts`, `calc.ts`, `useSurveyCalc.ts`, `runSurveyMutationPipeline.ts`,
     `types.ts`, `SurveySessionProvider.tsx` — **6–10 ч, не 1–2**.
  Побочно: `verifyAccessToken.js:10` кэширует `remoteJwks` в module-scope, `rateLimiters.js:70-110`
  и `logger.js:25` читают `process.env` **до** `loadEnv()` (`index.js:24` — импорты хойстятся),
  `validate.js:243` делает top-level `await` с чтением `components/schemas/CalcInput.yaml` из
  корня репо, а `catalog/loadCatalog.js:15` импортирует из `backend/scripts/`. Это не правки, но
  это четыре дополнительных ограничения на раскладку тестов.
- **Цена по плану / реальная цена:** 3–6 ч / **3–6 (createApp) + 2–4 (guard'ы моделей) +
  6–10 (`data-error-code`) + 0–4 (mongo URI) = 11–24 ч**, и всё это DEV на критическом пути.
- **Более дешёвая альтернатива:** сделать все четыре **в один день недели 1** и включить в А-0
  явной строкой, а не «внутри F-01a». Guard'ы моделей — 20 минут механической работы
  (`mongoose.models.X ?? mongoose.model(...)` × 4). Mongo URI не трогать вовсе, а поднять
  `MongoMemoryReplSet` (C2-05). `data-error-code` вынести из F-01a в отдельную задачу с честной
  оценкой, чтобы она не съела бюджет F-01a молча.
- **Что теряем, приняв альтернативу:** ничего по существу — теряется только формулировка «мы
  почти не трогаем прод». Она в любом случае неверна: A-1 + A-2 — это 164–308 ч правок продукта.

### C2-05 — `mongodb-memory-server` — это внешний сетевой сервис, а не герметичность

- **Серьёзность:** блокер
- **Что не взлетит:** §9.1: «БД — **`mongodb-memory-server`**, fallback — сервис `mongo:7`.
  Совместимость с `mongoose@9.5.0` **НЕ ПРОВЕРЕНА — нужен пилот**». §9.5 п.2 отводит на пилот 2 ч.
  §12.1 A-4 держит memory-server как основное решение; §9.2 отвергает Docker-compose, потому что
  он «мешает `mongodb-memory-server`».
- **Почему:** `mongodb-memory-server` **скачивает бинарь `mongod` с `fastdl.mongodb.org`** при
  postinstall или при первом запуске. Это ровно та внешняя зависимость, которую весь §3.3
  старается убрать. Три конкретных отказа:
  1. **Определение платформы.** Раннер `ubuntu-latest` — это 24.04. Официальные сборки MongoDB
     под `ubuntu2404` появились не для всех минорных версий; библиотека вынуждена маппить на
     `ubuntu2204`, и на этом маппинге исторически ломались CI после смены образа раннера.
     Отказ выглядит как «все Mongo-тесты красные с 5 утра, кода никто не трогал».
  2. **`retryWrites=true` на standalone.** `mongoConnectionConfig.js:49-54` навязывает его
     принудительно. Retryable writes определены только для реплика-сета/шарда.
  3. **Кэш.** Без `actions/cache` на `~/.cache/mongodb-binaries` каждый из 6+ job'ов PR-гейта
     качает бинарь заново.
  При этом транзакций в коде **нет** (`startSession`/`startTransaction`/`withTransaction` — 0
  совпадений), Atlas Search и timeseries — нет. То есть реплика-сет продукту не нужен, но
  **навязанный `retryWrites` его требует**.
- **Цена по плану / реальная цена:** 4–8 ч (+2 ч пилот) / **10–18 ч** и постоянный риск
  «зелёное вчера, красное сегодня».
- **Более дешёвая альтернатива:** **поменять основное решение и fallback местами.**
  В CI — `services: mongo:7` (образ тянется из реестра с ретраями GitHub, версия пинится тегом,
  готовность — через healthcheck; ноль кода). Локально — `MongoMemoryReplSet` (одноузловой
  реплика-сет: тот же API, что и `MongoMemoryServer`, +3–8 с на старт, зато `retryWrites` и
  `w=majority` честно работают без правки прод-кода). Решение принимается **в первый день, а не
  на третий**, потому что от него зависят конфиги vitest, которые пишутся на второй.
- **Что теряем, приняв альтернативу:** локальный прогон Mongo-тестов у разработчика без Docker
  становится чуть медленнее (реплика-сет вместо standalone), а CI-конфиг перестаёт быть
  «одинаковым локально и в CI». Второе — реальная потеря, но она дешевле, чем расследование
  плавающих падений скачивания бинаря.

### C2-14 — `grantPermissions(['clipboard-*'])` в глобальном `beforeEach` убьёт весь webkit/firefox smoke

- **Серьёзность:** существенно
- **Что не взлетит:** §6.1 `beforeEach` (**общий для всего набора**): «`context.grantPermissions

  стоит в общем `beforeEach`, падёт **не один кейс, а все 23** — и упадут они в setup, то есть
  без внятного отчёта. Проверка кода подтверждает, что разрешения реально нужны:
  `utils/surveyShare.ts:102-106` зовёт `navigator.clipboard.writeText`, вызовы —
  `useSurveyProject.ts:278,335`.
- **Цена по плану / реальная цена:** 12–20 ч на C-5 / **+4–8 ч отладки**, обнаруженной в самый
  неудобный момент — перед релизом.
- **Более дешёвая альтернатива:** одна строка — `if (browserName === 'chromium') await
  context.grantPermissions([...])`, и в `E2E-SHARE-001` брать токен **из сетевого ответа**
  (§6.2 это уже и предписывает), а проверку буфера обмена вынести в отдельный
  `@chromium-only` кейс. Заодно: `locale: 'uk-UA'` и `acceptDownloads` — это **опции контекста**,

- **Что теряем, приняв альтернативу:** копирование share-ссылки в буфер не проверяется в Firefox

### C2-15 — `E2E-NEG-001` (429) невозможно ретраить, а `retries: 1` включён

- **Серьёзность:** существенно
- **Что не взлетит:** `E2E-NEG-001` — «21-й запрос → `CALC_RATE_LIMIT_EXCEEDED`… Требует
  **отдельного процесса** бэкенда с `RATE_LIMIT_CALC_PER_15M=20` и без `RATE_LIMIT_DISABLED`».
  §6.4: «`retries: 1` в CI».
- **Почему:** окно `express-rate-limit` — 15 минут настенного времени. Если первая попытка упала
  на 19-м запросе (флейк дебаунса, таймаут ожидания), **вторая попытка стартует с уже
  израсходованным лимитом** и упадёт по-другому. Ретрай здесь не лечит, а превращает
  воспроизводимый провал в невоспроизводимый. Плюс 21 запрос через UI при дебаунсе 700 мс — это
  минимум 15–25 с чистого ожидания и 21 полный цикл React-рендера.
- **Цена по плану / реальная цена:** ~2 ч / **6–10 ч** + вечный флейк.
- **Более дешёвая альтернатива:** **сделать это не браузерным кейсом.** 21 `fetch` в цикле
  против `createApp()` + `server.listen(0)` в отдельном vitest-файле с собственным
  `test.env` (`RATE_LIMIT_CALC_PER_15M=20`, без `RATE_LIMIT_DISABLED`). План уже завёл под это
  `vitest.ratelimit.config.ts` (D3 §8 п.1) — надо просто не дублировать проверку в браузере.
  **~1.5 ч, детерминированно, 3 секунды прогона, никакого проекта `ratelimit-isolated` в
  Playwright.** Отдельный браузерный кейс оставить **только** на то, чего HTTP-тест не видит:
  «что пользователь видит на экране при 429» — а это одна строка текста, и её можно проверить
  через `page.route` с подставленным ответом 429 (0.5 ч, без реального лимитера).
- **Что теряем, приняв альтернативу:** не воспроизводим точную последовательность
  «автопересчёт довёл до лимита сам». Но это и не тестируется — это следствие дебаунса, и оно
  уже покрыто `E2E-REGR-014`.

### C2-23 — «Первая неделя ~40 ч» опирается на непроверяемые допущения

- **Серьёзность:** желательно
- **Что не взлетит:** §9.4 расписывает пять дней по 6–8 ч с конкретным результатом: «К концу
  первой недели есть зелёный PR-пайплайн из 6 job, работающий раннер, герметичная авторизация
  через JWKS, рабочий загрузчик фикстур и первый golden-эталон».
- **Почему:** первый пункт §9.5 честно признаёт: «**Ни один тест или скрипт не запускался** —
  `node_modules` отсутствуют во всех пакетах» (проверено: их нет ни в корне, ни в `backend`,
  ни в `frontend`, ни в `shared`). При этом день 1 включает **включение в CI пяти корневых
  verify, которые в CI никогда не работали**, в том числе `verify:language-policy` — а §7.5
  (поправка П4) прямо пишет, что этот гейт «надо переписывать» (6–12 ч, задача `F-11b`).
  Первый же запуск покажет неизвестное число падений. Аналогично `verifyRoomExteriorLayoutHeatLoss.js`
  — «вообще никогда не запускался», и его добавление в цепочку может быть как «0.5 ч», так и
  «полдня на выяснение, почему он красный». Плюс день 3 принимает решение по Mongo
  «и больше не пересматривает» — **после** того, как день 2 уже написал конфиги vitest.
- **Цена по плану / реальная цена:** 40 ч / **50–70 ч**, и результат первой недели вероятнее
  «3–4 job'а зелёные, два в работе».
- **Более дешёвая альтернатива:** **день 0 (2–4 ч), до всякого планирования недели**:
  `npm ci` во всех четырёх пакетах, `npm run verify` целиком, зафиксировать вывод в
  `docs/qa/baseline-verify.md`. Только после этого расписывать неделю — она станет
  предсказуемой, потому что число красных скриптов будет известно, а не предположено. Решение
  по Mongo (C2-05) перенести на день 0 вместе с ним. `verify:language-policy` включать в CI
  **в режиме предупреждения** (не блокирующем) до тех пор, пока `F-11b` его не перепишет —
  иначе день 1 закончится красным main.
- **Что теряем, приняв альтернативу:** один день из недели уходит на измерение, а не на
  строительство. Это единственная строка плана, где предлагаю потратить время, а не сэкономить.

## Что признал реалистичным

Претензий к этим пунктам нет — они проверены по коду и подтвердились.

1. **Стек выбран правильно.** Vitest + Playwright + встроенный `fetch` против `createApp()`
   вместо `supertest` — верно и по существу (ноль новых зависимостей под `verify:dead-code`),
   и по последствиям (тот же процесс ⇒ доступен `invalidateReferenceCache()`).
2. **`vite preview` действительно проксирует `/api`.** Проверено: `frontend/vite.config.ts`
   содержит **отдельный блок `preview.proxy`** с тем же таргетом `http://localhost:3001` и
   таймаутами 120 с — это не унаследованный `server.proxy`. Уровень 2 (прод-артефакт) достижим,
   как план и утверждает. Единственная оговорка — SSE (C2-13).
3. **JWKS-стаб — рабочий путь, и он даже дешевле, чем оценено.** `verifyAccessToken.js:16`
   читает `AUTH_JWKS_URI` из env без каких-либо ограничений; `new URL(jwksUri)` **не проверяет
   протокол**; hardcoded домена Clerk в коде нет вообще (единственное «clerk» — строковый enum
   провайдера в `projectsAuthConfig.js:10`); `AUTH_ISSUER`/`AUTH_AUDIENCE` тоже из env. Оценка
   8–16 ч (§6.1 B4) скорее завышена: реалистично **4–7 ч**. Вывод N-33 про HS256 подтверждён:
   `projectsAuthConfig.js:152-166` действительно fail-fast при `PROJECTS_AUTH_ENABLED=true`.
4. **Отказ от моков Nominatim/Meteostat в браузерных E2E — верно.** Подтверждено:
   единственная точка входа в климат — `buildReport.js:229` (`input.location && inputTemps?.outsideC
   == null`), а внешних `fetch` в бэкенде ровно три и все в `climate/` (`geocode.js:59`,
   `snipClimate.js:108,132`). Вызовов Clerk Backend API из бэкенда нет вообще. Браузерный набор
   действительно герметичен без единого мока внешнего HTTP.
5. **Реплика-сет продукту не нужен.** Подтверждено: `startSession`/`startTransaction`/
   `withTransaction` — 0 совпадений; `$search`/`$vectorSearch`/timeseries не используются;
   единственный `aggregate` — обычный `$group` (`projectsRoutes.js:168`). Претензия C2-05 — про
   навязанный `retryWrites`, а не про потребность продукта.
6. **UI поднимается без Clerk.** Подтверждено: `ClerkLazyRoot.tsx:44-49` — без
   `VITE_CLERK_PUBLISHABLE_KEY` SDK не импортируется вовсе, режим `legacy`;
   `authConfig.ts:13-15` — `VITE_AUTH_REQUIRED` по умолчанию не задан ⇒ `ProtectedRoute:21`
   пропускает всех; для API проектов есть штатный `VITE_PROJECTS_BEARER_TOKEN`
   (`projectsAuthToken.ts:38-41`), прямо описанный в `.env.example` как «Dev без Clerk UI: Bearer
   для API проектов (CI / ручной JWT)». Пилот по `E2E-AUTH-001` («НЕ ПРОВЕРЕНО, пропускает ли
   `ProtectedRoute`») можно закрыть чтением кода: **пропускает**.
7. **A-2 (130–246 ч правок проходимости) не оспариваю** — это число из `D5 §1.0`, оно выведено
   позадачно по 25 задачам `F-*` и выглядит добросовестно.
8. **Диагноз «перевёрнутая пирамида» верен.** Аргумент §4.1 — что слои А/Б/В сравнивают продукт
   сам с собой, а систематическое занижение невидимо изнутри, и потому нужен внешний оракул —
