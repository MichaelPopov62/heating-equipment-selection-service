# C1 — Критика полноты

**Объект критики:** `docs/qa/TEST_PLAN.md` (2107 строк, 14 разделов, версия 1.0 от 2026-08-23).
**Метод:** сверка плана с `_ORCH-NOTES.md` (43 находки), `S1-risk-register.md` (210 рисков),
`R1` (193 порога), `R5` (48 инвариантов), `R6` (B-01…B-21), `R2` (D-01…D-30), `U1`–`U4`,
`D1`–`D5`. Каждое утверждение «этого в плане нет» проверено `grep` по плану **и** по проектному
документу, из которого раздел собран; спорные числа (§7.1 A6-08 / `GA-13`) перепроверены **по
исходному коду продукта**.

## Резюме

| Серьёзность | Претензий |
|---|---|
| **Блокер** | **6** |
| Существенно | 9 |
| Желательно | 5 |
| **Итого** | **20** |

**Три главных вывода.**

1. **План проверяет, что PDF скачался, но нигде не проверяет, что в нём написано.** Приоритет
   владельца №0 сформулирован как «человек забирает смету»; гейт `GA-02` считает успехом факт
   получения файла. Ни один из 831 + 88 кейсов не сравнивает ни одного числа внутри PDF и внутри
   публичной share-страницы с числами отчёта. Документ, который мастер отдаёт клиенту, — единственный
   артефакт продукта, вообще не покрытый планом.
2. **Числа в релизном гейте `GA-13` посчитаны по неверным исходным данным, а связанный с ним P0
   `RISK-SEC-02` не покрыт ничем.** Проверено по коду: применяется `maxSurfaceTemperatureCelsius = 35`
   (не 29), `rFinish` плитки = `0.012/1.05 = 0.0114` (не 0.008). Порог гейта («в коде ≈ 1170 Вт/м²,
   `surfaceTempC` → 20.7 °C») не воспроизведётся; фактически ≈ **1316 Вт/м²** и **21.0 °C**.
   Гейт, порог которого не сходится с продуктом, — это гейт, который снимут при первом же прогоне.
3. **Трассируемости «риск → кейс» нет.** 130 идентификаторов из 210 (в том числе 8 P0) не встречаются
   в плане ни разу. Часть закрыта по существу групповыми формулировками, часть — нет, и **отличить
   одно от другого по документу невозможно**. Для документа, объявленного самодостаточным
   («разделов 3–14 достаточно, чтобы начать работу, не открывая исследовательские отчёты»), это
   означает, что подрядчик не может доказать полноту, а владелец — принять её.

## Ранжированный список претензий

### C1-01 — Порог `GA-13` и кейсы `A6-08…A6-13` посчитаны по неверным исходным данным; `RISK-SEC-02` (P0) не покрыт вообще

- **Серьёзность:** блокер
- **Что не покрыто.** План (§7.1 «Образец характеризационного кейса», §13.1 `GA-13`) утверждает:
  для плитки `rFinish ≈ 0.008`, `maxSurfaceT = 29`, лимит «как в коде» ≈ 1170 Вт/м²,
  `surfaceTempC` при `q = 90` → 20.7 °C. Проверено по коду:
  - `backend/src/logic/ufhRoomHeatFlux.js:170-172` — `maxSurfaceT = surfaceLimits.appliedMaxSurfaceT`,
    а `resolveAppliedSurfaceTemperatureLimits` (`:49-88`) возвращает
    `appliedMaxSurfaceT = finish.maxSurfaceTemperatureCelsius`. Для `ceramic_tile` это **35**
    (`backend/src/data/flooringFinishMaterials.js:16`). Значение
    `comfortMaxSurfaceTemperatureCelsius = 29` (`:17`) кладётся в `appliedComfortMaxSurfaceT`
    и **только пишется в отчёт** (`:219-221`) — поток им не ограничивается никогда. Это ровно
    `RISK-SEC-02` (P0), которого в плане **нет ни одним словом**.
  - `rFinish = computeFinishCoveringResistanceM2KW(finish)` = `0.012 / 1.05 = 0.0114`
    (`flooringFinishMaterials.js:11-14,62-67`), а не 0.008.
  - Отсюда фактический лимит в коде = `(35 − 20)/0.0114 ≈ **1316 Вт/м²**`; `surfaceTempC` при
    `q = 90` = `20 + 90·0.0114 = **21.0 °C**`. Оба числа гейта не воспроизведутся.
- **Чем это грозит.** Кейс `A6-08` («`it.fails` + ЗАМОК») будет красным с первого прогона не потому,
  что дефект починили, а потому что ожидание неверно; его снимут или «подкрутят» — и вместе с ним
  уйдёт единственная находка о безопасности. Одновременно в прод уходит вторая половина дефекта:
  комфортный лимит 29 °C вычисляется, показывается пользователю и **не действует**. Мастер видит
  «поверхня 21 °C» на полу, который физически греется до 35 °C: разрушение ламината/винила и ожог
  ступни — риск, за который отвечает он, а не сервис.
- **Где в плане должно быть.** §7.1 (образец кейса), §7.2 (`INV-F1`, `INV-F2`), §13.1 `GA-13`, §5.1 ТОП-20.
- **Предлагаемая правка.**
  1. §7.1 заменить абзац-образец: «Порог T-123, `ufhRoomHeatFlux.js:172`:
     `maxAllowableHeatFluxUpWm2 = max(0, (maxSurfaceT − insideC)/rFinish)`, где
     `maxSurfaceT = finish.maxSurfaceTemperatureCelsius` (плитка — **35 °C**), а
     `comfortMaxSurfaceTemperatureCelsius = 29` в ограничении **не участвует**. Знаменателем физически
     обязана быть `R_CONV_UP_M2KW = 0.1` (объявлена в том же файле, `:16`, корректно используется в
     `rUp` на `:158`). Численно для плитки (`rFinish = 0.012/1.05 = 0.0114`, `insideC = 20`):
     как в коде — лимит ≈ **1316 Вт/м²**, `surfaceTempC` при `q = 90` → **21.0 °C**; физически верно
     (комфортный предел 29 °C через `R_CONV_UP`) — лимит **90 Вт/м²**, `surfaceTempC` → **29.0 °C**».
  2. Добавить кейсы: «**`A6-14…A6-17` (P0, `RISK-SEC-02`).** Для каждого из четырёх финишей
     (`ceramic_tile` 35/29, `pvc_glue` 27, `pvc_click` 27, `laminate_click` 27) ассертить, что
     `heatFluxUpLimitedBySurface` вычисляется по `appliedMaxSurfaceT`, а не по
     `appliedComfortMaxSurfaceT`: при `circuitMeanC`, дающем `q↑` между комфортным и техническим
     пределом, `heatFluxUpLimitedBySurface === false` и `surfaceTempC > comfortMaxSurfaceTemperatureCelsius`.
     Режим — характеризация (`it.fails` + ЗАМОК), тикет `RISK-SEC-02`. Дополнительно `A6-18`:
     при заданном `presetMaxSurfaceTemperatureC` применяется `min(preset, finishMax)` — граница
     `preset = 28.9 / 29.0 / 29.1`».
  3. §13.1 `GA-13` переписать: «Лимит для плитки ≈ **90 Вт/м²** (сегодня ≈ 1316); `surfaceTempC`
     при `q = 90` → ≈ **29.0 °C** (сегодня 21.0). Дополнительно: ни в одной комнате отчёта
     `surfaceTempC` не превышает `comfortMaxSurfaceTemperatureCelsius` финиша — либо превышение
     сопровождается `WARN_*` в пользовательских предупреждениях».
  4. §7.2 `INV-F1` переформулировать как «`surfaceTempC ≤ comfortMaxSurfaceTemperatureCelsius`
     финиша, а при его отсутствии — `≤ maxSurfaceTemperatureCelsius`», режим **X**.
- **Оценка правки:** 3–5 ч (правка плана) + 4–6 ч (написание `A6-14…A6-18`).

### C1-02 — Содержимое PDF и публичной share-страницы не проверяется ни на одном слое

- **Серьёзность:** блокер
- **Что не покрыто.** `E2E-PDF-001` явно запрещает: «**Содержимое PDF в E2E не ассертить**».
  `E2E-PDF-002` проверяет только «размер больше финансового», `E2E-PDF-003` — `Content-Type`,
  `E2E-NEG-007` — коды ошибок, `SEC-PDF-01…05` — DoS и `%PDF-`. В §7 (831 проверка ядра) модулей
  `backend/src/projects/*` (сборка HTML под рендер) и `buildPublisherPresentation.js` нет ни в одной
  группе A1…A12 — `grep 'projects/\|renderPdf\|serializeShare' D2-engine-coverage.md` → **0**.
  `E2E-SHARE-001` ассертит наличие заголовков («Клієнт:», «Обладнання», «Кошторис»), но ни одного
  числа. Итог: **ни одна проверка плана не сравнивает ни одну сумму, позицию или имя внутри
  выдаваемого клиенту документа с содержимым отчёта.**
- **Чем это грозит.** Ровно тот класс дефекта, который план сам назвал главным («продукт не
  ломается — он молча выдаёт правдоподобное неверное»), пройдёт в прод в самом дорогом месте: PDF с
  пустой таблицей позиций, с суммой от предыдущего расчёта, с `0 грн` вместо цены трубы
  (`RISK-MONEY-02`), с обрезанной кириллицей или с экранированным `&amp;` в имени клиента — всё это
  даёт валидный `%PDF-`, правильный `Content-Type` и «размер больше финансового». Гейт `GA-02`
  («5 из 5 забрали смету») зелёный, клиент получает мусор. Отдельно: `GB-07` требует «≥ 80 % позиций
  чек-листа §11.4 блок 5 присутствуют» — измерить это без разбора содержимого документа нечем.
- **Где в плане должно быть.** §6.3 (`E2E-PDF-*`), §7 (новая группа), §13.1 `GA-02`, §13.2 `GB-07`, `GB-20`.
- **Предлагаемая правка.** Добавить в §6.3 подраздел «`PDF-CONTENT-01…05` — содержимое выдаваемого
  документа» (слой: интеграционный, `pdf-serial`, извлечение текста через `pdftotext`/`pdf-parse`
  на стороне теста, ассерты по извлечённому тексту):
  - `PDF-CONTENT-01` (P0): для `FIX-01` финансовый PDF содержит `commercial.totals.grandTotalUah`,
    `equipmentTotalUah`, `laborTotalUah`, `consumablesTotalUah` **теми же целыми копейками**, что и
    ответ `POST /api/v1/calc`; число строк таблицы позиций = `commercial.lines.filter(l => l.kind !== 'note').length`.
  - `PDF-CONTENT-02` (P0): «Ім'я клієнта» и «Об'єкт» из проекта присутствуют дословно; проверка
    кириллицы и апострофа (`Ім'я`), а также экранирования — имя `<b>А&Б</b>` печатается как текст,
    а не как разметка и не как `&amp;`.
  - `PDF-CONTENT-03` (P1): «Фінанси + технічний розрахунок» содержит `heatLoss.totalWatts` и
    `matching.boiler.selected.model`; без `includeTechnical` этих строк нет.
  - `PDF-CONTENT-04` (P0): PDF, полученный по share-ссылке без `Authorization`, **побайтно
    эквивалентен по числам** PDF владельца того же проекта (сравнение извлечённого текста после
    нормализации даты генерации).
  - `PDF-CONTENT-05` (P1): при `hydraulics.unavailableReason != null` в PDF присутствует явная
    отметка неполноты (парная к `INV-P8` и `GA-16`) — сегодня смета без труб и насоса печатается
    неотличимо от полной.
  В §13.1 `GA-02` порог переформулировать: «5 из 5 получают файл, **и `PDF-CONTENT-01`, `-02`
  зелёные** — файл содержит те же числа, что экран». `PDF-CONTENT-01`, `-02`, `-04` — в PR-smoke
  (проект `pdf-serial`, +3 кейса к 23).
- **Оценка правки:** 1 ч (план) + 14–22 ч (реализация 5 кейсов, включая извлечение текста и
  нормализатор дат).

### C1-03 — Второй `catch` в `buildReport` (коллекторы) не покрыт ни кейсом, ни инвариантом, ни гейтом

- **Серьёзность:** блокер
- **Что не покрыто.** План закрывает soft-fail гидравлики четырежды (`E2E-REGR-023`, `INV-P8`,
  `A11-13…A11-16`, `GA-16`). Второй, симметричный soft-fail — `pickManifolds` (`buildReport.js:520-563`,
  порог **T-246**: «`pickManifolds` бросил / вернул не тот shape → `ok: false`, `MANIFOLD_INTERNAL`,
  расчёт продолжается») — упомянут в плане **ровно один раз**, в §7.6, как цель покрытия строк
  («важно не общее число, а обе ветки `catch`»), и не имеет ни ID кейса, ни инварианта, ни строки
  в гейте. При этом `RISK-MONEY-03` (P1) прямо говорит: `manifolds.ok === false` **молча удаляет из
  сметы все коллекторы** — ТП, радиаторный и котловой (`buildFinancialBom.js:336-337`).
  `RISK-MONEY-03` в плане не упоминается; `INV-P9` перечисляет «коллектор при наличии зоны», но
  только в паре с `ok: true`, а здесь `ok` равен `false` — инвариант не срабатывает.
- **Чем это грозит.** Тот же дефект, что `RISK-HYDR-01`, но по другой ветке и **дороже**: смета
  уходит клиенту без коллекторов ТП (при 9–19 петлях это десятки тысяч гривен), с посчитанным
  «Загальна вартість об'єкта», с активным экспортом и с `200 OK`. Гейт `GA-16` его пропускает по
  формулировке — он говорит только про гидравлику.
- **Где в плане должно быть.** §7.2 (новый инвариант), §7.1 группа A11, §13.1 `GA-16`, §5.1 (ТОП-20 не
  требуется, но в §4.2 «как слои делят риск» — да).
- **Предлагаемая правка.**
  1. §7.2, в таблицу «Девять новых свойств» добавить десятое: «`INV-P10` (**P0**, `RISK-MONEY-03`,
     T-246): при `manifolds.ok === false` смета либо отсутствует, либо несёт явный флаг неполноты
     и **не содержит** позиций категории «коллектор» без отметки; `unavailableReason` заполнен.
     Симметрично `INV-P8`». Итог раздела изменить на «58 свойств».
  2. §7.1, группа A11: «`A11-21…A11-24` — soft-fail коллекторов (T-246): `pickManifolds` бросает
     исключение / возвращает `null` / возвращает объект без `outlets` → отчёт отдаётся, `manifolds.ok`
     = `false`, код `MANIFOLD_INTERNAL`, и в `commercial.lines` **нет** ни одной строки коллектора,
     а в `commercial` есть флаг неполноты». Объём A11 — 24 → **28** кейсов, итог слоя А — **652**.
  3. §13.1 `GA-16` переименовать в «Падение гидравлики **или подбора коллекторов** не даёт молчаливую
     смету» и добавить в метод `INV-P10`, `A11-21…A11-24`.
- **Оценка правки:** 1 ч (план) + 6–10 ч (4 unit-кейса + инвариант).

### C1-04 — Нет матрицы трассируемости «риск → кейс»: 130 из 210 ID реестра не упомянуты в плане ни разу

- **Серьёзность:** блокер
- **Что не покрыто.** Автоматическая сверка (`grep -o 'RISK-[A-Z]*-[0-9]*'` по обоим файлам):
  в `S1-risk-register.md` — 210 уникальных ID, в `TEST_PLAN.md` — 81. **Не упомянуты 130**, из них
  **8 P0**, **69 P1**, 53 P2. Полный список — в разделе «Систематическая сверка» ниже. Часть из них

  самодостаточность разделов 3–14.
- **Чем это грозит.** Три конкретных последствия, каждое дороже стоимости самой матрицы:
  (а) подрядчик не может при сдаче доказать, что риск закрыт, — приёмка превращается в спор;
  (б) при секвестре бюджета режут вслепую: сегодня по документу нельзя сказать, что именно

- **Где в плане должно быть.** Новое нормативное приложение + ссылка из §5.
- **Предлагаемая правка.** Добавить приложение «**Приложение Б. Трассируемость `RISK-*` → проверка**»
  — таблица на 210 строк, колонки: `ID риска` | `P` | `Закрывающие ID` (кейсы `E2E-*`, `A*-*`,
  `INV-*`, `AC-*`, `SEC-*`, `DATA-*`, `VAL-*`, `GA/GB-*`) | `Статус` из закрытого списка:
  `закрыт` / `частично` (с указанием, что именно не закрыто) / `сознательно не покрыт` (со ссылкой на
  §3.2 или §7.8) / `перенесён` (§12.3, §14) / **`НЕ ЗАКРЫТ`**. В §5 добавить абзац: «Риск без строки
  в Приложении Б считается не покрытым. Сумма строк со статусом `закрыт` + `частично` — метрика
  приёмки Фазы A и Фазы B; её значение публикуется вместе с гейтом (§13.3)». Таблица генерируется
  скриптом из тегов `@risk RISK-XXX-NN` в исходниках тестов (по образцу `@threshold` из §7.6),
  а не поддерживается руками.
- **Оценка правки:** 10–16 ч (заполнение 210 строк по существу; ~2 ч из них — генератор из тегов).

### C1-05 — Телеметрия проходимости вводится как прод-код без единой проверки, при том что на её числах стоят все цели §8.5

- **Серьёзность:** блокер
- **Что не покрыто.** §8.2 и блок `A-10` (§12.1) вводят 12 типов событий, батчер на `sendBeacon`,
  новый публичный эндпоинт `POST /api/v1/telemetry/funnel`, TTL-индекс 90 дней, whitelist имён и
  агрегатор `report:funnel` — **24–40 ч нового прод-кода на двух сторонах**. `grep` по плану:
  ни одного ID проверки на телеметрию (`TEL-*` не существует), эндпоинта нет ни в §6 (E2E), ни в
  §9 (контрактные), ни в §10.2 (`SEC-*`: он публичный и принимает запись в БД — это новый
  DoS/спам-вектор рядом с `SEC-PDF-*`), ни в §10.4 (`DATA-*`: TTL-индекс и ретеншн).
  При этом §8.5 требует по нему **семь** целевых значений, а §1 — три числа для владельца.
- **Чем это грозит.** Самый вероятный исход — «зелёная воронка»: `calc_blocked` не отправляется
  (батч теряется на `pagehide`, `sendBeacon` не сработал, whitelist отбросил имя), и Rate ОТКАЗА B
  показывает **0 %** ровно потому, что событие не доехало, а не потому, что дефект исправлен. Это
  прямо и полностью подделывает главный гейт Фазы A. Второй исход — утечка PII: схема запрещает
  значения полей, но запрет ничем не проверяется, а рядом стоит образец (`feedback`), который
  `clientIp` как раз сохраняет.

## Что проверил и признал полным

Перечисляю явно, чтобы не создавать впечатление, что не проверенное = отсутствующее.

1. **Пороги R1 по группам.** Диапазоны групп A1…A11 в сумме дают ровно 193 порога, без дыр и
   пересечений (`T-01…T-25` 25, `T-30…T-48` 19, `T-50…T-77` 28, `T-78…T-84` 7, `T-90…T-109` 20,
   `T-120…T-148` 29, `T-160…T-170` 11, `T-180…T-218` 39, `T-230…T-236` 7, `T-240…T-243` 4,
   `T-244…T-247` 4). Ни один порог реестра не остался вне групп. Претензия C1-07 — не о дырах в
   диапазонах, а о том, что для 38 из них не сказано, **что** проверять.
2. **Инварианты R5.** Все 48 (`INV-A1…G8`) присутствуют в §7.2 и в D2 поимённо; ни один не потерян.
   Претензия C1-06 — только об арифметике G/X.
3. **Перенос из проектных документов.** Сверка ID: все 94 идентификатора `E2E-*` из `D1` есть в
   плане; все `AC-*`, `GA-*`, `GB-*`, `PERF-RL-*`, `SEC-*`, `A11Y-*`, `MOB-*`, `COMPAT-*`, `DATA-*`
   из `D4` есть в плане. **При сборке не потеряно ни одного ID из D1 и D4** — это сильная сторона
   документа.
4. **Восемь поправок П1–П8** (§2.4) перенесены корректно и последовательно проведены по тексту:
   П1 снимает блокер B6 и меняет `E2E-NEG-001`, `PERF-RL-05`, `GB-12`, C-4; П2 понижает
   `RISK-PERF-05` и меняет ТОП-20, `GA-22`; П5 меняет приоритет `RISK-HYDR-02` и §5.3; П8 меняет
   объёмы §7. Противоречий между поправками и разделами не найдено.
5. **Четыре разрешённых противоречия E2E** (§6.5) и разрешение конфликтов U3 ↔ U4 по
   `E2E-REGR-012`, U1 ↔ R2 по `E2E-CALC-003` — сделаны корректно, с указанием, какой источник прав
   и почему.
6. **Интеграции, о которых спрашивалось отдельно:** SSE — `E2E-FEEDBACK-002/003`, `E2E-ADMIN-003`
   (отказ до `flushHeaders`), отдельный непараллельный проект `sse-serial`; Clerk —
   `SEC-CLERK-01…03`, `GB-22`, JWKS-стаб; Mongo — `E2E-NEG-010`, `DATA-*`, teardown `dropDatabase()`,
   пилот `mongodb-memory-server`, ночной кейс «file vs mongo»; климат (Nominatim/Meteostat) —
   §3.2 (недостижим из UI), группа A10, `E2E-NEG-003`, `climate-contract-probe`; Puppeteer/PDF —
   отдельный job, `PDF_REQUIRE_BROWSER=1`, `SEC-PDF-01…05`, замер RSS. **Дыра здесь ровно одна —
   содержимое PDF и share (C1-02).**
7. **Гонки и состояния:** дедупликация (`E2E-CALC-002`), out-of-order (`E2E-REGR-014`, `PERF-RL-06`),
   гонка пресетов (`E2E-REGR-006` + §6.5), две вкладки (`E2E-REGR-010`), мутация входа
   (`INV-P2`), детерминизм между процессами (`INV-P1`), пять источников недетерминизма (§7.7) —
   покрыты полно и точно. Не покрыты серверная конкуренция (C1-09) и частичные отказы цепочки
   экспорта (C1-14).
8. **Честность документа.** §5.2 («риски ТОП-20 без полноценного покрытия»), §7.8, §3.2, приложение
   «НЕ ПРОВЕРЕНО» (29 пунктов с ценой закрытия) — сделаны на редкость добросовестно: план нигде не
   выдаёт непроверенное за факт. Все претензии выше — о том, чего в этих списках **не оказалось**,
   а не о том, что там неверно.
