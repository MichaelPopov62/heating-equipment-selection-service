# Z5 · HTTP-слой: весь публичный API

Зона: `backend/src/api/` (2 739 строк) + смежные, через которые проходит каждый запрос:
`backend/src/index.js` (обработчик ошибок, CORS, лимит тела), `auth/authErrors.js`,
`projects/requireMongo.js`, `projects/serialize*.js`, `projects/projectAccess.js`.

Метод: чтение всех 9 маршрутных модулей целиком + поднятый локально бэкенд (см. «Как
проверялось»). Всё, что можно было подтвердить запросом, подтверждено запросом.

Уже зафиксировано в `TECH_AUDIT.md` и здесь **не переоткрывается**: отсутствие `maxItems`
у комнат (P1-1), публичный расчёт без авторизации (P2-3), корректная изоляция данных между
пользователями на всех 12 маршрутах, полные документы в списке админа, точный подсчёт при
пустом фильтре, необъявленный `429` в контракте, 12 расхождений схемы ответа расчёта (P2-17),
непокрытость слоя автопроверками (P2-18).

## Находки

### Z5-01 · Имя хоста базы данных уезжает анонимному клиенту — **БЛОКЕР-B**

`backend/src/projects/requireMongo.js:36-42` · `backend/src/index.js:238-241`

**Проблема.** `requireMongoForProjects()` перехватывает ошибку драйвера и кладёт
`connectErr.message` **дословно** в клиентское сообщение с кодом 503. Обработчик ошибок
маскирует текст только при `statusCode === 500` (`index.js:230-237`); ветка `> 500`
явно сохраняет `message` для клиента.

**Проверено запросом.** Бэкенд поднят с недостижимой строкой подключения:

```
$ curl -s -X POST -H 'Content-Type: application/json' \
    -d '{"type":"bug","message":"test"}' http://127.0.0.1:3998/api/v1/feedback
{"ok":false,"error":{"message":"getaddrinfo ENOTFOUND heatcalc-prod-secret.internal.example",
 "code":"MONGODB_UNAVAILABLE","statusCode":503}}
```

**Последствие.** Маршрут `POST /api/v1/feedback` (#29) авторизации не требует. В момент
любой аварии базы **любой посетитель** получает внутреннее имя хоста кластера Atlas —
вместе с сообщением драйвера («Authentication failed», «bad auth», имя реплика-сета).
Это готовая цель для атаки и одновременно сигнал «сервис сейчас без базы».
Без Mongo в окружении утекает другое: `«…задайте MONGODB_URI або MONGODB_USER/PASSWORD/
URL/DB у backend/.env»` — путь к файлу конфигурации и имена переменных (`requireMongo.js:25`,
проверено тем же curl).

**Решение.** Клиенту — фиксированная строка («Сховище тимчасово недоступне»), исходное
сообщение — только в лог, как уже сделано для 500. Правка в одном месте:
`requireMongo.js:36-42` перестаёт передавать `connectErr.message` наружу.

**Цена: 30 мин. Риск правки: нет.**

### Z5-02 · История расчётов читает полные отчёты, чтобы вернуть сводку — **БЛОКЕР-B**

`backend/src/api/projectsRoutes.js:586-593` · `backend/src/models/Calculation.js:37-39`

**Проблема.** `Calculation.find({projectId}).lean()` идёт без проекции. В документе лежат
три тяжёлых поля `Mixed`: `calcInput`, `report`, `summary`. В ответ (`serializeCalculationListItem`,
`serializeProject.js:114-122`) попадают только `id`, `projectId`, `summary`, `createdAt`.
Всё остальное читается из базы, разбирается в BSON и выбрасывается.

**Последствие.** Верхняя граница документа расчёта — 14 МБ (`documentSizeLimits.js:15`),
квота — 50 расчётов на проект. Один авторизованный запрос `GET /projects/:id/calculations`
при дефолтном `limit=20` тянет в память до 280 МБ на инстансе с 512 МБ, где два PDF уже
занимают всё (P2-9). Это не рост базы «когда-нибудь» — это один пользователь и один клик
по вкладке истории.

Тот же дефект в двух местах поменьше: `projectsRoutes.js:296-298` (последний расчёт для
карточки проекта — читается целиком ради `summary`) и `projectsRoutes.js:672` (для PDF
`report` действительно нужен — здесь корректно).

**Решение.** `.select({ projectId: 1, summary: 1, createdAt: 1 })` в двух местах (:587, :296).
Ответ побайтово не меняется — сериализатор и так эти поля не отдаёт.

**Цена: 20 мин. Риск правки: нет** (контракт ответа не затрагивается).

### Z5-03 · `?limit=0` снимает пагинацию полностью — **БЛОКЕР-B**

`backend/src/api/projectsRoutes.js:116-120`, вызовы `:144`, `:583`

**Проблема.**

```js
function parseLimit(raw, fallback, max) {
  const n = Number(raw);
  if (!Number.isFinite(n) || n < 0) return fallback;
  return Math.min(Math.floor(n), max);
}
```

Ноль проходит все проверки: он конечен и не отрицателен, `Math.min(0, 100) === 0`.
Дальше `Project.find(filter).limit(0)`, а в MongoDB **`limit(0)` означает «без лимита»**.
Верхняя граница в 100 записей защищает от `limit=100000` и не защищает от `limit=0`.

**Проверено.** Опции запроса действительно уходят в драйвер с нулём:

```
$ node -e "…M.find({}).limit(0).getOptions()"   →  {"limit":0,"skip":0}
```

Поведение сервера MongoDB при `limit: 0` — документированная семантика «без ограничения».
Сквозной прогон против живой базы — **НЕ ПРОВЕРЕНО** (Mongo в окружении аудита нет).

**Последствие.** `GET /api/v1/projects?limit=0` от админа возвращает **всю коллекцию
проектов** целиком, полными документами (`survey` + `lastCalcInput` + `shareSnapshot`) —
это ровно тот сценарий на 520 МБ, который в TECH_AUDIT отнесён к «когда вырастет до 10 000»,
но достижимый одним параметром уже сегодня. `GET /projects/:id/calculations?limit=0`
в связке с Z5-02 читает все 50 отчётов проекта.

**Решение.** Одна строка: `if (!Number.isFinite(n) || n < 1) return fallback;`.
Заодно закрывает `limit=0.4` (сейчас `Math.floor` даёт тот же ноль).

**Цена: 15 мин. Риск правки: нет.**

### Z5-04 · Публичная ссылка даёт анонимный доступ к самой тяжёлой операции — **БЛОКЕР-B**

`backend/src/api/publicSharesRoutes.js:112-166` · `backend/src/projects/pdfRenderSemaphore.js:14-17`
· `backend/src/api/middleware/rateLimiters.js:99-103`

**Проблема.** `GET /api/v1/public/shares/:token/pdf` не требует авторизации и запускает
рендер Chromium. Ограничение — общий лимит публичных чтений, 120 запросов за 15 минут
**на IP**, тот же самый, что и для лёгкого JSON-ответа `#24`. Семафор пропускает
2 рендера одновременно (дефолт `PDF_MAX_CONCURRENT`).

**Последствие.** По замеру из P2-9 два браузерных процесса вместе с сервером — 512 МБ
из 512. Разница с P2-9 в том, **кто может это вызвать**: не владелец проекта, а любой,
кому попала ссылка `/s/{token}` — она по определению рассылается клиентам монтажника
и не отзывается автоматически. Стоимость атаки — два параллельных `curl`.

**Решение.** Отдельный лимитер на PDF-маршруты (владельческий и публичный), порядка
5–10 запросов за 15 минут; `PDF_MAX_CONCURRENT=1` уже рекомендован в P2-9 и делает
отказ честным 503 вместо падения. Лимитер добавляется одной константой в
`rateLimiters.js` и одной ссылкой в каждом из двух маршрутов.

**Цена: 30 мин. Риск правки: низкий** (легальный сценарий — 1–2 выгрузки на просмотр).

### Z5-05 · Нормализация входа затирает собственные предупреждения — **ДОЛГ**

`backend/src/api/validate.js:768`, `:776` (против `:158`, `:601`,
`logic/normalizeHeatingUfhPreset.js:76,101`)

**Проблема.** Механизм уведомления пользователя о подменённых значениях —
`heatingSystem._normalizationWarnings`. Пять из семи мест записи корректно **дописывают**
в массив. Два места — `assertBoilerDhwSchemeCompatibility` — **присваивают заново**:

```js
hs._normalizationWarnings = [ 'Зв'язка «Одноконтурний котел + БКН» змінено на двоконтурну…' ];
```

Вызывается это на строке `:361`, то есть **после** записи предупреждений о типах комнат
(`:288`), о режиме ТП (`:308`) и о температурном графике (`:309`).

**Проверено прогоном `validateAndNormalizeInput` на файловом справочнике.** Один и тот же
вход, отличается только схема ГВС:

```
B (схема не переписывается):
  _normalizationWarnings: ["Тип приміщення «r1»: «гостинная» нормалізовано до «гостиная»."]

A (квартира + «1К + БКН» → переписано на двухконтурную):
  _normalizationWarnings: ["Зв'язка «Одноконтурний котел + БКН» змінено…"]     ← предупреждение
                                                                                 о типе исчезло
```

**Последствие.** Продукт молча меняет две вещи во входе и сообщает об одной. Пользователь
видит замену схемы ГВС и не видит, что его тип помещения был исправлен, — при том что
именно этот механизм должен закрывать вопрос «уведомляется ли пользователь о подмене
его значений». Теряются также предупреждения о несовпадении пресета потолка и о режиме ТП.

**Решение.** Заменить два присваивания на дописывание — ровно тем кодом, что уже есть
в `pushNormalizationWarning` (`validate.js:149-159`).

**Цена: 15 мин. Риск правки: нет.** Побочный эффект: в ответе станет больше предупреждений,
чем сегодня, — это и есть цель.

### Z5-06 · Неизвестные поля запроса удаляются молча — **ДОЛГ**

`backend/src/api/validate.js:77-81`

**Проблема.** AJV сконфигурирован с `removeAdditional: true`. Схема `CalcInput`
на каждом уровне объявляет `additionalProperties: false`, поэтому любое поле, которого
нет в схеме, **вырезается из тела до расчёта, без ошибки и без предупреждения**.

**Проверено прогоном.**

```
вход:  heatingSystem: { supplyC: 75, returnC: 65, unknownKnob: 'ignore-me' },
       totallyUnknownTopLevel: { a: 1 }
после: has unknownKnob: false | has totallyUnknownTopLevel: false
       warnings about drop: (ни одного)
```

**Последствие.** Опечатка в имени поля на клиенте (`waterUnderfloorHeating` →
`waterUnderFloorHeating`) даёт **HTTP 200 и расчёт по умолчаниям**, а не 400. Здесь же
проходит граница «где кончается проверка схемы и начинается бизнес-нормализация»:
до AJV работают три функции нормализации (`validate.js:265-268`), после AJV — ещё
двенадцать (`:288-376`). Ошибиться именем поля — самый вероятный класс ошибки интеграции,
и он единственный не даёт никакого сигнала.

**Решение.** Не переключать на `removeAdditional: false` махом — это сломает совместимость
со старыми черновиками, которые сегодня проходят. Дешевле: собрать список удалённых путей
(AJV отдаёт их при `removeAdditional: 'failing'` либо сравнением до/после `structuredClone`,
который уже делается на `:262`) и класть в те же `_normalizationWarnings`. Тогда клиент
увидит «поле X проигнорировано», а поведение не изменится.

**Цена: 2–4 ч. Риск правки: низкий.**

### Z5-07 · Ошибка библиотеки JWT отдаётся клиенту дословно — **ДОЛГ**

`backend/src/auth/authErrors.js:33-35`

**Проблема.** `mapAuthErrorToResponse` знает два кода (`PROJECTS_AUTH_NOT_CONFIGURED`,
`MONGODB_UNAVAILABLE`) и подставляет им безопасный текст. Для всего остального —
`message = err.message`, то есть текст исключения `jose`/JWKS, с кодом 401/403.

**Последствие.** Тот же класс, что Z5-01, но на маршрутах проектов: клиент, приславший
любой невалидный токен, получает внутреннюю формулировку (адрес JWKS провайдера,
`JWKSNoMatchingKey`, `unable to fetch`). Сеть ответов подсказывает атакующему, чем
именно отличается его попытка от валидной. Полный текст **НЕ ПРОВЕРЕНО** — требует
поднятой конфигурации Clerk; код-путь однозначен.

**Решение.** Инвертировать умолчание: клиенту всегда «Недійсний або прострочений токен»,
исходное сообщение — только в `logger.warn` (уже пишется, `authErrors.js:87-91`).
Явные исключения перечислить списком, как сейчас перечислены два кода.

**Цена: 20 мин. Риск правки: нет.**

### Z5-08 · Ограничитель частоты стоит после авторизации — **ДОЛГ**

`backend/src/api/projectsRoutes.js:128` против `:135`, `:210`, `:276`…

**Проблема.** Порядок монтирования:

```js
router.use('/api/v1/projects', mongoMiddleware, requireAuth);   // :128 — на префикс
router.get('/api/v1/projects', projectsReadRateLimiter, …);      // :135 — на маршрут
```

Express выполняет middleware префикса раньше обработчиков маршрута. Значит для запроса
без валидного токена цепочка обрывается на `requireAuth` (401) и **до лимитера не доходит
никогда**. Каждый такой запрос при этом успевает выполнить `requireMongoForProjects()`
и полный разбор токена.

**Последствие.** Неограниченный поток 401 на 12 маршрутах проектов: перебор токенов
не тормозится, нагрузка на проверку JWKS не ограничена, в логах — неограниченный шум.
Ключ лимитера (`rateLimiters.js:14-20`) для этих маршрутов всегда `user:*`, потому что
он вычисляется уже после `requireAuth`, — то есть анонимный трафик в принципе не имеет
своей корзины.

**Решение.** Перенести лимитер в ту же строку `:128`, до `requireAuth`. Ключ по-прежнему
даст `user:*` для авторизованных (req.user ещё не установлен → ключом станет IP; это
корректнее текущего для анонимных). Одна строка + перепроверка, что порог 120/15 мин
не режет живую сессию.

**Цена: 30 мин. Риск правки: низкий.**

### Z5-09 · Приватные ответы и публичный снимок без заголовков кэширования — **ДОЛГ**

`backend/src/api/routes.js:102-105` (единственное место, где `no-store` ставится)
· `backend/src/utils/setNoStoreCacheHeaders.js`

**Проблема.** `Cache-Control` выставляется только для `GET /api/v1/presets/*`. Остальные
25 маршрутов отдают ответы без него.

**Проверено запросом.**

```
$ curl -i http://127.0.0.1:3999/api/v1/me
HTTP/1.1 200 OK
ETag: W/"9b-uZeq0zvt1vKIL5irZr2Kej18n7c"          ← Cache-Control отсутствует
{"ok":true,"user":{"id":"…","email":"dev-local@localhost",…}}
```

**Последствие, два разных.** (а) Приватные ответы — `/me`, список проектов, PDF сметы —
не помечены `no-store`. Заголовок `Authorization` защищает от разделяемых кэшей, но
не от кэша браузера, дискового кэша PDF и истории навигации на общем компьютере;
для монтажника с одним ноутбуком на бригаду это реально. (б) Публичный снимок
`GET /api/v1/public/shares/:token` — наоборот, кэшируется чем угодно по эвристике,
и **отзыв ссылки (`DELETE …/share`) не инвалидирует ничего**: у клиента и на промежуточном
прокси остаётся рабочая копия сметы.

**Решение.** `setNoStoreCacheHeaders` — на роутер проектов, `/me` и оба PDF-маршрута
(функция написана, применяется одной строкой на префикс, как на `:102`).
Для публичного снимка — `Cache-Control: no-cache, must-revalidate` (перепроверка на каждый
показ, отзыв срабатывает мгновенно), не `no-store`: снимок неизменяем и `ETag` уже работает.

**Цена: 30 мин. Риск правки: нет.**

### Z5-10 · Идемпотентности нет ни на одном пишущем маршруте — **ДОЛГ**

`projectsRoutes.js:210-237` (создание) · `projectAccess.js:193-204`, `:210-221` (квоты)
· `projectsRoutes.js:770-794` (публикация)

Три разных сценария, один корень — «прочитать, решить, записать» без атомарности.
Сквозные прогоны против живой базы — **НЕ ПРОВЕРЕНО** (Mongo нет); ниже разбор по коду.

**(а) Повторный `POST /api/v1/projects`.** Ключа идемпотентности нет, уникального индекса
по `(ownerId, clientName)` в модели нет (`models/Project.js:47-49` — три индекса, ни одного
уникального). Двойное нажатие «Створити» = два проекта с одинаковым именем. Пользователь
удалит лишний руками; неприятно, но не опасно.

**(б) Квоты.** `assertCanCreateProject` считает `countDocuments`, потом обработчик пишет
(`:213` → `:224`). Между ними нет ничего атомарного: параллельные запросы на границе
квоты пройдут все. Тот же рисунок у `assertCanCreateCalculation` (`:471` → `:519`).
Превышение — на единицы документов, не на порядок. **Чинить не надо**: цена атомарного
счётчика выше ущерба.

**(в) Параллельная публикация ссылки — единственное, что стоит починки.** Обработчик
читает проект (`:726`), берёт существующий токен или **генерирует новый** (`:774`),
затем пишет через `findOneAndUpdate` (`:779`). Два одновременных «Опублікувати» на
неопубликованном проекте дадут два разных токена; победит записанный вторым. Первый
клиент получит в ответе `publicPath` того токена, который в его же транзакции уже
перезаписан, — **ссылка, которую он скопировал и отправил клиенту, отдаст 404**.
Поле `shareToken` объявлено `unique: true, sparse: true` (`models/Project.js:31`), но
уникальность здесь не помогает: токены разные, конфликта индекса нет.

**Решение (в).** Генерировать токен внутри одной атомарной операции:
`findOneAndUpdate({_id, shareToken: {$exists: false}}, {$set: {shareToken: new}})`,
при отсутствии результата — перечитать и использовать уже существующий токен.
Снимок при этом всё равно перезаписывается — это ожидаемое поведение.

**Цена: 2–3 ч на (в) с перепроверкой сценария отзыв→повторная публикация. Риск: средний** —
трогает единственный механизм, ссылки от которого уже разошлись по людям.

### Z5-11 · Расчёт сохраняется до проекта: при отказе остаётся половина — **ДОЛГ**

`backend/src/api/projectsRoutes.js:519` (`Calculation.create`) → `:526` (`project.save()`)

**Проблема.** Порядок записи: сначала документ расчёта, потом проект. Транзакции нет.
Если `project.save()` откажет (обрыв соединения, отказ валидации `survey`, таймаут),
`catch` на `:551` залогирует и отдаст 500 — **при уже созданном расчёте**.

**Последствие.** Пользователь видит ошибку и жмёт «Розрахувати» ещё раз. Каждая попытка
съедает единицу квоты в 50 расчётов на проект и оставляет расчёт, у которого
`project.lastCalcInput` не соответствует сохранённому входу. Молчаливого искажения сметы
нет — расчёт целиком лежит в своём документе; портится история и квота.

**Решение.** Поменять порядок местами: сначала `project.save()` (дешёвая запись),
затем `Calculation.create` (тяжёлая). При отказе тяжёлой операции состояние остаётся
консистентным, а пользователь просто повторяет.

**Цена: 1 ч с перепроверкой. Риск: низкий.**

### Z5-12 · Удаление проекта нетранзакционно — **ДОЛГ**

`backend/src/api/projectsRoutes.js:402-413`

**Проблема.** Сначала `Project.findOneAndDelete` (`:402`), затем
`Calculation.deleteMany({projectId})` (`:413`). Между ними — сетевой вызов.

**Последствие.** Падение процесса между операциями оставляет расчёты без проекта. Прочитать
их через API невозможно (все чтения расчётов начинаются с проверки доступа к проекту,
`:577`, `:625`), то есть утечки данных нет — есть невидимый рост базы, который ничем
не убирается и никак не виден. На 512 МБ и бесплатном кластере это медленно съедает место.

**Решение.** Поменять порядок (сначала расчёты, потом проект) — тогда худший исход
«проект остался без истории», что видно пользователю и исправимо повторным удалением.
Плюс одноразовый скрипт-уборщик сирот, если удаления уже происходили.

**Цена: 30 мин + 1 ч на скрипт. Риск: нет.**

### Z5-13 · Имя клиента приводится к строке вместо отказа — **КОСМЕТИКА**

`backend/src/projects/validateProjectBody.js:19-32` · `backend/src/utils/sanitizeString.js:11`

**Проверено прогоном чистой функции.**

```
{"clientName":{"$ne":1}}   =>  {"clientName":"[object Object]"}
{"clientName":12345}       =>  {"clientName":"12345"}
{"clientName":["a","b"]}   =>  {"clientName":"a,b"}
```

**Проблема.** `sanitizeTrimAngleBrackets` делает `String(v ?? '')` — что угодно становится
строкой, поэтому проверки типа фактически нет ни у `clientName`, ни у `label`.

**Последствие.** Внедрения нет: объект схлопывается в `"[object Object]"` и до фильтра
Mongo как оператор не доходит (это к тому же — часть того, почему инъекция здесь закрыта,
см. «Проверено и чисто»). Ущерб репутационный: вместо 400 пользователь получает 201
и проект с именем `[object Object]`, который потом надо чинить руками.

**Решение.** `if (typeof raw !== 'string') → 400` перед санитизацией, в одной функции.

**Цена: 30 мин. Риск: низкий** — отклонит запросы, которые сегодня проходят; клиент
шлёт строку, но стоит прогнать анкету перед выкладкой.

### Z5-14 · Админские и системный маршруты без ограничителя частоты — **КОСМЕТИКА**

`adminRoutes.js:65` · `adminFeedbackRoutes.js:65,133,175` · `systemRoutes.js:28`

**Проблема.** Пять маршрутов не подключены ни к одному лимитеру. Для системного это
означает неограниченный перебор `X-System-Token` (`systemRoutes.js:39`, сравнение
обычным `!==`, не постоянного времени) и неограниченный запуск полной перезагрузки
справочников при верном токене. Для SSE (`:133`) — неограниченное число одновременных
соединений на одного админа; каждое держит таймер и подписку.

**Последствие.** Всё за админской ролью, то есть за уже пройденной авторизацией — отсюда
низкая категория. Токен системного маршрута — единственная точка, доступная снаружи
без JWT; перебор непрактичен при достаточной энтропии токена (**НЕ ПРОВЕРЕНО** — значение
задаётся в окружении хостинга).

**Решение.** Существующий `createLimiter` с порогом 10/15 мин на системный маршрут
и 300/15 мин на админские; для SSE — счётчик открытых подписок на пользователя.

**Цена: 20 мин на лимитеры. Риск: нет.**

### Z5-15 · Мелочи семантики и лишние поля в ответах — **КОСМЕТИКА**

Сгруппировано: каждое по отдельности не окупает отдельной задачи, вместе — полчаса.

1. **405 не отдаётся никогда.** Неподдерживаемый метод на существующем пути падает
   в общий catch-all (`routes.js:213-219`). Проверено: `DELETE /api/v1/calc` → `404`.
   Клиент не отличит «нет такого ресурса» от «не тот метод».
2. **`OPTIONS` отвечает 204 на любой путь, включая несуществующий** (проверено:
   `OPTIONS /api/v1/whatever` → 204). Поведение библиотеки `cors`, безопасное:
   заголовок `Access-Control-Allow-Origin` для чужого источника не выставляется
   (проверено с `Origin: https://evil.example`), браузер запрос заблокирует.
   Оставить как есть.
3. **`ownerId` в каждом элементе списка проектов** (`serializeProject.js:59-61`) —
   отдаётся всем, не только админу. Это собственный идентификатор пользователя,
   утечки чужих данных нет; но внутренний ключ в публичном контракте без нужды.
4. **`_normalizationWarnings` уезжает в ответ.** Служебное поле пишется в `calcInput`
   (`validate.js:158`), сохраняется в `project.lastCalcInput` (`projectsRoutes.js:525`)
   и возвращается в `ProjectDetail.lastCalcInput` (`serializeProject.js:91-95`).
   В отчёте оно вычищается (`report/buildReport.js:718`), в проекте — нет.
5. **Тело не того типа принимается как пустое.** `POST /api/v1/calc` с
   `Content-Type: text/plain` не парсится и доходит до AJV как `{}` → 400
   `VALIDATION_ERROR` «отсутствует building» вместо честного 415. Проверено curl.

**Цена: 30 мин на всё. Риск: нет.**

## Проверено и чисто

**Единообразие конверта ошибок — полное.** Прямой поиск по `backend/src/api/` не нашёл
ни одного ответа мимо `sendErrorEnvelope` / `next(err)`: единственные `res.send` —
это два тела PDF (`projectsRoutes.js:700`, `publicSharesRoutes.js:161`). Middleware
авторизации отвечают через тот же конверт (`auth/authErrors.js:72,93`), ограничитель
частоты — тоже (`rateLimiters.js:44-50`). 404 (`routes.js:213`) и разбор JSON
(`index.js:193-210`) дают тот же формат. Проверено запросами: 404, битый JSON, 400 AJV,
503 — четыре разных источника, один формат ответа.

**Проглоченных исключений нет.** Все 24 асинхронных обработчика обёрнуты в `try/catch`
с `next(err)`; `mongoMiddleware` в трёх модулях (`projectsRoutes.js:66-73`,
`adminRoutes.js:42-49`, `publicSharesRoutes.js:23-30`) корректно пробрасывает отказ.
`catch` с подстановкой умолчания в зоне **не найдено ни одного**. Отдельно проверен
единственный обработчик без `next` — SSE (`adminFeedbackRoutes.js:133-168`): ошибка
записи в закрытый сокет ловится в шине событий (`feedback/feedbackEventHub.js:44-57`),
поэтому отвалившийся админский поток не роняет `POST /api/v1/feedback` и не мешает
остальным подписчикам. Есть страховочная сетка на фоновые отказы (`index.js:33-38`).

**Ответ на «что при недоступности базы».** Проверено запросами: все маршруты проектов,
админские и `POST /api/v1/feedback` отдают 503 `MONGODB_UNAVAILABLE`, ни один не зависает
и не отдаёт 200 с пустыми данными. Претензия только к тексту сообщения — Z5-01.
`GET /health`, `/api/v1/calc`, `/api/v1/catalog`, `/api/v1/presets/*` работают без базы
(следствие изоляции расчётного ядра).

**Инъекция через query закрыта на каждом параметре.** Express разбирает `?p[$ne]=x`
в объект; проверено по коду, что все чтения query это переживают: `search` и `ownerId`/
`ownerEmail` требуют `typeof === 'string'` (`projectsRoutes.js:146-149`,
`projectAccess.js:57-64`), `limit`/`skip` идут через `Number()` → `NaN` → умолчание
(`:116-120`), `includeLastCalculation` сравнивается строго (`:295`),
`includeTechnical` — по белому списку (`parseIncludeTechnicalQuery.js:9-17`),
курсор админского фида декодируется в `try/catch` с проверкой ObjectId
(`adminFeedback.js:83-103`), все `:id` проходят `parseObjectIdParam` с обратной сверкой
строки (`parseObjectId.js:12-17`). Оператор в фильтр Mongo не попадает ни по одному пути.

**Загрязнение прототипа закрыто.** Тело клонируется через `structuredClone`
(`validate.js:262`), затем AJV с `additionalProperties: false` вырезает всё, чего нет
в схеме, — включая `__proto__` как обычный ключ.

**Экранирование регулярного выражения поиска.** `projectsRoutes.js:155` экранирует
все метасимволы перед `$regex` — ни отказа по catastrophic backtracking, ни подстановки
чужого шаблона.

**Персональные данные обратной связи не утекают.** `clientIp` пишется в базу
(`feedbackRoutes.js:42-43`), но `serializeAdminFeedback` (`feedback/adminFeedback.js:198-221`)
его не отдаёт — проверено пофайлово по списку полей. Публичный снимок сметы отдаётся
белым списком (`serializeShare.js:56-74`): ни `ownerId`, ни `survey`, ни `calcInput`.

**Валидация админского фида — эталон для остальных маршрутов.** `limit` ограничен
диапазоном 1–100 с отказом вне его (`adminFeedback.js:116-120` — тот случай, где `limit=0`
корректно отклоняется), тело `PATCH` принимает ровно одно поле и отвергает любое лишнее
(`:160-162`), повторные query-параметры отклоняются явно (`:110-114`). Это единственный
модуль зоны, покрытый проверочным скриптом, — и это видно по качеству.

## Сильные стороны

1. **Один конверт ошибок на весь API, без исключений.** Редкость для проекта такого
   возраста: обычно к этому моменту в коде уже 3–4 разных формата. Здесь клиенту
   не нужно знать, какой слой ответил.
2. **Маскирование 500 сделано правильно** (`index.js:230-237`): текст и стек уходят
   только в лог, клиент получает нейтральную строку и `INTERNAL_ERROR`. Ошибка ровно
   одна — эта дисциплина не распространена на 503 и 401 (Z5-01, Z5-07).
3. **`requestId` сквозной**: генерируется на входе (`index.js:98-100`), попадает
   в `api.request` / `api.response` / `api.error` и в бизнес-события маршрутов
   (`project.calc.start` / `.done` / `.fail`). Разбор инцидента по расчёту проекта
   возможен уже сегодня — в отличие от анонимного расчёта (P2-8).
4. **Проверка доступа продублирована внутри операции изменения.** `findAccessibleProjectLean`
   для ответа и `buildAccessibleProjectByIdFilter` внутри `findOneAndUpdate` /
   `findOneAndDelete` — гонка «проверил, потом чужой стал владельцем» закрыта
   на всех пишущих маршрутах.
5. **Кросс-владельческий доступ админа пишется в аудит** (`projectAccess.js:137-154`) —
   отдельным событием, с обоими идентификаторами. Для будущего платного продукта это
   уже готовая половина требования по журналированию.
6. **`coerceTypes: false` у AJV.** Осознанный выбор против удобства: `"12"` не станет
   числом. Для расчёта, где число уходит в диаметры и мощности, это правильно.
7. **Лимиты вычислены по назначению, а не одним числом.** Пять раздельных корзин
   (`rateLimiters.js:70-110`) с порогами под стоимость операции: расчёт проекта 15,
   запись 60, чтение 120. Каждый порог переопределяется переменной окружения без релиза.
8. **Ограничения размера документа проверяются до записи** (`documentSizeLimits.js:64-73`) —
   отказ 413 приходит раньше, чем драйвер упрётся в лимит BSON.
