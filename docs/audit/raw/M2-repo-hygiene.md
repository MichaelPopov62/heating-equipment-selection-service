### [M2-01] В публичном репозитории лежит точный список admin-email, а повышение до admin не требует подтверждённой почты

- **Ось:** A5 | **Категория:** БЛОКЕР-A
- **Якорь:** `docs/deploy/render.md:43`, `docs/deploy/smoke-tests.md:100`,
  `backend/scripts/verifyPlatformAdminAllowlist.js:68`,
  `backend/src/auth/resolveUser.js:54` и `:79`, `backend/src/auth/mapJwtPayload.js:74-75`
- **Что не так:** три файла в `origin/main` публикуют боевое значение
  `PLATFORM_ADMIN_EMAILS=popov1ms@i.ua,romantikzizni@gmail.com`. `docs/deploy/render.md:39`
  и `docs/deploy/environments.md:118` прямо фиксируют: список **один и тот же** на staging
  и production. В коде повышение до `role: 'admin'` делается по одному лишь совпадению
  строки email из JWT:

  ```js
  // backend/src/auth/resolveUser.js:54
  const platformAdmin = isPlatformAdminEmail(identity.email);
  // :79
  if (isPlatformAdminEmail(identity.email) && user.role !== 'admin') { … role: 'admin' … }
  ```

  `identity.emailVerified` вычисляется (`mapJwtPayload.js:74-75`), кладётся в Mongo
  (`User.js:26`) и **нигде не проверяется перед выдачей admin**.
- **Сценарий вреда:** атакующий читает `render.md` (это первая ссылка из README по слову
  «deploy»), узнаёт оба адреса, и дальше ищет один шаг: любой путь получить в Clerk-инстансе
  JWT с claim `email` = один из этих адресов и `email_verified: false` — соцпровайдер без
  верификации почты, включённый в Clerk Dashboard, dev-инстанс staging, ошибка в настройке
  JWT-template. Успех = `role: 'admin'` в production Mongo (список общий!) со всеми
  admin-эндпоинтами. Второй, более простой сценарий: адреса известны → целевой фишинг /
  сброс пароля на конкретный ящик, а не «на кого-нибудь».
- **Стоимость починки:** 2–3 ч. (а) заменить оба адреса в доках на `admin@example.com` и
  перенести реальное значение в Render Dashboard; в `verifyPlatformAdminAllowlist.js:68`
  подставить example.com; (б) в `resolveUser.js` добавить `&& identity.emailVerified` к обеим
  проверкам; (в) развести списки staging и production.
- **Если не чинить никогда:** пока Clerk настроен строго — ничего. Но защита держится
  исключительно на настройке внешнего SaaS, которую владелец не контролирует из кода и не
  проверяет ни одним verify-скриптом. При первом включении соцлогина — тихая эскалация до admin.
- **Риск самой починки:** гейт `emailVerified` может отсечь самого владельца, если Clerk
  не кладёт claim `email_verified` в токен. Проверить на staging до prod.

  Шесть подряд коммитов 2026-08-13 (`c431cf9`…`75ac0e0`) — с одним и тем же текстом про
  один и тот же CSS-файл.
- **Мешает ли это ОДНОМУ автору — проверил, а не предположил.** Взял реальную задачу
  «когда менялась логика финансовой сметы» и прогнал:

  ```
  $ git log --all --oneline -S'buildFinancialBom'
  e788b12  docs(qa): аудит готовности продукта …
  aa05172  add changed dock backenda
  54ba052  add checked the service documentation
  e7d6e19  add translated the site into Ukrainian
  ea81bd8  add architecture change
  ```

  Четыре кандидата, и ни одно сообщение не отвечает на вопрос «зачем поменяли смету».
  «add translated the site into Ukrainian» — это коммит на 190 файлов и 4885 строк, в
  котором заодно поменялась смета. Чтобы понять что именно, надо читать диффы вручную.
  То же с `displayedRadiatorSectionsTotal`: три коммита, один из них — Initial commit,
  второй — `fdab7f7 «Hide Cursor settings»`.

  **Честный вывод:** сообщения дают ноль. Но потери пока небольшие — история короткая
  (2 месяца), автор всё помнит, `git log -S` по идентификатору всё равно находит
  коммит-кандидатов. Это станет дорого в двух точках: (а) через полгода, когда память
  выветрится; (б) в момент, когда придёт второй человек.
- **Отдельная проблема — размер коммита.** 18 коммитов (13%) трогают >50 файлов, топ —
  345, 228, 190, 102, 92, 90. `git bisect` на таких коммитах даёт ответ «сломалось где-то
  в этих 190 файлах», то есть не даёт ничего. Это дороже плохих сообщений.
- **Стоимость починки:** 30 минут суммарно.
- **Что предложить (дёшево и работает для одиночки):**
  1. `git config commit.template .gitmessage` с четырьмя строчками-подсказками
     (`тип(область): что и зачем`) — стоит 10 минут, снимает «add changed».
  2. Правило «один коммит = одна тема» без всякого инструмента — именно оно, а не
     формат сообщения, вернёт работоспособность `git bisect`.
- **Что предлагать НЕ надо (и это часть вывода):** husky + commitlint + lint-staged,
  conventional-changelog, semantic-release, squash-политики, переписывание старых
  сообщений через `git filter-repo`. Для одного автора это чистые накладные расходы:
  pre-commit hook у одиночки заканчивается `--no-verify`, а генератор CHANGELOG'а
  бессмыслен там, где нет ни тегов, ни релизов, ни внешних потребителей.
- **Если не чинить никогда:** археология по истории останется невозможной; при найме
  второго человека он не сможет пользоваться `git log` и `git blame` как источником
  контекста и будет спрашивать владельца по каждому файлу.
- **Риск самой починки:** нулевой (шаблон коммита ничего не блокирует).

### [M2-10] Нет LICENSE, при этом `backend/package.json` объявляет ISC и не помечен `private`
