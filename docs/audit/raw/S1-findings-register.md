### П-1. Архитектурный барьер: почему `no-restricted-imports` не работает

**M1 (§4, §16.1):** «36 кросс-доменных импортов в обход `public.js`; правило в

JSDoc-типы, runtime-обходов 31; текущее правило не ловит ни одного из них; «если конфиг

**Моя проверка — 1: `npx eslint --print-config` по девяти файлам разных каталогов.**

### П-2. Сложность `buildReport`: тревога или защитный шум

**M1 (§7, §16.15, §18):** `buildReport` цикломатика **256** при 506 строках — «главный сигнал
по коду», «самая горячая точка синхронного расчёта».

**A3 (§2.2, п.3 «НЕ ТРОГАТЬ»):** это оркестратор, а не логика; cx набирается защитным
разыменованием; 19 `if`, 0 циклов; следствие находки A3-01 (`any` в денежном коде).

**A4 (§1.5):** те же защитные цепочки бесплатны по времени.

**Моя проверка.** Вырезал тело функции (`backend/src/report/buildReport.js:206-712`) и посчитал:

```
строк:      507
?. :        126
?? :         70
if :         19
for/while:    0
await:        2
```

Числа A3 воспроизведены полностью. Оба `await` — `:231` (сетевой климат) и `:630` (локальный AJV).

Замер A4 независимо закрывает вопрос цены: 50 комнат **без** тёплого пола проходят через те же
защитные цепочки за **1.69 мс**, со сплошным ТП — за 166.92 мс. Если бы `?.`/`??` стоили заметного
времени, нижняя граница не была бы 1.7 мс. Полный отчёт на 1 помещении — **0.25 мс**.

**Якорь:** `backend/src/report/buildReport.js:206` (сигнатура), `:226,:281,:292,:323,:421,:517,
:565,:618` (8 пронумерованных стадий), `docs/audit/artifacts/A4-bench-eventloop-raw.txt`.

> **Итоговая формулировка (одной записью — `S1-33`).** Цикломатика 256 у `buildReport` —
> **не находка, а измеритель другой находки**. Функция линейна: 19 ветвлений и ноль циклов
> на 507 строк, структура — пронумерованный пайплайн из 8 стадий. Сложность создают
> 126 `?.` + 70 `??` + 89 тернарников, то есть защитное разыменование данных, которые
> компилятор не может подтвердить, потому что они `any` (см. узел **К-1**).
> По времени защита бесплатна (замер A4). **Резать `buildReport` сейчас нельзя** — это
> зафиксирует защитный шум в новых границах. Правильный порядок: починить `S1-10` (26 битых
> спецификаторов), затем **измерить цикломатику заново** — значительная часть исчезнет сама,
> без единой правки логики. Категория: **НЕ ТРОГАТЬ** (до `S1-10`), затем пересмотр.
> Настоящая доменная сложность — в `pickBoiler` (41 `if`, 26 арифметических операций) и
> `pickRadiators` (36 `if`, 7 циклов), и это `S1-38`.

### К-1. 26 ссылок без `.js` в рукописных `.d.ts` → непроверяемые цены

**Корневая причина.** В `backend/src/**/*.d.ts` **26 ссылок на типы записаны без расширения
`.js`**, чего требует `moduleResolution: nodenext`. TypeScript такую ссылку не резолвит и молча
подставляет `any`. Ошибку он не показывает, потому что `tsconfig.strict-base.json:12` содержит
`skipLibCheck: true`, а все эти файлы — `.d.ts`, то есть для `tsc` «библиотечные».

**Моя проверка** (счёт по регулярке, исключая корректные `…js')`):
```
26 битых import('…') в .d.ts:
  20 × backend/src/types/shared-types.d.ts
   2 × backend/src/types/boiler-types.d.ts
   2 × backend/src/hydraulics/types.d.ts
   2 × backend/src/logic/ufhLoopHydraulics.types.d.ts
+  5 статических import type без .js
```
Числа A3 воспроизведены.

**Симптомы — ветка целиком:**

| ID | Симптом |
|---|---|
| `S1-10` | **1 712 выражений с типом `any` в `backend/src`** (покрытие 96.5 %), с концентрацией ровно в денежном коде: `buildFinancialBom.js` — 227, `buildReport.js` — 204, `enrichProposalBundlePrice.js` — 78 |
| `S1-33` | Цикломатика `buildReport` = 256 — защитный шум из 126 `?.` + 70 `??` (П-2) |
| `S1-12` | «Непроверяемые цены труб и насосов»: `matching.hydraulics.proposal` → `any`, вся цепочка `pump.pumpSource/.catalogPumpId/.model/.price` собирается из непроверяемых данных |
| `S1-26` | **Живой дефект:** бренд электробойлера никогда не попадает в коммерческое предложение |
| `S1-35` | Гейт `verifyNoTypeBypass.mjs` даёт зелёный свет — он текстовый и тихий `any` не видит в принципе |

**Тип печатается правильным именем.** Разработчик наводит курсор на `CalcRuntimeContext.catalog`,
видит `NormalizedCatalog`, получает автодополнение — и **не получает никакой проверки**.
Это хуже обычного `any`: обнаружить нельзя ни глазами, ни IDE, ни `tsc`.

**Доказательство, что дыра реальна.** A3 закрыл её на копии дерева и посмотрел, что вылезло:
до — `tsc` 0 ошибок, после — **ровно 4**, все настоящие, без шумного каскада.
Три из четырёх — один дефект: `enrichProposalBundlePrice.js:32-34` читает `selected.brand`,
которого нет ни в типе, ни в валидаторе, ни в данных.

**Моя проверка живого дефекта:**
```
$ node -e "…" backend/test_data.json.example
waterHeaters: 5 | с brand: 0
$ sed -n '131,140p' backend/src/catalog/types.d.ts
export interface WaterHeaterCatalogItemNormalized {
  model: string; type: string; variants: …; heatingElementType?: …; powerDetails?: …; features?: …;
}          ← поля brand нет
```
Ветка мертва всегда. Бренд электробойлера не попадает в строку комплекта коммерческого
предложения — тихая денежная ошибка, которую один битый спецификатор прятал месяцами.

**Одна правка.** (1) Добавить `.js` к 26 спецификаторам — механически, 1 ч.
(2) Починить 4 ошибки, которые вылезут. (3) Добавить в `verifyNoTypeBypass.mjs` регулярку на
относительный `import('…')` без `.js` внутри `.d.ts` — 20 строк, чтобы не вернулось.

**Цена: 4–6 часов.** Риск измерен фактически, а не на глаз: 4 ошибки, продуктовое поведение
не меняется — правятся только `.d.ts`, рантайм-кода эти строки не содержат.

**Что чинится попутно.** Самый денежный код проекта получает проверку типов. Половина
цикломатики `buildReport` становится ненужной — и вопрос «резать ли `buildReport`» надо
пересматривать **после** этой правки, а не до. Наёмный разработчик перестаёт получать ложную
уверенность в файле сметы (−0.5 дня из 8 по оценке A3 §6.5). Переход на TypeScript эту
проблему **не решил бы** — битые спецификаторы в `.d.ts` сломались бы точно так же.

**Смежный, но отдельный дефект того же класса:** `shared/waterHeaterFormContract.d.ts:5`

не экспортирует (проверил — там только константы `:5,13-17,19`). Поле, выбирающее схему связки
«котёл — ГВС» и напрямую влияющее на мощность котла, не типизировано ни на одной стороне
контракта. **30 минут** (`S1-27`).

**Корневая причина.** Состояние анкеты живёт одновременно в трёх местах — localStorage-черновик,
React-состояние сессии, сервер — и **ни одно не назначено источником истины**. Кода сверки
не существует вовсе: `savedAt` пишется и мигрируется, но **ни разу нигде не сравнивается**;
`setQueryData` не используется нигде; на бэкенде `Project` объявлен с `versionKey: false`.

**Моя проверка:**
```
$ sed -n '36,46p' backend/src/models/Project.js
  { timestamps: true, versionKey: false, collection: 'projects' }
```
Оптимистической блокировки нет; `PUT /api/v1/projects/:id` шлёт только `{clientName, survey}`
без `If-Match` и без версии. **Потерянное обновление не просто не обрабатывается — его
невозможно обнаружить** ни на клиенте, ни на сервере.

**Симптомы — семь QA-находок и три инцидента, все уже задокументированы:**

| Источник | ID |
|---|---|
| `docs/qa/research/_ORCH-NOTES.md:41,318,324,431` | `N-07`, `N-30`, `N-31`, `N-42` |
| `docs/qa/research/U5-ux-rootcause.md:93-96,113-116` | `F-08`, `F-09`, `F-10`, `F-14` |
| `docs/qa/research/U4-ux-adversarial.md:311,329,344` | инциденты `#5`, `#6`, `#7` |
| Аудит | `S1-04` (это хранилища), `S1-20` (сессия — не машина состояний) |

**Главный сценарий воспроизводится за 3 клика:** правка комнаты → таймер персиста на 400 мс →
навигация через 100 мс → cleanup гасит таймер **без флаша** → возврат на `/` → `DRAFT_LOADED` →
`return structuredClone(mutation.draft)` — **полная замена** актуального состояния устаревшим
снимком. Правка потеряна дважды, без единого сообщения.

**Отдельный путь, не покрытый ни одной QA-находкой:** откат деплоя делает
`storedVersion > SURVEY_DRAFT_SCHEMA_VERSION`, исключение ловится, и черновик **безвозвратно
удаляется**, в проде — молча.

**Одна правка (минимальная версия, ~4 ч, даёт ~80 % эффекта):**
(1) флаш черновика на размонтирование и на `pagehide` — cleanup должен записывать, а не только
гасить таймер (сейчас подписок на `beforeunload|pagehide|visibilitychange` — ноль);
(2) `DRAFT_LOADED` перестаёт быть безусловной заменой — сравнивать монотонный счётчик мутаций
(не `savedAt`: часы устройства могут быть сбиты).

**Полная версия: 8–14 ч** (+ `try/catch` вокруг `setItem`; `schemaVersion` из будущего —
откладывать, а не удалять; подписка на `storage`; `versionKey` + 409 на бэкенде).

**Что чинится попутно.** Семь QA-находок и три инцидента закрываются одной структурной правкой
вместо семи точечных. Плюс сюда же примыкает **самая дешёвая правка с видимым эффектом во всём
аудите** (`S1-20`, 2–3 ч): убрать `thermalRegimeTouchedRef` — снимок состояния, взятый только
при монтировании и никогда не синхронизируемый, из-за которого при открытии сохранённого
проекта **молча заменяется температурный график** (пользователь сохранил 55/45, открыл завтра —
получил 75/65 и другую смету).

### К-4. Нет `id` и `brand` у части номенклатуры

**Корневая причина.** У котлов, радиаторов и водонагревателей **нет поля `id`**. Идентичность
SKU держится на строке `model` плюс `catalogKey`, генерируемый **по индексу в массиве**:
`catalogSeedBuild.js:95` — `catalogKey: \`boiler-double-${i}\``. Стабильные ключи от артикула
есть только у `manifold`/`boilerManifold`/`unibox`. Перестановка строк в JSON молча переназначает
ключи. Параллельно `brand` у котлов и радиаторов **отсутствует как поле** — бренд зашит внутрь
строки `model` и извлекается хардкод-подстроками в скоринге (`pickRadiatorsCore.js:148-169`:
`score += 120` для `mirado`/`fondital`, `+100` для `radik`/`korado`).

**Симптомы:**

| ID | Симптом |
|---|---|
| `S1-19` | **Мультивендорность стоит 8–14 чел.-недель и является переписью**, а не доработкой: не к чему привязать оффер |
| `S1-26` | Бренд не попадает в смету (у водонагревателей `brand` нет и в типе, и в валидаторе — К-1) |
| `S1-19` | Цена — tie-break в **четырёх** подборщиках (`manifold.js:206,213,266,274`; `unibox.js:218`; `waterHeater.js:60-66,83-89`). Вторая цена на тот же SKU **меняет результат подбора**, а не только сумму → поедут все эталоны и персонный оракул |

| — | Каталог заливается полной перезаписью (`seed.js:319` — `deleteMany({})`), истории цен нет |

**Одна правка (предусловие, а не решение).** Стабильные SKU-идентификаторы + `brand` как поле

Это самая дорогая позиция всего аудита, и её можно не платить.

### К-5. Render free

**Корневая причина.** Backend на бесплатном плане Render: инстанс засыпает, 512 МБ памяти,
0.1 CPU shared.

**Симптомы:**

| ID | Симптом | Замер |
|---|---|---|
| `S1-13` | Cold start **21.7 с** до первого байта; вебхуки платёжки не успевают (типичный таймаут 5–20 с) | `A4-coldstart-raw.txt` |
| `S1-14` | `PDF_MAX_CONCURRENT=2` **не влезает в 512 МБ**: один Chromium — 275 МБ, два — 509 МБ, два вместе с базовым RSS backend (74 МБ) — **512 из 512**; после крупного расчёта (RSS 117 МБ) сборка **перестаёт завершаться вовсе** | `A4-pdf-512mb-parallel2-raw.txt` |
| `S1-09` | Нет keepalive и нет аптайм-мониторинга — владелец узнаёт о поломке от пользователя | grep = 0 |
| `S1-08` | Нет мониторинга вообще: ни метрик, ни трейсов, ни error tracking, ни алертов | grep по `sentry\|prom-client\|opentelemetry\|datadog\|uptimerobot` = 0 |
| `S1-01` | Рестарт по health-check **обнуляет счётчики rate limit** (MemoryStore без `store`) → атака из `S1-01` самоподдерживающаяся | `rateLimiters.js:38-51` |
| `S1-40` | Множитель «Render free / ноутбук» — **×23–30**, измерен живыми запросами | `A4-bench-render-raw.txt` |

**Одна правка... которой нет.** Здесь узел разветвляется, и это надо сказать честно:

- **Cold start** закрывается **сменой тарифа**: платные инстансы Render не усыпляются.
  0 часов разработки. Цена плана — **НЕ ПРОВЕРЕНО** (A6 называет ≈$7/мес, A4 отказался
  подтверждать цифру по памяти; проверяется за минуту на render.com/pricing).
- **512 МБ** сменой тарифа **не закрывается**, если новый тариф остаётся с той же памятью.
  Отдельная правка: `PDF_MAX_CONCURRENT=1` — **5 минут**, значение переменной окружения,
  откатывается мгновенно. Заодно поднять `PDF_QUEUE_WAIT_MS` с 15 000 до ~40 000, чтобы при
  concurrency=1 очередь из 10 человек не отсекалась на седьмом.
- **Мониторинг** — **20 минут** в UI, $0: внешний аптайм-монитор на `GET /health` с

**Что чинится попутно.** Аптайм-монитор за 20 минут закрывает три симптома сразу
(`S1-08` частично, `S1-09`, `S1-13` частично). `PDF_MAX_CONCURRENT=1` за 5 минут превращает
«зависание обоих запросов и падение сервиса» в «трети пользователей быстрый и внятный 503» —
это улучшение, а не регресс.

потому что нормирован **в запросах**, а стоимость запроса различается в **22 000 раз**.
Починка — одна строка `maxItems`.

**S1-05.** Механизм soft-fail **правильный и его не надо убирать** — валить весь расчёт из-за
одного модуля хуже. Чинить надо не механизм, а отсутствие флага. Сценарий: пустой пул труб →
`pickPipe.js:96` кидает обычный `Error` без `code` → `catch` подставляет `pipeLines: []`,
`estimatedTotalPrice: 0` → **HTTP 200**. Монтажник получает смету, в которой раздела труб просто
нет, отдаёт её клиенту и узнаёт о недостаче на объекте. Это структурная причина симптома,
который QA описал как «не падает и почти всегда врёт».

**S1-06.** Коэффициент запаса — **справочная величина**, которая живёт в
`backend/data/appliances.json` именно затем, чтобы её правили без релиза (1.15 для традиционных
котлов, 1.05 для конденсационных). Клиент держит копию литералом в трёх местах: константа `0.15`,
подпись «Запас (15%)» строкой и формула. Значение **уже приходит в ответе API** и **уже парсится**
(проверил: `parseBoilerFromReport.ts:52`). Расхождение существует прямо сейчас, в одном и том же
печатном документе: `:127-128` пишет «Запас» от литерала 0.15, `:189` — «Опалення ×1.05» с сервера.
Для конденсационных аппаратов это две разные цифры на соседних таблицах одного приложения.
Худший вариант: монтажник верит первой цифре, «поправляет» подбор вверх и продаёт избыточный
котёл — при том, что **сам проект предупреждает о вреде этого** (`boilerMatchingByType.js:163`).
