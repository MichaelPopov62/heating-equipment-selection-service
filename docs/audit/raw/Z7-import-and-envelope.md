## Зона 1 · Импорт проектов

### Что проверяется и что принимается на веру — карта

| Поле бандла | Проверка | Куда попадает |
|---|---|---|
| `exportSchemaVersion` | строгое `=== 1` (число, не строка) | нигде |
| `project.clientName` | обязательно, `<`/`>` вырезаются, ≤ 200 симв. | `projects.clientName` |
| `project.label` | ≤ 200 симв. | `projects.label` |
| `project.survey` | plain-object → JSON ≤ 512 000 симв. | `projects.survey` (Mixed) |
| `project.lastCalcInput` | **только размер**, тип не проверяется | `projects.lastCalcInput` |
| `calculations[i].calcInput` | plain-object + размер | `calculations.calcInput` (Mixed) |
| `calculations[i].report` | **только «это объект»** | `calculations.report` (Mixed) |
| `calculations[i].summary` | plain-object; санитизируется **только** `objectType` | `calculations.summary` |
| `calculations[i].sourceCreatedAt` | строка, `Date.parse` для сортировки | **никуда** |
| `exportedAt`, `source.calculationsTotal` | не проверяются | нигде |
| `_id`, `__v`, `ownerId`, `shareToken`, `sharePublishedAt`, `shareSnapshot`, `publicPath` | вырезаются рекурсивно до глубины 12 | — |

**Ответы на поставленные вопросы, коротко.** Чужого владельца назначить нельзя
(`importProjectBundle.js:46-52` — белый список полей, `ownerId` берётся из токена). Даты
подделать нельзя (`sourceCreatedAt` не переносится, `createdAt` ставит Mongoose). Квоты
проверяются обе (200 проектов, 100 расчётов). Документ сверх лимита BSON не пройдёт — но
и не может возникнуть (см. Z7-10). Зацикленный JSON невозможен в принципе (`JSON.parse`
не создаёт циклов), глубоко вложенный безопасен: `JSON.parse`/`JSON.stringify` в V8
не рекурсивны — проверено на 100 000 уровней вложенности, ни переполнения стека,
ни исключения. Поля, которые не должны переноситься, **в основном** вырезаются — исключение
в Z7-06. Главные дыры — не в правах, а в целостности (Z7-02, Z7-03) и атомарности (Z7-01).

### Z7-01 · Импорт не атомарен: провал на середине оставляет полупроект — **БЛОКЕР-B**

`importProjectBundle.js:54` (создание проекта) vs `:63-83` (цикл записи расчётов);
транзакций в кодовой базе нет вообще (`grep startSession|withTransaction` по `backend/src` → 0).

**Проблема.** Проект создаётся первым, расчёты пишутся по одному в цикле, и **внутри цикла**
на каждой итерации заново проверяется квота (`:64`) и размер документа (`:80`). Любой отказ
на N-й итерации — квота исчерпана, документ великоват, обрыв связи с базой — выбрасывает
исключение наружу. Отката нет: проект и N−1 уже записанных расчётов остаются в базе.

**Последствие.** Клиент получает 409/413 и считает, что импорт не состоялся. В базе при этом
лежит проект с частичной историей расчётов, неотличимый от полного. Повтор импорта создаёт
второй такой же проект — и съедает квоту владельца (200). Для функции, которую заводили ради
переноса данных между окружениями, это худший из возможных режимов отказа: молчаливая
неполнота вместо честного «не вышло».

**Решение.** Проверить вместимость **до** создания проекта:
`existingCount + payload.calculations.length <= max` одним `countDocuments`, вместо проверки
на каждой итерации. Плюс `try/catch` вокруг цикла с `Project.deleteOne` + `Calculation.deleteMany`
по `projectId` при любой ошибке. Транзакция не нужна и на бесплатном кластере может быть
недоступна — компенсирующего удаления достаточно.

**Цена: 40 минут.** Риск правки: низкий (путь изолирован, вызывается из одного маршрута).

### Z7-02 · `report` попадает в базу, не пройдя ни одной проверки содержания — **ДОЛГ**

`validateProjectImportBody.js:75` (`assertCalcObject(itemRaw.report, …)`),
`importProjectBundle.js:66-81`.

**Проблема.** `report` проверяется ровно на одно свойство: «это plain-object». Ни AJV
по `CalcReport.yaml`, ни сверки версии схемы отчёта, ни пересчёта
(`importProjectBundle.js:2-3` — «создаёт project + calculations без runCalculation»).
`{"report": {}}` проходит и сохраняется как полноценный отчёт.

**Последствие.** Это **единственный путь**, которым в коллекцию `calculations` попадает отчёт,
не произведённый `runCalculation`. Дальше он ничем не отличается от настоящего: открывается
в интерфейсе, уходит в PDF, публикуется по ссылке. Прямое усиление P1-4 (неполная смета
неотличима от полной): здесь неполной может быть не смета, а весь отчёт.

**Решение.** Прогнать `report` через AJV по `CalcReport.yaml` (валидатор уже собран и живёт
в процессе — `validate.js`) и отклонять несоответствие. Отдельным флагом
`?skipReportValidation=1` оставить лазейку для переноса архивных бандлов, если он нужен.

**Цена: 1–1.5 часа** (0.5 — подключить валидатор к пути импорта; 0.5–1 — прогнать
существующие бандлы и решить, сколько из них не пройдут). Риск: средний — начнёт отклонять
бандлы старых поколений, что и есть цель, но объём надо увидеть заранее.

Уже описано как факт в `docs/qa/research/R6-fixtures-and-data.md:773-777` (RISK-DATA-15);
здесь — как дефект с ценой.

### Z7-03 · `summary` берётся из бандла дословно и может противоречить отчёту — **ДОЛГ**

`validateProjectImportBody.js:83-85`, `importProjectBundle.js:69-72`,
`extractCalculationSummary.js:73-86`.

**Проблема.** Если в бандле есть `summary`, он **не выводится из отчёта**, а копируется как
есть; `sanitizeCalculationSummary` чинит ровно одно поле — `objectType`. Проверено
в процессе: `summary: { heatLossKw: -999, boilerModel: 'FAKE', generatedAt: '2099-01-01' }`
проходит валидацию без изменений.

**Последствие.** Список расчётов и карточки проекта показывают KPI из `summary`, а открытый
расчёт — из `report`. После импорта эти два источника могут расходиться сколь угодно сильно,
и никакой код этого не заметит. Пользователь выбирает расчёт по списку, открывает — там
другие числа.

**Решение.** Всегда выводить `summary` из `report` (`extractCalculationSummary` уже написан
и уже вызывается в ветке «summary отсутствует»). Убрать ветку доверия — одна строка:
`const summary = extractCalculationSummary(report);`.

**Цена: 15 минут.** Риск: нет — при консистентном бандле результат тот же.

### Z7-04 · `survey` не-объект молча отбрасывается вместо отказа — **ДОЛГ**

`validateProjectImportBody.js:127-131`, `stripMongoExportFields.js:54-59`.

**Проблема.** `stripSurveyProjectId` возвращает `undefined` для всего, что не plain-object,
и следующая строка — `if (survey) { assertSurveyShape(survey); … }`. То есть при
`survey: "zzz"`, `survey: [ … ]`, `survey: 42` проверка формы **не вызывается ни разу**,
а поле просто исчезает.

**Последствие.** Битый или урезанный бандл импортируется с ответом **201 ok** и пустой
анкетой. Пользователь видит успех и проект без данных — и узнаёт об этом, только открыв его.
Проверено в процессе: `{exportSchemaVersion:1, project:{clientName:'A', survey:'zzz'}}` →
`{ clientName: 'A', calculations: [] }`, без ошибки.

Побочно: таблица «что отвергается при импорте» в `docs/qa/research/R6-fixtures-and-data.md:812`
утверждает «`survey` не объект → 400 VALIDATION_ERROR». **Для ветки бандла это неверно** —
там 201. (Для `POST /api/v1/projects` — верно, туда `assertSurveyShape` вызывается напрямую.)

**Решение.** Вызвать `assertSurveyShape(projectRaw.survey)` **до** `stripSurveyProjectId`.
Одна строка.

**Цена: 15 минут.** Риск: нет.

### Z7-05 · `lastCalcInput` не проверяется на тип — **ДОЛГ**

`validateProjectImportBody.js:133-138`.

**Проблема.** Для `calculations[i].calcInput` вызывается `assertCalcObject` (`:74`), для
`lastCalcInput` — **только** `assertCalcInputJsonSize`. Массив, число и строка проходят.
Проверено: `lastCalcInput: [1,2,3]` → сохраняется как есть.

**Последствие.** `projects.lastCalcInput` объявлен как `CalcRequestBody` и читается клиентом
для «продолжить расчёт». Массив вместо объекта роняет эту ветку на клиенте уже после
успешного импорта — в месте, где причина не видна.

**Решение.** `assertCalcObject(lastCalcInput, 'project.lastCalcInput')` рядом с проверкой
размера. Одна строка, функция уже есть в файле (`:42-46`).

**Цена: 10 минут.** Риск: нет.

### Z7-06 · Гарантия «служебные поля вырезаны» ложна глубже 12 уровней — **ДОЛГ**

`stripMongoExportFields.js:68-69` (`if (depth > 12) return value;`).

**Проблема.** Рекурсивная чистка обрывается на глубине 12 и возвращает поддерево **как есть**,
без единой замены. Комментарий (`:62`) честно говорит «ограниченная глубина», но вызывающий
код относится к результату как к гарантии.

**Последствие.** Проверено в процессе: `shareToken` и `ownerId`, помещённые на 15-й уровень
вложенности внутрь `survey`, доживают до возврата валидатора (и, судя по коду записи, до
`projects.survey` — Mixed-поле пишется целиком). Практический ущерб сегодня мал: эти ключи
читаются только с верхнего уровня документа, глубоко вложенная копия ни на что не влияет.
Опасен не сегодняшний ущерб, а расхождение между тем, что функция обещает именем и заголовком
файла, и тем, что она делает.

**Решение.** Либо отклонять вход глубже лимита (`throwAppError` вместо `return value`), либо
переписать обход циклом с явным стеком без ограничения глубины. Первое — честнее и дешевле.

**Цена: 20 минут** (правка + обновление комментария + пункт в `verifyProjectImport.js`).
Риск: низкий — бандлы такой глубины не встречаются, отказ никого не заденет.

### Z7-07 · Legacy-импорт подставляет выдуманный `calcInput` вместо отказа — **ДОЛГ**

`normalizeLegacySurveyImport.js:51-58`, ключевая строка `:55`:
`calcInput: reportInput ?? { building: { temps: { insideC: 20 } } }`.

**Проблема.** Тот самый класс, что и P2-1 (трубы «по умолчанию стальные»): если у legacy-файла
`lastCalcReport` есть, а `lastCalcReport.input` нет, вместо отказа подставляется заглушка —
здание без комнат, без ограждений, с температурой 20 °C.

**Последствие.** В базе появляется расчёт, у которого отчёт настоящий, а вход — фикция.
Любая попытка пересчитать проект от сохранённого входа даст пустое здание, а не исходный
объект; расхождение отчёта и входа при этом ничем не помечено. Отличие от P2-1 в масштабе,
а не в природе: там подмена искажает число, здесь — весь вход.

**Решение.** Нет `lastCalcReport.input` — не создавать расчёт вовсе (анкета всё равно
переносится через `survey`). Замена `??`-заглушки на условие: `if (reportInput) { … }`.

**Цена: 20 минут.** Риск: низкий — сейчас такой расчёт бесполезен, его отсутствие не хуже.

### Z7-08 · Импорт стирает историю дат — **ДОЛГ**

`validateProjectImportBody.js:86-88` (`sourceCreatedAt` разбирается),
`sortCalculationsForImport.js:19-27` (используется для порядка),
`importProjectBundle.js:74-81` (в документ **не попадает**).

**Проблема.** `sourceCreatedAt` доходит до записи и там теряется: `calculationDocPayload`
содержит только `projectId`, `calcInput`, `report`, `summary`. `createdAt` проставляет
Mongoose — момент импорта.

**Последствие.** Двойственное. Хорошая половина: **дату подделать нельзя** — это и есть ответ
на вопрос о подделке дат, и это правильное поведение по умолчанию. Плохая: после переноса
между окружениями вся история расчётов проекта схлопывается в одну секунду. Порядок сохраняется
(сортировка отрабатывает), различить «этот расчёт делали в марте, тот в августе» — нельзя.
Для сметы с датой актуальности цен (P2-7) это прямая потеря.

**Решение.** Отдельное поле `sourceCreatedAt` в документе `calculations` (не подменять
`createdAt` — его неподделываемость ценна), отображать в истории как «исходная дата». Схема
Mongoose + сериализатор + подпись в интерфейсе.

**Цена: 1–1.5 часа.** Риск: низкий. **Приоритет — только вместе с P2-7**, отдельно не окупается.

### Z7-09 · `clientName` и `label` приводятся к строке без проверки типа — **КОСМЕТИКА**

`validateProjectBody.js:20,40` → `sanitizeString.js:12` (`String(v ?? '')`).

**Проблема.** Тип не проверяется, всё пропускается через `String()`. Проверено:
`clientName: {}` → проект с именем `"[object Object]"`; `clientName: ['a','b']` → `"a,b"`.
В legacy-ветке этого достаточно и для распознавания файла как валидного SurveyDraft
(`normalizeLegacySurveyImport.js:17-18`).

**Последствие.** В списке проектов появляется мусорное имя, найти проект по нему нельзя.
Не опасно — угловые скобки вырезаются, длина ограничена.

**Решение.** `typeof raw === 'string'` перед санитизацией, иначе 400.

**Цена: 15 минут.** Риск: нет.

### Z7-10 · Проверка размера документа на этом пути мертва, а запись — N+1 — **ДОЛГ**

`documentSizeLimits.js:15` (лимит 14 МБ), `importProjectBundle.js:64,80-81`,
`backend/src/index.js:121` (`express.json({ limit: '1mb' })`).

**Проблема, две части.**

*Мёртвая проверка.* `assertCalculationDocumentSize` сравнивает оценку BSON с 14 МБ, но тело
запроса ограничено 1 МБ на входе. Достичь 14 МБ через импорт невозможно ни при каких данных —
проверка на этом пути не срабатывает никогда. Она осмысленна на пути `POST /projects/:id/calc`,
где отчёт строит сервер, но в таблице режимов отказа импорта (`R6:809`) числится живой.

*N+1.* На каждый расчёт делается отдельный `countDocuments` (`:64`) и отдельный `create`
(`:81`), последовательно, с `await` внутри `for`. Один запрос импорта — до 200 обращений
к базе (100 расчётов × 2), при лимите 60 запросов за 15 минут это до 12 000 обращений
на окно от одного авторизованного администратора.

**Последствие.** Первое — ложное чувство защищённости в документации. Второе — импорт
крупного проекта занимает секунды вместо десятков миллисекунд и держит соединение; на
бесплатном инстансе с health-check из P1-13 это заметно.

**Решение.** Считать квоту один раз до цикла (совмещается с Z7-01) и писать пачкой
через `Calculation.insertMany`. Проверку размера оставить — она защищает другой путь;
поправить строку в `R6`.

**Цена: 30 минут** (совместно с Z7-01 — 20). Риск: низкий.

### Z7-11 · Гейт импорта проверяет исходник грепом, а не поведением — **ДОЛГ**

`backend/scripts/verifyProjectsImportAdmin.js:17,32-36`.

**Проблема.** Скрипт читает `projectsRoutes.js` как текст и проверяет, что в нём встречается
подстрока `requireRole('admin')`. Ни одного вызова, ни одного запроса.

**Последствие.** Проверка останется зелёной, если `requireRole` окажется мёртвым кодом,
если middleware поставят после обработчика, если внутри него появится ранний `next()`.
И станет красной от переноса строки или замены кавычек. Тот же класс, что P1-10: гейт
утверждает не поведение, а форму записи.

**Решение.** Заменить на реальный запрос к маршруту с тремя токенами (нет токена → 401,
`role=user` → 403, `role=admin` → 201). Требует поднятого приложения — но `verifyProjectImport.js`
рядом уже показывает, что чистые функции тестируются без базы, а маршрут без базы вернёт 503
до проверки прав, поэтому нужен либо мок-слой Mongo, либо перенос в набор e2e.

**Цена: 1.5–2 часа** (0.5 — вынести подписание тестового HS256-токена в общий хелпер, уже
описано в `R6:824-838`; 1–1.5 — сам сценарий). Риск: нет. **Не срочно**, но выше по ценности,
чем большинство долга: это единственная автопроверка admin-гейта во всём проекте.

### Вердикт по безопасности импорта

Импорт **не является внешней входной поверхностью** в том смысле, в каком её задавал бриф:
маршрут закрыт `requireRole('admin')` (`projectsRoutes.js:246`), а при выключенной JWT-аутентификации
`requireRole` отдаёт 403 **первым же действием** (`requireRole.js:21-28`) — то есть в dev-режиме
импорт недоступен вообще. Произвольный JSON сюда грузит администратор, а не пользователь.

С этой поправкой:

| Вектор | Итог |
|---|---|
| Создать проект с чужим владельцем | **Нет.** Белый список полей, `ownerId` только из токена |
| Подделать даты | **Нет.** `sourceCreatedAt` не переносится, `createdAt` ставит Mongoose |
| Обойти квоты | **Нет.** Обе проверяются. Но провал квоты оставляет мусор — Z7-01 |
| Положить документ сверх лимита BSON | **Нет,** и не может возникнуть — тело ограничено 1 МБ (Z7-10) |
| Перенести токен публикации / snapshot / `_id` | **Нет** до глубины 12, **да** глубже — Z7-06, ущерб нулевой |
| Загрязнение прототипа | **Нет.** Проверено: `{"__proto__":{…}}` из `JSON.parse` не наследуется, `Object.prototype` чист |
| Глубоко вложенный / зацикленный JSON | **Безопасно.** Циклы невозможны, 100 000 уровней проходят без исключения |
| Записать в базу заведомо ложный отчёт | **Да** — Z7-02, Z7-03. Главный риск зоны |

Опасность зоны — не в правах и не в отказе в обслуживании, а в том, что импорт **обходит
расчётное ядро**: в базу ложится отчёт и сводка, которые никто не считал и никто не проверил,
после чего они неотличимы от настоящих на всём пути до PDF и публичной ссылки.

## Зона 2 · Расчёт ограждающих конструкций

### Формула и единицы — проверено численно

`envelopeHeatLoss.js:65-66`, `wallAssembly.js:72-81`.

```
R = Rsi+Rse + d_ст/λ_ст + d_ут/λ_ут   [м²·К/Вт],  d в метрах
U = 1/R                               [Вт/(м²·К)]
Q = U · S · ΔT · f                    [Вт]
```

Контрольный прогон (газобетон D500, λ = 0.14, d = 375 мм, S = 12 м², ΔT = 25 К,
β = 1.1 для ориентации N):
`R = 0.158 + 0.375/0.14 = 2.8366` → `U = 0.352538`, `Q = 0.352538·12·25·1.1 = 116.338 Вт`.
Ответ сервера: `uValue = 0.3525382755842063`, `qWatts = 116.33763094278808`. **Совпадает.**
Перевод мм → м выполняется в обоих местах (`:72`, `:75`), единицы согласованы.

### Обработка вырожденных значений — проверено запросами

### Z7-12 · Неизвестный пресет стены даёт 500 вместо 400 — **БЛОКЕР-B**

`wallAssembly.js:94-96` (и ещё пять `throw new Error` в том же файле: `:110`, `:116`, `:119`,
`:127`, `:132`, `:69`, `:79`), вызов — `heatlossByRooms.js:129-132`,
контракт — `components/schemas/EnvelopeElementInput.yaml:22` (`presetId: { type: string }`,
без `enum`).

**Проблема.** `resolveExternalWallUValue` бросает `new Error(...)` без `statusCode` и `code`.
Общий обработчик (`backend/src/index.js:228-234`) для 500 подменяет текст на
«Внутрішня помилка сервера» и в проде обнуляет код. При этом `presetId` **элемента** ничем
не ограничен: `assertExternalWalls` проверяет только `objectMeta.externalWalls.presetId`
(`externalWallsValidate.js:32-38`) и отдельно запрещает элементам префикс `insul_`
(`:118-127`) — произвольная строка и пресет чужого вида проходят насквозь.

**Последствие. Проверено запросами на живом сервере:**

| Запрос | Ответ |
|---|---|
| `objectMeta.externalWalls.presetId = "bogus_wall"` | **400** `EXTERNAL_WALLS_INVALID_PRESET` + внятный текст |
| `envelopeElements[0].presetId = "bogus_wall"` | **500** `INTERNAL_ERROR`, «Внутрішня помилка сервера» |
| `envelopeElements[0].presetId = "win_dg_pvc"` (пресет окна) | **500** `INTERNAL_ERROR` |

Одна и та же ошибка пользователя в двух соседних полях даёт диаметрально разные ответы.
Второй случай на публичном анонимном маршруте `POST /api/v1/calc`: клиент не узнаёт, что
именно не так, а сервер пишет в лог стек — то есть каждый такой запрос выглядит как авария
приложения. При живом отслеживании ошибок (Sentry из «Инструментария») это ещё и поток ложных
инцидентов от опечатки в JSON. Клиентской валидации, которая поймала бы это раньше, нет (P1-17).

Сегодня из интерфейса такой запрос не собирается: пресеты приходят из того же API. Но
`mergeWithFallback` (`frontend/src/services/envelopePresets.ts:24-39`) **дополняет** ответ API
локальным списком из 17 пресетов — если пресет когда-нибудь уберут с сервера, клиент продолжит
его предлагать, а сервер ответит на выбор пятисоткой. Сейчас все 17 id присутствуют в серверном
списке из 47, значения `uValue` и `lambdaWmK` совпадают — проверено сравнением файлов.

**Решение.** В `wallAssembly.js` заменить `new Error` на ошибки с `statusCode: 400` и кодом
(шаблон готов — `externalWallsValidate.js:135-142`, `fieldError`). Дополнительно проверять
`presetId` каждого элемента `kind=wall` в `assertExternalWalls` рядом с существующей проверкой
на `insul_` — тогда отказ будет приходить из валидатора, до расчёта, с путём до поля.

**Цена: 30–40 минут** (20 — семь `throw` в `wallAssembly.js`; 15 — проверка элементов
в `assertExternalWalls`). Риск правки: **низкий** — числа не меняются, меняется только код
ответа. Ни одна из 52 автопроверок эти строки не исполняет, поэтому регресс невозможен —
и это же означает, что новое поведение надо покрыть проверкой самому.

### Z7-13 · Без `thicknessMm` стена считается по паспортному U, который не соответствует ни одной предлагаемой толщине — **ДОЛГ**

`wallAssembly.js:101-113`, ключевая строка `:109` (`if (wallPreset.uValue != null) return wallPreset.uValue;`),
`components/schemas/BuildingObjectMeta.yaml:64` (`required: [presetId]` — `thicknessMm` необязателен).

**Проблема.** При `facadeSystem: 'none'` и отсутствующем `thicknessMm` расчёт по слоям
пропускается и берётся справочное `uValue` пресета. Это молчаливая подстановка: ни ошибки,
ни предупреждения в `report.warnings` (проверено — предупреждения о стенах отсутствуют).
А справочное `uValue` **не совпадает ни с одной толщиной из `thicknessOptionsMm` того же
пресета** — вычислено по формуле самого проекта:

| Пресет | `uValue` (фолбэк) | Толщина, которой он соответствует | Предлагаемые толщины и их U |
|---|---:|---:|---|
| `wall_gas_concrete_d500` | 0.41 | 319 мм | 200→0.630 · 300→0.435 · **375→0.353** · 400→0.332 · 500→0.268 |
| `wall_brick_solid` | 1.47 | 402 мм | 250→2.072 · 380→1.535 · 510→1.219 · 640→1.011 |
| `wall_brick_hollow` | 1.26 | 254 мм | 250→1.277 · 380→0.903 · 510→0.698 · 640→0.569 |
| `wall_monolithic_concrete_200` | 3.15 | 271 мм | **200→3.628 (единственная)** |
| `wall_limestone_400` | 1.00 | 463 мм | **400→1.130 (единственная)** |
| `wall_shell_400` | 0.92 | 464 мм | **400→1.044 (единственная)** |

**Последствие.** Для трёх нижних пресетов выбор однозначен — толщина ровно одна, — и фолбэк
**занижает** U на 11–13 %, то есть занижает теплопотери всего объекта. Для газобетона расхождение
зависит от того, что имел в виду пользователь: против 375 мм фолбэк **завышает** на 16 %,
против 500 мм — на 53 %. Проверено запросом: тот же объект без `thicknessMm` даёт
`U = 0.41`, `total = 175.89 Вт` вместо `U = 0.3525`, `total = 151.24 Вт` — **+16.3 %**
к теплопотерям, и дальше в мощность котла, диаметры и насос.

Из интерфейса путь сегодня не достижим: анкета всегда проставляет толщину
(`createDefaultSurveyDraft.ts:62` → 300, `createEmptySurveySessionState.ts:35` → 300,
`migrateLegacyExternalWalls.ts:29` → 375, `:42` → 300 — три разных умолчания для одного поля,
сами по себе тоже подстановки без источника). Достижим по API и через импорт (Зона 1,
где `calcInput` не валидируется вовсе).

**Решение, по возрастанию цены.** Минимум: при уходе в фолбэк добавлять предупреждение
в `report.warnings` — «U взят справочный, толщина не задана» (15 минут). Правильно: считать
`thicknessMm` обязательным для пресетов с `uModel` и отклонять запрос, как это уже сделано
для утеплённого фасада (`externalWallsValidate.js:111-116` — код написан, надо снять условие
`facadeSystem !== 'none'`). Тогда исчезнет и трёхзначное умолчание на клиенте.

**Цена: 15 минут** (предупреждение) или **40 минут** (обязательность + выравнивание умолчаний
клиента). Риск второго варианта: средний — начнёт отклонять сохранённые `calcInput` без
толщины, если такие есть. **Проверить перед правкой,** сколько их в базе.

### Z7-14 · `thicknessMm` элемента молча игнорируется для стен — **ДОЛГ**

`heatlossByRooms.js:116-123` (вычисляется `thicknessMmToUse`) vs `:129-132`
(для `kind === 'wall'` используется другая ветка, где толщина берётся только из
`objectMeta.externalWalls`), схема — `EnvelopeElementInput.yaml:24`
(`thicknessMm: { type: number, minimum: 50, maximum: 2000 }`, без оговорок).

**Проблема.** Поле объявлено в контракте элемента, проверяется AJV, вычисляется в коде —

**Последствие.** Клиент API (и импортированный `calcInput`) задаёт толщину конкретной стены,

по толщине наружными стенами — типового для пристроек и мансард — результат тихо неверен.

**Решение.** Либо использовать `el.thicknessMm ?? externalWalls.thicknessMm` в вызове
`resolveExternalWallUValue` (расширение возможностей, надо продумать взаимодействие
с утеплителем), либо отклонять `thicknessMm` у элементов `kind=wall` как неподдерживаемое.
Второе честнее и соответствует нынешней модели «один набор стен на объект»
(`BuildingObjectMeta.yaml:59-62`).

**Цена: 20 минут** (отклонять) / **1–1.5 часа** (поддержать по-настоящему, с учётом
утеплителя и печати). Риск: низкий.

которого у валидатора сейчас нет). Риск: низкий; отказ может задеть сохранённые анкеты
с таким рассогласованием — **посчитать до правки**.

### Z7-16 · Нет проверки `outsideC < insideC`: теплопотери уходят в минус — **ДОЛГ**

`envelopeHeatLoss.js:103-105` (`const deltaT = insideTempC - outsideTempC;` без проверки знака),
`components/schemas/CalcInput.yaml:40-41` (`insideC` 5…35, `outsideC` −60…**40**).

**Проблема.** Диапазоны заданы независимо, перекрёстной проверки нет. `insideC = 20`,
`outsideC = 40` — валидный вход по схеме, `ΔT = −20 К`.

**Последствие. Проверено запросом:** `envelopeWatts = −93.07`, `totalWatts = −120.99`,
HTTP 200, ни одного предупреждения на эту тему среди шести выданных. Дальше по конвейеру
отрицательное число поглощается полом мощности ГВС (`Math.max(24, …)`, P2-19) и превращается
в подобранный котёл **Vaillant ecoTEC pro VUW 246/5-3, 24 кВт** — на здание с отрицательными
теплопотерями. Смета выглядит нормальной.

через API и через импортированный `calcInput`. Но здесь важен не сценарий, а свойство:

**Решение.** Проверка `outsideTempC < insideTempC` в `calculateHeatLoss` с отказом 400 —
и, отдельно, проверка `totalWatts > 0` перед подбором оборудования. Вторая ценнее первой:
она ловит весь класс, а не один вход.

**Цена: 20 минут** (обе проверки) + **10 минут** на текст ошибки. Риск: нет.

### Z7-17 · Нет верхней границы площади элемента — **ДОЛГ**

### Z7-18 · Две реализации одной формулы, `extraR` учитывается только в одной — **ДОЛГ**

`wallAssembly.js:72-81` (`computeWallUFromLayers`) vs `heatlossByRooms.js:52-56`
(`computeUFromThickness`), тип — `backend/src/types/shared-types.d.ts:325` (`extraR?: number`).

**Проблема.** Обе функции считают `U = 1/(surfaceR + d/λ)`, но `computeUFromThickness`
добавляет `model.extraR ?? 0` (`:54-55`), а `computeWallUFromLayers` про `extraR` не знает
вовсе. Какая из двух отработает — решает `kind` элемента: `wall` идёт в первую, остальное
во вторую.

**Последствие.** Сегодня нулевое: у всех 47 пресетов `extraR: 0` — проверено. Но поле
объявлено в типе, задано во всех уммоделях и, судя по названию, заведено ровно для случая
«дополнительное термическое сопротивление слоя». Первый же пресет стены с ненулевым `extraR` —
воздушная прослойка, облицовка, штукатурный слой — будет учтён для потолка и пола и **тихо
проигнорирован для стены**. Ошибку будет невозможно найти по симптому: числа правдоподобные,
формула «та же».

**Решение.** Учесть `extraR` в `computeWallUFromLayers` (одна строка, поведение не меняется,
пока все нули) — либо, лучше, свести две функции в одну и вызывать из обоих мест.

**Цена: 15 минут** (добавить слагаемое) / **40 минут** (свести в одну). Риск: нет, пока
все `extraR: 0` — это и есть окно, когда правку можно сделать бесплатно.

### Z7-19 · Константы без ссылки на источник — **КОСМЕТИКА**

`wallAssembly.js:17` (`WALL_SURFACE_R = 0.158`), `:20`
(`INSULATION_THICKNESS_BOUNDS = { min: 30, max: 300 }`).

**Проблема.** Обе константы снабжены комментарием о том, **что** они значат, и ни одна —
о том, **откуда** взялась. `0.158` сходится: `1/8.7 + 1/23 = 0.11494 + 0.04348 = 0.15842`,
то есть αв = 8.7 и αз = 23 Вт/(м²·К) по ДБН В.2.6-31 / СП 50.13330 — но эта проверка сделана
аудитом, а не автором; в коде нет ни номера норматива, ни разложения на слагаемые. Для
`30…300` мм источник восстановить не удалось — **НЕ ПРОВЕРЕНО**.

Побочно: верхняя граница 300 мм превышает максимум `thicknessOptionsMm` у **всех пяти**
пресетов утеплителя (у всех `[50, 80, 100, 120, 150, 200]`). Значения 201…300 мм проходят
валидацию, но не соответствуют ни одному предлагаемому варианту.

Обе величины продублированы в контракте (`BuildingObjectMeta.yaml:90-92` — те же 30 и 300;
`FACADE_SYSTEMS` — тот же enum на `:78-79`). Сегодня совпадают, синхронность ничем
не проверяется.

**Решение.** Комментарий с номером норматива и разложением `Rsi + Rse`; либо привести верхнюю
границу утеплителя к 200, либо расширить `thicknessOptionsMm`. Сверку константы и схемы —
одной строкой в существующий проверочный скрипт.

**Цена: 20 минут.** Риск: нет.

### Z7-21 · Одинаковое поверхностное сопротивление для «нет фасада» и вентфасада — **КОСМЕТИКА**

`wallAssembly.js:140` (`surfaceR: wallPreset.uModel.surfaceR ?? WALL_SURFACE_R` — та же
величина для всех трёх значений `facadeSystem`).

**Проблема.** Для вентилируемого фасада наружная поверхность обращена в вентилируемую
прослойку, а не в наружный воздух, и нормативное Rse для неё отличается от 1/23. В расчёте
используется одно и то же `Rsi + Rse = 0.158`.

**Последствие.** Оценочно ~1 % по U для типовой утеплённой стены (`R ≈ 5.4`, расхождение
слагаемого ≈ 0.04 м²·К/Вт) — на фоне остальных находок зоны это шум. Отмечено не ради числа,
а потому что различие между `sftk` и `ventilated` в модели сегодня **отсутствует полностью**:
проверено запросом — СФТК с ППС 100 мм и вентфасад с минватой `insul_minwool_100` дают
побайтово одинаковый `U = 0.1851620744663534`. Два конструктивно разных решения различаются
только допустимым материалом утеплителя (`externalWallsValidate.js:93-109`), но не физикой.

**Решение.** Либо задать отдельный `surfaceR` для `ventilated`, либо явно записать
в комментарии, что упрощение принято сознательно, и назвать порядок погрешности.

**Цена: 20 минут.** Риск: нет.

### Z7-22 · В отчёте `areaM2` уже умножена на `count`, и `count` отдан рядом — **КОСМЕТИКА**

`heatlossByRooms.js:178` (`areaM2: el.areaM2 * (el.count ?? 1)`),
`envelopeHeatLoss.js:73,79` (обе величины возвращаются),
`components/schemas/HeatLossElementReport.yaml:13,43` (`areaM2` и `count` описаны
без единого слова о связи между ними).

**Проблема.** На входе `EnvelopeElementInput.yaml:30` прямо говорит: «Если задано, площадь
считается как areaM2 × count». На выходе `areaM2` — уже произведение, а `count` рядом.
Проверено: вход `areaM2: 12, count: 3` → ответ `areaM2: 36, count: 3`.

**Последствие.** Любой потребитель отчёта, повторивший правило входа, получит площадь,
умноженную дважды. Сегодня ни один такой потребитель не найден — **НЕ ПРОВЕРЕНО** по печати
и PDF, поиск по фронтенду упоминаний `count` рядом с элементами ограждения ничего не дал.

**Решение.** Одна строка в описании поля `areaM2` в `HeatLossElementReport.yaml`:
«суммарная площадь, `count` уже учтён».

**Цена: 10 минут.** Риск: нет.

### Z7-23 · `uValue: 0` во входе молча обнуляет элемент — **КОСМЕТИКА**

`envelopeHeatLoss.js:49-52` (комментарий и проверка `uValue < 0`),
`components/schemas/EnvelopeElementInput.yaml:23` (`uValue: { type: number, minimum: 0 }`).

**Проблема.** Ноль разрешён намеренно и обоснованно: комментарий (`:49`) объясняет, что
`U = 0` — это тёплый пол между жилыми этажами, потери через который не считаются, и
`heatlossByRooms.js:164` пользуется тем же приёмом для границ помещения. Но проверка
не различает «ноль от нас» и «ноль от клиента»: схема входа тоже допускает `minimum: 0`.

**Последствие.** Проверено: `uValue: 0` на наружной стене → `qWatts = 0`,
`totalWatts = 0`, HTTP 200, без предупреждений. Целая стена исчезает из расчёта беззвучно.
Слабое место — та же немота, что в Z7-13 и Z7-15.

**Решение.** `exclusiveMinimum: 0` для входного `uValue` в схеме — служебный ноль ставит
сервер, а не клиент, и на него ограничение не распространяется.

**Цена: 15 минут.** Риск: низкий — отклонит сохранённые входы с явным нулём, если такие есть.
