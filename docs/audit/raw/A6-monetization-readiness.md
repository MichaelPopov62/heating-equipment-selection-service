# A6 — Архитектурная готовность к деньгам

**Дата:** 2026-08-23. **Ветка:** `qa/audit-and-persona-suite`.
**Ось:** A6 — строго техническая оценка. Не бизнес-анализ: только что есть в коде, чего нет,
что придётся построить и сколько это стоит.

**Учтено:** `M2` (репозиторий публичный; корневой `verify` падает у всех — «verify поймает» не опора).
**Не переоткрывается:** блок `RISK-MONEY-01…17`, `RISK-HYDR-01/09/11/12`, `RISK-SEC-06`, `PAY-01…10`,
`E2E-BILLING-001…006`, гейты `GA-28` / `GB-01…07` — это зона QA. Я объясняю **архитектурную причину**
и предлагаю структурную правку, ссылаясь на их ID (§5, §7).

---

## Резюме до находок

Три сценария владельца стоят принципиально разного:

| # | Сценарий | Оценка | Чего не хватает по существу |
|---|---|---|---|
| 1 | Платная выгрузка PDF / подписка для мастеров | **4–7 чел.-недель** | entitlement, вебхук, гейт, дата прайса, оферта |
| 2 | Дилерские сметы с комиссией ~4% | **1 + 10–16 недель** | выплаты наружу (юрлицо, акты, split) — тяжелее, чем приём денег |
| 3 | Аукцион дилерских предложений | **24–40 недель** | мультивендорный каталог — **перепись слоя каталога**, не доработка |

Главный технический блокер — не код: **Render free засыпает, cold start 30–50 с**, и первый
вебхук платёжки после простоя гарантированно отваливается по таймауту (A6-08). Самая дорогая
позиция отчёта — **мультивендорность (A6-11): 8–14 чел.-недель, и это перепись**.

Хорошая новость, которую стоит услышать до списка проблем: **точка отсечения в архитектуре уже
есть и стоит правильно** — `shareSnapshot` (A6-02), а связка «tier пользователя → содержимое
документа» уже работает ровно один раз и работает верно (`buildPublisherPresentation.js:15`).
Гейт не надо изобретать, надо размножить существующий образец.

## Неудобный вопрос: можно ли продавать PDF, если смета уже у клиента в JSON?

**Нет — если продавать «файл». Да — если продавать цены и документ.** Технически:

Что уже помогает — `unitPriceUah` **уже nullable по контракту**:
`components/schemas/FinancialBomLine.yaml:45-48` (`nullable: true`, «null — нет цены»),

1. `commercial.lines[].unitPriceUah` / `lineTotalUah` → `null`, `totals.grandTotalUah` **оставить**

2. `matching.boiler.*` — `estimatedTotalPrice`, `equipmentBundleTotalPrice`,

Обязательный дискриминатор: сегодня `null` уже означает «цену забыли» (`RISK-MONEY-04`,
`RISK-MONEY-02`). Скрытая цена и потерянная цена станут неразличимы — нужен явный флаг
`priceHidden: true` на строке, иначе платный гейт замаскирует денежные дефекты.

**Квоты уже есть** — `projects/projectAccess.js:193-204` (`PROJECT_QUOTA_EXCEEDED`) и `:207-220`
(`CALCULATION_QUOTA_EXCEEDED`), 409, лимиты из env (`auth/projectsAuthConfig.js:204-215`).
Каркас «право → проверка → 409 → ErrorEnvelope» существует; не хватает связи с tier и оплатой.

## Предлагаемая схема

Четыре коллекции. Ни одна не трогает существующие — только добавляются.

**`entitlements`** — баланс права.
```
userId ObjectId ref User
kind   'pdf_credits' | 'subscription'
balance        Number  (для subscription — 0, право даёт validUntil)
grantedTotal   Number
consumedTotal  Number
validFrom      Date
validUntil     Date | null
status         'active' | 'suspended' | 'expired'
lastOrderId    ObjectId ref Order
```
Индексы: `{ userId: 1, kind: 1 }` **unique**; `{ validUntil: 1 }`.

**Списание обязано быть атомарным одним запросом:**
```js
Entitlement.findOneAndUpdate(
  { userId, kind: 'pdf_credits', balance: { $gte: 1 },
    $or: [{ validUntil: null }, { validUntil: { $gt: new Date() } }] },
  { $inc: { balance: -1, consumedTotal: 1 } },
  { new: true },
)
```
Существующий в проекте паттерн квоты — `countDocuments` + сравнение
(`projectAccess.js:194-196`) — **гоночный**: два параллельных запроса проходят оба. Для проектов
это неважно, для оплаченных выгрузок — это раздача бесплатных документов. Копировать образец
`projectAccess.js` нельзя, это надо сказать явно.

**`orders`** — `providerOrderId` (**unique**), `userId`, `sku`, `amountMinor`, `currency`,
`status ∈ {created, pending, paid, failed, refunded}`, `createdAt`, `paidAt`.
Индексы: `{ providerOrderId: 1 }` unique, `{ userId: 1, createdAt: -1 }`, `{ status: 1, createdAt: 1 }` (для сверки).

**`paymentEvents`** — сырьё вебхука и **сама идемпотентность**:
`provider`, `eventId`, `type`, `rawBody` (String), `signatureOk` Bool, `receivedAt`,
`processedAt`, `orderId`, `error`.
Индекс `{ provider: 1, eventId: 1 }` **unique** — это и есть ключ идемпотентности.
Порядок: сначала `insertOne` (дубль ловится `E11000` → отвечаем 200 и выходим), потом обработка.
Транзакции при таком порядке **не нужны**.

**`entitlementLedger`** — append-only аудит (закрывает `PAY-09`):
`userId`, `delta`, `reason ∈ {purchase, consume, refund, expire, admin_grant, admin_revoke}`,
`refType/refId` (orderId / projectId / shareToken), `actorUserId`, `at`, `balanceAfter`.
Индексы: `{ userId: 1, at: -1 }`, `{ refType: 1, refId: 1 }`.
Баланс в `entitlements` — производная величина; ledger — истина. Расхождение = сигнал сверки.

## Три решения, которые надо принять до кода

**Срок действия — вычислять на чтении, а не по расписанию.** В репозитории нет ни одного
планировщика: `.github/workflows/` содержит только `verify.yml`, `node-cron`/`agenda`/очередей
нет (grep — 0). Значит «сгорание» должно быть условием в фильтре списания (выше), а не
sweep-джобой. Плюс: не нужна новая инфраструктура. Минус: `status: 'expired'` актуализируется
лениво — админ-выдача должна это учитывать.

**Перенос остатка.** При продлении подписки `$inc: { balance: +N }` и `$max: { validUntil }` —
одна операция, остаток переносится сам. Обнуление (`$set: { balance: N }`) — тоже одна строка;
это продуктовое решение, но зафиксировать его надо в схеме, а не в голове.

**Возвраты не отзывают уже выданный документ.** `shareSnapshot.publisherPresentation`
вмораживается в момент публикации (`buildShareSnapshot.js:118-120`), ссылка уже у клиента.
Технически откатить нельзя, и **не надо** — но это обязано быть написано в оферте
(см. `PAY-10`). Возврат = отрицательная запись ledger + `$inc` баланса; отрицательный баланс
допустим, гейт проверяет `>= 1`.

**Стоимость:** 16–28 ч — 4 модели, атомарное списание, ledger, admin-чтение баланса
(без пользовательского UI).

## Что придётся построить

1. **`POST /api/v1/payments/:provider/webhook`** с верификацией подписи.
   **Ловушка, которую надо знать заранее:** `backend/src/index.js:121` —
   `app.use(express.json({ limit: '1mb' }))` **глобально, до роутов**. HMAC считается по
   **сырому** телу; после `express.json` его уже нет. Либо `express.raw({type:'*/*'})`,
   смонтированный на путь вебхука **выше** строки 121, либо
   `express.json({ verify: (req,_res,buf) => { req.rawBody = buf } })`. Пропустить это —
   значит потратить день на «подпись не сходится».
2. **Идемпотентность** — unique-индекс по `eventId` (§2), без транзакций.
3. **Транзакции доступны, но не нужны.** MongoDB Atlas по `mongodb+srv`
   (`docs/deploy/first-deploy.md:64`) — это replica set, `withTransaction` работает.
   Порядок «insert event → debit/credit» даёт нужную семантику дешевле. Фиксирую как факт,
   чтобы не тратить время на поиск альтернатив.
4. **Сверка** — эндпоинт/скрипт «все `orders` со `status: pending` старше 15 мин → опросить
   провайдера». При отсутствии планировщика — запуск на первом запросе пользователя и вручную.
   6–10 ч. Без сверки cold start (ниже) делает состояние заказа недостоверным.
5. **Состояние заказа** — конечный автомат `created → pending → paid|failed → refunded`,
   переходы только вперёд, повтор вебхука в уже конечное состояние = no-op.

**Стоимость §3:** 20–32 ч (один провайдер, без UI оплаты). Плюс 8–14 ч на UI checkout/возврата.

# НАХОДКИ

### [A6-01] `POST /api/v1/calc` не подключён к auth-пайплайну вообще — гейт негде поставить, и rate limit считается по IP
- **Ось:** A6 | **Категория:** БЛОКЕР-B
- **Якорь:** `backend/src/api/routes.js:196` (`router.post('/api/v1/calc', calcRateLimiter, …)`),
  `backend/src/api/middleware/rateLimiters.js:14-19`, `openapi.yaml:12` + `:270`
- **Что не так:** в цепочке calc нет ни `optionalAuth`, ни `requireAuth`. `req.user` не
  существует физически, поэтому `resolveRateLimitKey` (`rateLimiters.js:14-19`) всегда падает
  в ветку IP. Это не «не гейтим по тарифу» — это «не знаем, кто пришёл».
- **Сценарий вреда:** любая попытка ввести платный уровень упирается в то, что на самом
  нагруженном эндпоинте нет субъекта права. Плюс сегодняшний эффект: офис монтажников за одним
  NAT делит 20 расчётов / 15 мин на всех (`rateLimiters.js:64-66`) — это уже `PAY-06`.
- **Стоимость починки:** 1–2 ч (добавить `optionalAuth` **перед** `calcRateLimiter`; порядок
  критичен). Это предусловие для A6-02, делать первым.
- **Если не чинить никогда:** платного гейта на расчёте не будет; останется только продажа
  документа, а цены утекают через `/calc` и `/catalog`.
- **Риск самой починки:** минимальный — `optionalAuth` при `!isProjectsAuthRequired()`
  сразу `next()` (`auth/optionalAuth.js:18-21`), а битый токен глотается в гостя (`:33-44`).
  Изменится ключ лимита у залогиненных → часть e2e с лимитами может поехать.

### [A6-02] Резать надо на сериализации; `shareSnapshot` уже стоит ровно там, где нужно
- **Ось:** A6 | **Категория:** ДОЛГ (проектное решение, не дефект)
- **Якорь:** `backend/src/api/routes.js:202`, `backend/src/projects/buildShareSnapshot.js:47-101`,
  `backend/src/api/projectsRoutes.js:714-823`
- **Что не так:** гейта нет, но **место для него подготовлено лучше, чем обычно бывает**.
  `buildShareSnapshot` — единственная функция, превращающая расчёт в коммерческий артефакт;
  она уже отказывается публиковать без сметы (`:48-54`, `SHARE_COMMERCIAL_REQUIRED`).
  Добавить туда же проверку и списание права — это ~30 строк, а не архитектурная работа.
- **Сценарий вреда (если выбрать другое место):** списание на `GET …/pdf` означает, что платит
  тот, кто скачивает, а скачивает **клиент мастера**. Либо клиент упрётся в 402, либо мастер
  оплатит N скачиваний вместо одного документа. Плюс придётся трогать
  `publicSharesRoutes.js:112`, а это ломает уже разошедшиеся ссылки.
- **Стоимость починки:** 6–10 ч (списание на `POST …/share`) + 8–14 ч (редакция ответа `/calc`).
- **Если не чинить никогда:** продавать нечего — весь результат бесплатен и публичен.
- **Риск самой починки:** `verifyProjectShare.js` и `E2E-BILLING-*` понадобится

  производителей. Отдельно 2–4 ч на guard неполной сметы (можно сделать сразу, независимо).

  это делает уже опубликованные ссылки неуязвимыми к любым будущим изменениям каталога и сметы —
  включая мультивендорность. Не типизировать и не «нормализовать»: строгий тип превратит
  каждое изменение сметы в миграцию всех исторических снапшотов.
- **Публичный `GET /api/v1/public/shares/{token}/pdf` без JWT** (`publicSharesRoutes.js:112`).
  Выглядит как дыра в платном гейте, но при списании на публикации (A6-02) это правильное
  поведение: клиент мастера не имеет и не должен иметь аккаунта. Не закрывать — добавить
  отдельный rate limit (A6-09) и всё.
- **Отсутствие транзакций Mongo.** Порядок «insert `paymentEvent` → изменить баланс» даёт
  идемпотентность через unique-индекс без транзакций. Не вводить `withTransaction` ради
  «правильности» — это добавит режим отказа (`TransientTransactionError`, ретраи) без выгоды.
- **`price` как tie-break в четырёх подборщиках** (`matching/manifold.js:206` и др.). Логика
  разумная и работает. Трогать только в рамках A6-11, и только целиком.
- **Отсутствие планировщика.** Соблазн поставить `node-cron` под истечение подписок велик.
  Не надо: вычисление срока на чтении (§2) решает задачу без нового режима работы процесса,
  который на Render free всё равно ненадёжен из-за сна инстанса.

# Сильные стороны

Что в архитектуре **уже** хорошо готово к деньгам — это существенная часть результата:

1. **Точка отсечения существует и стоит правильно.** `projects/buildShareSnapshot.js:47-101` —
   единственный переход «расчёт → коммерческий артефакт», и он уже умеет отказывать
   (`:48-54`, `SHARE_COMMERCIAL_REQUIRED`). Гейт вставляется в готовый шов, а не прорубается.
   В проектах такого возраста это обычно не так.
2. **Связка «tier → содержимое документа» уже работает.**
   `projects/buildPublisherPresentation.js:11-31` + `buildEstimatePdfHtml.js:200-215`:
   `free` не получает блок контакта, `marketplace` получает другую подпись. Один рабочий
   прецедент стоит десяти страниц дизайна — остальные гейты делаются по образцу.
3. **Каркас прав уже промышленный.** `requireAuth` / `requireRole` / `optionalAuth`,
   нормализация `role`/`subscription` **fail-closed** с бросанием 403 на неизвестном значении
   (`authorizationPolicy.js:39-69`), `USER_ROLES` и `SUBSCRIPTION_TIERS` как единый SSOT,
   на который ссылается сама Mongo-схема (`models/User.js:7`, `:32`, `:41`). Дублирования
   литералов нет — редкая дисциплина.
4. **Квоты как механизм уже есть** — `projectAccess.js:193-220`, коды `PROJECT_QUOTA_EXCEEDED`
   / `CALCULATION_QUOTA_EXCEEDED`, 409, единый `ErrorEnvelope`. Тарифным квотам остаётся
   поменять источник лимита с env на entitlement.
5. **Контракт сметы с самого начала допускает позицию без цены** —
   `components/schemas/FinancialBomLine.yaml:45-48` (`nullable`), фронт рисует `—`
   (`FinancialSummaryTable.tsx:18-21`). Бесплатное превью отрисуется существующим компонентом.
   Это прямая экономия недели работы, и она получилась из аккуратно спроектированного контракта,
   а не случайно.
6. **PDF-пайплайн защищён по-взрослому.** Семафор с ограниченным ожиданием в очереди и
   осмысленным 503 (`pdfRenderSemaphore.js:12-25`, `PDF_QUEUE_TIMEOUT`), таймаут рендера
   (`renderPdfFromHtml.js:13-16`), явные коды `PDF_BROWSER_MISSING` / `PDF_RENDER_TIMEOUT`,
   лимиты размера документа. Для сервиса, который запускает Chromium по HTTP-запросу, это
   именно то, что нужно, и обычно этого нет.
7. **Каталог валидируется строго на входе.** `validateCatalog.js:39-48` — отсутствие или `NaN`
   в цене **бросает исключение**, каталог не грузится. Благодаря этому «цена = 0» в проде
   возможна только для труб и насосов (`productSchemas.js:113,124` — `required: false`), а не
   везде. Дефекты `RISK-MONEY-02/04` ограничены двумя типами номенклатуры исключительно
   благодаря этому валидатору.
8. **Rate limiting уже готов к смене ключа с IP на пользователя** —
   `rateLimiters.js:14-19` возвращает `user:<id>`, как только появится `req.user`.
   Требование `PAY-06` закрывается одной строкой в A6-01.

## НЕ ПРОВЕРЕНО

- **Конкретные таймауты и политика ретраев выбранного платёжного провайдера.** Провайдер не
  выбран, интеграции в коде нет. Оценка A6-08 опирается на общий порядок величин (ожидание
  ответа 5–20 с у типовых провайдеров против cold start 30–50 с). Вывод «первый вебхук после
  простоя не проходит» от точных цифр не зависит, но конкретные числа надо подставить после
  выбора провайдера.
- **Фактическое время cold start на текущем Render-сервисе не измерялось мной.** Взято из
  брифинга и `docs/qa/research/_CONTEXT.md:110`; QA отмечает, что в их прогонах cold start
  Render **не воспроизведён** (`docs/qa/TEST_PLAN.md:726`, `E2E-NEG-004`) — измерялся только
  прогрев кэша справочников. Замер на боевом сервисе после суток простоя — 15 мин работы,
  и его стоит сделать до решения по A6-08.
- **План Render (free / Starter) не подтверждён** ни одним файлом репозитория: `render.yaml`
  отсутствует по прямому указанию `docs/deploy/render.md:23`, тариф не указан ни в одном
  документе `docs/deploy/`. Проверяется в Render Dashboard за минуту.
- **Юридические требования Украины к публичной оферте и возвратам** — вне моей компетенции;
  п. 4 в A6-13 сформулирован как требование к наличию документа, а не к его содержанию.
- **Оценки трудозатрат** даны для одного разработчика, знакомого с кодовой базой (то есть для
  автора), без учёта переключения контекста и без учёта работ по осям A1–A5.
