## Вердикт по клиентской авторизации

**Дыры нет. Есть фитиль.**

Обойти `ProtectedRoute` прямым переходом по URL — можно, и это ничего не даёт.
Обойти `AdminRoute` — нельзя, потому что решение принимает сервер.

Разбор по вопросам:

| Вопрос | Ответ | Якорь |
|---|---|---|
| Можно ли обойти `ProtectedRoute` по URL? | Да, если `VITE_AUTH_REQUIRED ≠ 'true'` — guard становится тождественной функцией | `ProtectedRoute.tsx:21` |
| Что при этом утекает? | Ничего. Оболочка `/projects` рендерится, API отвечает 401, список пуст | `useProjectsListQuery.ts:31-36` |
| Можно ли обойти `AdminRoute`? | Нет. Роль берётся только из ответа `GET /api/v1/me`, не из JWT-декода на клиенте | `AdminRoute.tsx:20,25` |
| Утечка админского интерфейса? | Нет. `AdminFeedbackPage` — lazy-чанк **внутри** guard, до проверки роли не монтируется | `AppRouter.tsx:35-39,74-82` |
| Клиент решает или сервер? | Сервер. `requireRole` fail-closed: при выключенной JWT-аутентификации admin API отвечает 403 **всем**, а не пускает всех | `backend/src/auth/requireRole.js:21-28` |
| Что рендерится до загрузки Clerk? | Спиннер `ClerkAuthLoadingFallback`, пока грузится чанк SDK; после монтирования `ClerkProvider` — уже дочерние маршруты, с сессией «ещё не готова» | `ClerkLazyRoot.tsx:61-67`, `ClerkAuthProviderInner.tsx:35` |

Клиентский guard в этой архитектуре — навигационное удобство, а не защита. Это правильно
и так и должно быть. Опасность в другом: **обе половины контура управляются переменными
окружения, которые по умолчанию открыты** — `VITE_AUTH_REQUIRED` (Z2-01) и
`VITE_PROJECTS_BEARER_TOKEN` (Z2-02). Первая при отсутствии пускает всех на `/projects`,
вторая при наличии раздаёт валидный чужой Bearer каждому анониму в JS-бандле.
Обе не проверяются ни одним из 10 verify-скриптов фронтенда.

**НЕ ПРОВЕРЕНО:** фактические значения этих переменных на Vercel — нужен доступ к панели,
5 минут. До этой проверки Z2-02 остаётся теоретическим, как и P1-2 в основном отчёте.

## Находки

### Z2-01 · `VITE_AUTH_REQUIRED` открыт по умолчанию — БЛОКЕР-B

`auth/authConfig.ts:13-15` · `PublicAuthProviderInner.tsx:33` · `AuthProvider.tsx:96` ·
`ProtectedRoute.tsx:21-24` · `frontend/.env.example:6`

**Проблема.** `isAuthRequiredInFrontend()` возвращает `true` только при точном совпадении
строки `'true'`. Переменная не задана, задана с опечаткой, забыта в новом окружении Vercel —
всё это даёт `false`, и тогда `isAuthenticated: !isAuthRequired` = `true` без всякой сессии.
`ProtectedRoute` пропускает. В `.env.example` строка **закомментирована** — то есть образец
конфигурации по умолчанию воспроизводит открытое состояние.

**Последствие.** Гость открывает `/projects`: видит оболочку списка проектов, `AccountBar`
не показывает кнопку «Увійти» (`AccountBar.tsx:51-53` — обе ветки требуют `isAuthRequired`),
запрос списка уходит без токена, приходит 401, экран показывает текст ошибки API. Данные
не утекают — сервер закрыт. Утекает доверие: пользователь попадает в тупик, где нет ни списка,
ни способа войти. Отдельно: тот же флаг в `false` меняет поведение `AdminRoute`
(`isMeQueryEnabled` становится `true` для анонима, `useMeQuery` бьёт в `/me` без токена
и получает 401 на каждой загрузке любой страницы).

**Решение.** Не менять логику флага — добавить проверку в гейт сборки: скрипт `verify:*`,
падающий, если production-бандл собран без `VITE_AUTH_REQUIRED=true`. Соседний
`verifyDevPanelAccess.mjs:38-44` уже делает ровно это для `VITE_DEV_TOOLS` — копируется
почти целиком.

**Цена:** 30–60 мин. **Риск правки:** низкий; сломает герметичный E2E, который сознательно
использует `false` (`docs/qa/research/R4-test-infra-feasibility.md:140`) — проверку вешать
на production-профиль, не на все сборки.

### Z2-02 · Bearer-токен может попасть в публичный JS-бандл — БЛОКЕР-B

`services/projectsAuthToken.ts:37-41` · `services/projectsAuthHeaders.ts:12`

**Проблема.** Последний уровень отката при разрешении токена — `import.meta.env.VITE_PROJECTS_BEARER_TOKEN`.
Любая переменная с префиксом `VITE_` **инлайнится Vite в бандл как строковый литерал**.
Гарда `import.meta.env.DEV` вокруг этой ветки нет.

**Последствие.** Если переменная когда-нибудь окажется задана в окружении Vercel — production
или preview, — валидный JWT чужого аккаунта раздаётся каждому анониму вместе с JavaScript,
и `getProjectsAuthHeaders` подставляет его во **все** запросы: проекты, `/me`, admin API.
Сценарий не выдуманный: собственные документы тестирования предписывают эту переменную
как штатный способ обхода Clerk (`QA_ORCHESTRATOR_PROMPT.md:58`,
`docs/qa/research/R4-test-infra-feasibility.md:12`). Один скопированный набор env
из staging в production — и токен опубликован. Обнаружить это нечем: ни один verify-скрипт
не смотрит в собранный бандл на предмет секретов.

**Решение.** Два шага, оба дешёвые. (1) Обернуть ветку в `import.meta.env.DEV` — токен
перестанет попадать в production-сборку физически. (2) Добавить в `verifyStartState.mjs`
(он уже читает `dist/assets/*.js`, `:46-51`) одну проверку:
`assert.doesNotMatch(allBundles, /eyJ[A-Za-z0-9_-]{20,}\./)` — литерал JWT в бандле.

**Цена:** 30–45 мин. **Риск правки:** нет для прода; потребует правки конфигурации E2E,
если тот полагается на production-профиль сборки.

### Z2-03 · Публичная смета не показывает предупреждения расчёта — БЛОКЕР-B

`SharePresentationPage.tsx` (весь файл) · `parsePublicShare.ts:93-95` ·
`serializeShare.js:70` · `buildTechnicalPrintHtml.ts:203,346`

**Проблема.** Массив `warnings` доходит до клиента: бэкенд его кладёт в снимок, парсер
принимает и валидирует. `SharePresentationPage` **не рендерит его нигде** — вхождений слова
`warnings` в файле ноль. Единственное место, где предупреждения печатаются, — технический
блок, а он свёрнут по умолчанию (`SharePresentationPage.tsx:177-189`, `techOpen` стартует
`false`, `:32`).

**Последствие.** Это фронтовая половина P1-4. Заказчик монтажника открывает ссылку и видит
аккуратную смету с итоговой суммой — без единого признака, что расчёт неполный, что модуль
упал, что подбор выполнен с оговорками. Бэкенд честно сообщил; интерфейс промолчал.

**Решение.** Блок `warnings` над кошторисом, всегда развёрнутый, визуально отличный
от таблицы. Данные уже на руках, парсер уже написан, вёрстка — одна секция рядом
с `styles.meta`.

**Цена:** 1–2 ч. **Риск правки:** нет. **Профит:** закрывает половину P1-4 без единой правки
бэкенда и до появления флага `complete: false`.

### Z2-04 · Инструкция для разработчика показывается клиенту — БЛОКЕР-B

`services/calc.ts:11-12,24,61`

**Проблема.** Константа `CALC_BACKEND_HINT` — текст «Запустіть API: `cd backend && npm run start`
(або з кореня: `npm run dev:full`)…» — подставляется в сообщение об ошибке при сетевом сбое

**Решение.** Две строки: в проде — «Сервер тимчасово недоступний, спробуйте за хвилину»,
в dev — существующий текст под `import.meta.env.DEV`.

**Цена:** 30 мин. **Риск правки:** нет.

### Z2-05 · Ни одного таймаута на сетевых запросах — ДОЛГ

`services/calc.ts:44`, `services/meApi.ts:31`, `services/publicShareApi.ts:22,47`,
`services/adminFeedbackApi.ts:62,81` · единственное вхождение `AbortSignal` во всём
`services/` и `query/` — SSE-поток (`adminFeedbackStream.ts:12,54`)

**Проблема.** `fetch` вызывается без `signal` везде, кроме потока админки. Верхней границы
ожидания не существует ни на уровне клиента, ни на уровне React Query.

**Последствие.** Холодный старт хостинга 22–32 с: спиннер крутится, кнопка расчёта
заблокирована (`useSurveyCalc.ts:152`), кнопки «отмена» у пользователя нет, сообщения
о том, что происходит, тоже нет. Пользователь считает, что приложение зависло, и перезагружает
страницу — на главной это ещё и риск потери черновика (P1-3).

**Решение.** `AbortSignal.timeout(30_000)` в `postCalc` и в клиентах проектов + отдельный
текст «Сервер не відповідає». Начать с `postCalc` — это единственный запрос на критическом
пути монтажника.

**Цена:** 1–2 ч на все клиенты, 30 мин на один `postCalc`. **Риск правки:** низкий.

### Z2-06 · Офлайн не обрабатывается вообще — ДОЛГ

`query/queryClient.ts:14-21` · `onlineManager`/`navigator.onLine` — 0 вхождений во всём
`frontend/src`

**Проблема.** `networkMode` не задан, то есть действует умолчание React Query `'online'`:
при `navigator.onLine === false` запросы и мутации переводятся в состояние `paused`
и **остаются в `isPending` бесконечно**. Ни один экран не различает «грузится» и «сети нет».

**Последствие.** Котельная в подвале, связи нет. Монтажник жмёт «Зберегти на сервер» —
`saveProjectMutation` (`useProjectMutations.ts:61`) уходит в паузу, кнопка показывает спиннер
без конца, сообщения нет. Он жмёт ещё раз, уходит со страницы, теряет введённое (P1-3).
Когда сеть вернётся, запрос уйдёт сам — но пользователь к тому моменту уже сделал выводы.

**Решение.** Подписка на `onlineManager` в корне и баннер «Немає зв'язку — зміни збережуться
локально». Полноценная офлайн-очередь не нужна и не окупится.

**Цена:** 2–3 ч. **Риск правки:** нет. **Профит:** полевой сценарий — основной сценарий
этого продукта.

### Z2-07 · Мигание страницы входа у вошедшего пользователя — ДОЛГ

`auth/authContext.ts:12-20` (нет поля «загружается») · `ClerkAuthProviderInner.tsx:35,108` ·
`ProtectedRoute.tsx:21-23` · `LoginPage.tsx:30,32` · `useAuthRedirectAfterClerk.ts:19-25`

**Проблема.** `isAuthenticated` вычисляется как `clerkSessionReady = isLoaded && isSignedIn`.
Пока Clerk SDK не поднял сессию, это `false` — неотличимо от «не вошёл». В `AuthContextValue`
нет третьего состояния, поэтому guard не умеет ждать: он либо пускает, либо редиректит.

**Последствие.** Обновление страницы на `/projects` у вошедшего монтажника: `ClerkProvider`
смонтирован, дети отрендерены, сессия ещё грузится → редирект на `/login` → там
`useAuthRedirectAfterClerk` дожидается сессии и возвращает обратно по `returnTo`. Ситуация
самозалечивается, но на медленной мобильной сети пользователь успевает увидеть форму входа
и решить, что его разлогинило. История навигации замусорена.

**Решение.** Добавить `isAuthLoading` в контекст (три провайдера, по одной строке каждый)
и в `ProtectedRoute` рендерить `ClerkAuthLoadingFallback` вместо `Navigate`, пока оно `true`.

**Цена:** 1–2 ч. **Риск правки:** средний — трогает единственное место, решающее
о доступе; править только вместе с ручной проверкой четырёх состояний (гость, вошёл,
вход в процессе, Clerk выключен).

### Z2-08 · Ленивая загрузка Clerk отключается на всю вкладку — ДОЛГ

`ClerkLazyRoot.tsx:13,39-42,51`

**Проблема.** Один визит на `/projects` записывает в `sessionStorage` флаг `clerk-sticky`,
и дальше `clerkActive` истинно **на всех маршрутах** до закрытия вкладки — включая главную

**Последствие.** Механизм 1b-6 (не грузить SDK там, где он не нужен) работает ровно один

**Решение.** Хранить не «был на защищённом маршруте», а «сессия существует» — и сбрасывать
флаг при выходе. Либо не активировать sticky на публичных путях.

**Цена:** 1 ч. **Риск правки:** низкий. Брать в связке с другим перф-пакетом, отдельно
не окупается.

### Z2-09 · Ошибки прода исчезают бесследно — ДОЛГ

`components/AppErrorBoundary/AppErrorBoundary.tsx:30-34` · `App.tsx:25-31`

техблока не убивал смету, — 30 мин.

**Цена:** 45 мин суммарно, из них 15 — довесок к уже запланированной работе.
**Риск правки:** нет.

| Скриптов, обходящих дерево файлов (структурный инвариант) | 2 |

**Проблема — не в регексах, а в зеркалах.** `verifyFrontendAuth.mjs:140-151` объявляет
функцию `resolveToken`, воспроизводящую приоритет источников токена, и тестирует **её**.
Продуктовая `resolveProjectsBearerToken` (`services/projectsAuthToken.ts:24-41`) при этом
не вызывается. Поменяйте в ней порядок источников местами — скрипт останется зелёным
и напечатает `verify:frontend-auth OK`. То же в `verifyStartState.mjs:18-27,36-40`
и `verifySurveySessionPipeline.mjs:18,56,92,110` — там 4 зеркала подряд.

**Последствие.** Гейт качества сообщает «OK» о коде, который не выполнялся. Для нового
разработчика это хуже отсутствия проверок: зелёный прогон читается как доказательство.
Отдельно: 82 утверждения `verifyFrontendAuth.mjs` не покрывают `ProtectedRoute` **вообще**
(упоминаний ноль) и не проверяют ни одного из двух env-флагов из Z2-01/Z2-02.

**Что при этом честно работает и трогать не надо:**
`verifySeoStatic.mjs:63-104`, `verifyStartState.mjs:46-89`, `verifySurveySessionPipeline.mjs:142-167`
читают собранный бандл и проверяют, что строка или отдельный чанк действительно туда попали —
регексом по исходнику это не подделать. `verifyTypesPlacement.mjs:29-66`
и `verifyReportColocation.mjs:58-121` обходят дерево и проверяют структурные инварианты
(SSOT типа, размещение парсеров) — для такой задачи чтение файлов и есть правильный метод.

**Решение.** Не переписывать — основной отчёт справедливо рекомендует заморозить харнесс.
Одно точечное действие: перенести **4 зеркала** в тесты обычного фреймворка, импортирующие
реальные функции. Либо вскроется расхождение, либо будет доказано, что его нет; сегодня
неизвестно ни то, ни другое.

**Цена:** 2–3 ч. **Риск правки:** нет. **Профит:** самая дешёвая точка входа для миграции
на нормальные тесты — 4 функции, у которых уже написаны наборы данных.

### Z2-11 · Один входящий отзыв перезапрашивает все страницы админки — ДОЛГ

`query/queries/useAdminFeedbackQuery.ts:49` · `hooks/useAdminFeedbackStream.ts:55,58`

**Проблема.** `staleTime: 0` плюс `invalidateQueries(adminFeedbackRoot)` при открытии потока
и на **каждое** событие `created`. Инвалидация `useInfiniteQuery` перезапрашивает все ранее
подгруженные страницы, а не добавляет одну запись.

**Последствие.** Админ подгрузил 5 страниц (150 обращений) и оставил вкладку открытой.
Каждое новое обращение = 5 запросов к admin API — тому самому, который по разделу
«При 10 000 проектов» тянет полные документы вместо проекции. При потоке обращений это
самоусиливающаяся нагрузка на единственный процесс с 512 МБ.

**Решение.** На `onCreated` не инвалидировать, а `setQueryData` — вставить запись в первую
страницу. Инвалидацию оставить на `onOpen` и на кнопку «Оновити».

**Цена:** 1–2 ч. **Риск правки:** средний (ручная синхронизация кэша, легко разъехаться
с фильтрами). **Брать, когда поток обращений станет заметным**, — сейчас не мешает.

### Z2-12 · Слепые повторы запросов на ошибках 4xx — ДОЛГ

`query/queryClient.ts:18` · `queries/useMeQuery.ts:36-41` (единственное исключение) ·
классы ошибок: `meApi.ts:13`, `adminFeedbackApi.ts:19`, голый `Error` в `calc.ts:77`
и `publicShareApi.ts:27`

**Проблема.** Глобальное `retry: 1`. Статус HTTP до React Query доносит только `MeApiError`,
поэтому политика «не повторять 401» написана ровно в одном месте. Для всех остальных
запросов 400, 403, 404 повторяются вслепую.

**Последствие.** Каждая валидная ошибка стоит двух запросов вместо одного и приходит
к пользователю вдвое позже. Для публичной ссылки с опечаткой в токене — два похода
в базу вместо одного, для анонима, которого можно послать бесплатно.

**Решение.** Не унифицировать четыре класса ошибок (это перебор). Добавить в
`createAppQueryClient` общий предикат: повторять только при отсутствии статуса или
статусе ≥ 500. Для этого достаточно, чтобы клиенты бросали ошибку с полем `statusCode` —
у двух из четырёх оно уже есть.

**Цена:** 1 ч. **Риск правки:** низкий.

### Z2-14 · Глобальный `index, follow` отдаётся и на публичной ссылке — КОСМЕТИКА

`frontend/index.html:10` · `seo/JsonLdBoundary.tsx:15-22`

Один `index.html` на все маршруты SPA несёт `<meta name="robots" content="index, follow">`,
включая `/s/{token}`. Практического последствия нет: `robots.txt` останавливает послушных

`JsonLdBoundary`: по маршрутам из `shouldLoadClerkForPath` плюс `/s/` выставлять
`content="noindex, nofollow"`. 30–40 мин, риска нет. **Профит низкий — брать только заодно
с другой правкой SEO.**

## Сильные стороны

Перечисляю только то, что редко встречается у одиночного проекта в этом возрасте.

1. **Решение о правах принимает сервер, и это видно в коде.** `AdminRoute.tsx:20` берёт роль
   из ответа `/me`, а не из JWT-декода, до которого рукой подать (`authConfig.ts:95`).
   `requireRole.js:21-28` fail-closed: при выключенной аутентификации admin API закрыт всем,
   а не открыт всем. Инверсия по умолчанию сделана в правильную сторону.
2. **Публичный снимок — белый список, а не чистка.** `buildShareSnapshot.js:72-91`: новое поле
   в отчёте не утечёт само. Обратный подход («удалить лишнее») даёт утечку при каждом
   расширении отчёта.
3. **Токен ссылки сделан правильно с первого раза.** 24 байта CSPRNG = 192 бита
   (`shareToken.js:8,16`), не `ObjectId`; нормализация входа отсекает мусор до похода в базу
   (`:25-30`).
4. **Фронтенд не доверяет собственному API.** Строгие парсеры на границе
   (`parsePublicShare.ts`, `parseMeResponse`, `parseAdminFeedback`) с явным отказом
   вместо приведения типов. Это то, чего обычно нет.
5. **DevPanel выключен конструктивно.** Тройное условие: staging-билд И `VITE_DEV_TOOLS=1`
   И `role === 'admin'` из `/me`, плюс ожидание разрешения `/me`
   (`isDevToolsEnabled.ts:18-22,30-37`). Не «спрятано стилями» — не смонтировано.
6. **Ленивая загрузка Clerk с проверкой в бандле.** `ClerkLazyRoot` + `shouldLoadClerkForPath`,
   и — что важнее — `verifyStartState.mjs:80-89` проверяет по собранному `dist/`,
   что SDK действительно вынесен в отдельный чанк и не попал в главный. Здесь автор проверил
   результат, а не намерение.
7. **`safePageUrl`** (`AdminFeedbackPage.tsx:58-66`) — валидация протокола перед `href`
   из пользовательских данных. Защита от `javascript:` в поле, которое приходит от анонима.
