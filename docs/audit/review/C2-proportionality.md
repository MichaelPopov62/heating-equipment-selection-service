## 1. Опасное: три рекомендации, которые сломают работающее (и одна — утечёт данные)

### 1.1 `S1-07`: «бэкапы MongoDB, 2–3 ч, **$0**» — в этой формулировке это публикация базы пользователей

**Что требует план.** П3a, Волна 1, БЛОКЕР-A: «`mongodump` по расписанию
(**GitHub Actions cron → артефакт**, либо ручной еженедельный дамп)», $0, риск описан мягко:
«хранить только в приватном хранилище» (`REMEDIATION_PLAN.md`, П3a).

**Почему это опасно.** Репозиторий **публичный** (`M2`, `_CONTEXT.md:167`). Артефакты
GitHub Actions доступны всем, у кого есть доступ на чтение репозитория, — то есть **всем**.
Дамп содержит `users` (email), `projects` (`clientName`, адреса объектов, телефоны из анкеты),
`feedback` (`clientIp`, `models/Feedback.js:26`). Один cron — и вся база персональных данных
монтажников и их клиентов лежит на публичном URL. Это хуже, чем отсутствие бэкапа: отсутствие
бэкапа — риск для владельца, публикация базы — ущерб третьим лицам и предмет иска.
Второй слой: MongoDB Atlas требует IP-allowlist, у GH-раннеров адреса динамические → чтобы
cron заработал, автор поставит `0.0.0.0/0` и **навсегда снимет сетевой периметр базы**
ради еженедельного дампа.

**Замена.** Вычеркнуть вариант «GitHub Actions» из плана целиком, а не оговаривать.
Два допустимых варианта, оба проще:
1. **Платный снапшот Atlas** (Flex/M2, ≈$9/мес) — включается тумблером, ноль кода,
   ноль обслуживания, восстановление кнопкой. Для вехи B это дешевле часа работы автора.
2. **Ручной `mongodump` раз в неделю на локальный шифрованный диск** + один раз проверенное
   восстановление. 1 ч на первый раз, 10 мин/нед дальше.

**И честно про «$0».** Вариант 2 — не $0, а **повторяющаяся обязанность навсегда**.
План обязан это писать: у одиночки любая еженедельная ручная процедура умирает за месяц.
Поэтому правильный выбор — платный снапшот. Это единственное место аудита, где я рекомендую
**потратить деньги вместо времени**.

**Категория.** Остаётся `БЛОКЕР-A`. Отсутствие бэкапа — не карго-культ.

### 1.2 П2a, пункт 2: `express.json({limit:'256kb'})` на маршруте — правка-плацебо

**Что требует план.** «Лимит тела **только на `/api/v1/calc`**: `express.json({ limit: '256kb' })`
как локальный middleware в `routes.js:196`, а не глобально» — с большим предупреждением о том,
что глобальный лимит сломает импорт проектов (`documentSizeLimits.js:9,12`).

**Почему это не работает.** `backend/src/index.js:121` монтирует `express.json({limit:'1mb'})`
**до** `createRoutes()` (`:124`). К моменту, когда управление доходит до `routes.js:196`,
тело уже прочитано целиком и разобрано. body-parser 2.2.2 (`lib/read.js:39-44`) на втором
проходе видит завершённый стрим и молча выходит:
```js
if (onFinished.isFinished(req)) { debug('body already parsed'); next(); return }
```
То есть локальный парсер **не проверит ни одного байта**. Правка выглядит сделанной, лимита нет.
Хуже: обнаружив это, автор «починит» правку единственным очевидным способом — понизит глобальный
лимит, — и получит ровно ту поломку импорта проектов, о которой план предупреждает.
План сам создал ловушку, о которой предупреждает.

**Замена.**
- **Пункт 2 выбросить целиком.** Защиту даёт пункт 1 — `maxItems: 60` в
  `components/schemas/CalcInput.yaml:51`: AJV отсекает вход **до** `buildReport`, а стоимость
  разбора 1 МБ JSON — единицы миллисекунд, не 4.16 с. Замер A4 показывает CPU в расчёте,
  а не в парсинге.
- Если хочется второй линии — три строки на маршруте, без body-parser:
  `if (Number(req.headers['content-length']) > 262144) return sendErrorEnvelope(res, {statusCode:413,…})`.
  Пять минут, работает, глобальный парсер не трогает.

**Экономия:** −0.5 ч и −1 сценарий тихой поломки платящей функции.

### 1.3 П4: порядок работ уничтожит черновики у всех пользователей при первом откате деплоя

**Что требует план.** Волна 1 — «минимальная версия»: флаш черновика + **`DRAFT_LOADED`
сравнивает монотонный счётчик мутаций**. Волна 2 («П4-добор») — «`schemaVersion` из будущего
**откладывать, а не удалять**».

**Почему это порядок наоборот.** Счётчик мутаций — новое поле черновика, то есть
`SURVEY_DRAFT_SCHEMA_VERSION` (`frontend/src/types/surveyDraft.ts:21`, сейчас 4) станет 5.
После этого любой откат фронтенда на предыдущую сборку даёт `storedVersion 5 > 4` →
`migrateSurveyDraft.ts:57-61` кидает → `surveyDraftStorage.ts:18-27` ловит и делает
`localStorage.removeItem(...)`. **Черновик пользователя удаляется молча и безвозвратно.**
План сам называет этот путь «не покрытым ни одной находкой QA» — и ставит его в Волну 2,
**после** правки, которая его активирует. Пакет, который чинит потерю данных, при таком порядке
её и вызовет.

**Замена.** Три строки в `surveyDraftStorage.ts` (вернуть `null`, не удалять ключ) переносятся
**в самое начало Волны 1, до всего остального П4**. Это 10 минут и обратная совместимость
навсегда.

**И заодно — сокращение самого П4 (см. §2.4).**

биллинг». Для первых десятков клиентов эти вещи не связаны. В коде **уже есть всё для ручной

`buildPublisherPresentation.js:15` — готовый образец связки «tier → содержимое документа».

0 строк кода, настраивается в кабинете провайдера) и **один middleware**, который проверяет
`req.user.subscription !== 'free'` на выгрузке PDF.

**Замена.**
1. Волна 2 = платёжная ссылка + гейт на выгрузку + ручная выдача `pro` через существующий
   admin-эндпоинт. **6–10 ч.**
2. Вебхук писать тогда, когда ручная выдача начнёт мешать — то есть примерно с 20-го платящего

3. **Каскад экономии:** без вебхука исчезает предусловие `S1-13` (cold start 21.7 с ломает

**Экономия: 39–65 ч и одна внешняя зависимость.** Это самое большое сокращение, которое
я предлагаю, и оно не снижает планку продукта ни на грамм: клиент платит, клиент получает PDF.

**Возражение, которое я снимаю заранее.** «Ручная выдача не масштабируется» — верно, и не должна.
`S1-64` (запрет копировать гоночный паттерн квоты) и `S1-НТ-36` (идемпотентность через

### 2.2 Контракт `bomItems` `S1-22` — **44–76 ч → 4–8 ч** для вехи B

предусловие мультивендорности в волне «взять деньги» непоследовательно: либо оба в Волне 2,
либо оба за её пределами. Правильно — **оба за пределами**.
