## 1. Критические пропуски — меняют план

### КП-1. Пять физических констант прошли триаж «на мёртвость», но не «на недоиспользование» — и две из них лежат в основании P0

**Что пропущено.** `knip-backend.txt:52-58` вывел в «Unused exports» пять расчётных констант:
`R_CONV_UP_M2KW`, `R_CONV_DOWN_HEATED_M2KW`, `R_CONV_DOWN_UNHEATED_M2KW`
(`backend/src/logic/ufhRoomHeatFlux.js:16,18,20`), `K_VENT_NATURAL`, `K_VENT_RECUPERATION`
(`backend/src/logic/ventilationReserve.js:9,12`).
A2 разобрал этот класс и закрыл его правильно, но **только по одной оси** —
`A2-dead-code-and-duplication.md:86`: «над-экспортированы: используются внутри своего файла,
лишний `export`, кода за ними нет». Как утверждение о мёртвости это верно.
Вопрос, который не был задан: **используется ли константа везде, где обязана?**

**Почему это важно.** Для `R_CONV_UP_M2KW` ответ — нет, и это ровно механизм QA-P0.
В одном файле, в четырнадцати строках друг от друга:

```
backend/src/logic/ufhRoomHeatFlux.js:158   const rUp = rPipeEmbed + rScreedHalf + rCovering + R_CONV_UP_M2KW;   // верно
backend/src/logic/ufhRoomHeatFlux.js:172   const maxAllowableHeatFluxUpWm2 = Math.max(0, (maxSurfaceT - insideC) / rFinish);
backend/src/logic/ufhRoomHeatFlux.js:179   const surfaceTempC = insideC + heatFluxUpWm2 * rFinish;
```

`:158` собирает полный стек сопротивлений вверх и включает плёнку пол→воздух.
`:172` и `:179` — единственные два места, где считается **предельный поток** и **отчётная
температура поверхности**, — берут вместо неё `rFinish`, сопротивление одного лишь финишного
покрытия. Для плитки `rFinish` на порядок меньше `R_CONV_UP_M2KW = 0.1`, поэтому
`maxAllowableHeatFluxUpWm2` завышается кратно, а `surfaceTempC` занижается.
Это дословно `RISK-SEC-01` (P0, `docs/qa/research/S1-risk-register.md:65`: «для плитки
не срабатывает никогда; отчётная `surfaceTempC` занижена на 6–8 K») и `RISK-SEC-02`
(P0, `:286`). **Правильная величина объявлена в том же файле и корректно применена
на четырнадцать строк выше** — это не пробел в знаниях, а дефект проводки в одну строку.

**Что добавить.**
1. Находку `S1-нов-01` в реестр: якорь `backend/src/logic/ufhRoomHeatFlux.js:158,172,179`,
   ссылки `RISK-SEC-01`, `RISK-SEC-02`, категория БЛОКЕР-A (единственная находка всего
   корпуса, где слово «безопасность» означает ожог, а не доступ), цена — 1 ч на правку,
   плюс обязательный golden-перепрогон по `docs/qa/TEST_PLAN.md:2201-2214`.
2. В методологию (`TECH_AUDIT.md:211-229`) — правило: список knip «unused exports»
   триажится **дважды**: на мёртвость и на недоиспользование. Второй проход по оставшимся
   68 экспортам — 2–3 ч, и он адресный: смотреть надо только расчётные константы.

**Почему это важно.** Неразобранными остались, в порядке убывания веса:

| Якорь | Функция | Параметров |

**Что добавить.** Исправить `M1-static-metrics.md:476` (иначе якорь ведёт читателя не туда);
завести `S1-нов-02` — «7 функций с ≥5 позиционными параметрами в расчётном и денежном коде,
из них две с семью», категория ДОЛГ, 3–5 ч на перевод четырёх горячих в объектный параметр;

### КП-4. Слой «физика и подбор»: 17 P0 без архитектурной причины — при том, что как минимум три причины локализуются одной строкой

**Что пропущено.** Аудит зафиксировал четыре точки пересечения с QA
(`TECH_AUDIT.md:177-182`) и честно объявил, что «не планирует починку ни одного дефекта
физики» (`:184-185`). Устав, однако, требовал не починки, а **объяснения причины**
(`raw/_CONTEXT.md:88-90`): «если QA нашёл симптом, а причина лежит в архитектуре — объясни
причину, сославшись на ID находки QA».

Из 42 P0 реестра QA аудит ссылается по ID на **пять**. Не получили ни ссылки, ни разбора:
семь `RISK-CALC-*`, десять `RISK-MATCH-*`, обе `RISK-SEC-*`. Три из них проверены мной
в коде, и причина в каждом — структурная и короткая:

| QA-ID (P0) | Симптом | Структурная причина (проверено чтением) | В аудите |
|---|---|---|---|
| `RISK-CALC-01` / `N-17` | Вентиляция подменена плоским `kVent` 1.3/1.1 | `backend/src/logic/heatlossByRooms.js:266` **вычисляет `volumeM3 = areaM2 × heightM`** и тут же выбрасывает; `:258` `designWatts = envelopeWatts * kVent`; `:290` `ventilation: { method:'kVentPerRoom', watts: 0 }`. В доменной модели нет сущности «воздушная нагрузка»: объём есть, ΔT есть, кратности нет | нет |
| `RISK-MATCH-01` / `N-18` | Подбор котла не реагирует на теплопотери | `backend/src/utils/boilerMatchingByType.js:38` `return Math.max(heat, hw);` — две независимые нагрузки схлопнуты в один скаляр **до** матчинга, поэтому ни фильтр каталога, ни «запас за опаленням» (`matching/boiler.js:335-346`) не знают, какой член победил | симптом процитирован (`A3:305-308`) как аргумент за разрез `pickBoiler` по сложности — без ID QA и без причины |
| `RISK-SEC-01` / `-02` | Лимит температуры пола | см. [КП-1](#кп-1) | нет |

**Почему это важно, а не придирка.** Для `RISK-CALC-01` из кода следует вывод, меняющий цену:
**входной контракт менять не нужно.** `room.heightM` — обязательное поле
(`backend/src/types/shared-types.d.ts:281`), `volumeM3` уже считается на `heatlossByRooms.js:266`,
`deltaT` доступен там же. Недостаёт только кратности `n`, и её можно взять по типу помещения.
QA оценивал это как изменение физики; тех-аудит был единственным, кто мог сказать, что
данные уже в области видимости и правка локализована в одной функции. Он этого не сказал.

**Что добавить.** Раздел в `TECH_AUDIT.md` после §7.2 — «Причины симптомов QA, которые
мы не чиним, но обязаны назвать»: таблица выше, плюс явная строка «входной контракт
достаточен / недостаточен» для каждой. Это ~2 страницы и 3–4 ч работы, починки не создаёт,
но снимает с плана QA (`D2`, гейт «б») необходимость самому искать причину.

### КП-6. `openapi.yaml` и `components/schemas/` — 120 файлов, 4 671 строка, заявленный контракт API, ноль гейта

**одно**, и то в подсчёте объёма («25 путей `openapi.yaml`», `:146`).

Что я проверил вместо аудита:

  13 предупреждений, все одного косметического класса `spec-ref-siblings`

  и все три — построчным `assert.match` по регулярке
  (`scripts/verifyAuthDocs.mjs:141-177`, `scripts/verifyBackendDocs.mjs:316`,
  `backend/scripts/verifyCalcInputSchema.js:45`), то есть проверяют **буквы, а не схему** —
  тот самый класс, который аудит уже опознал для `verifyNoTypeBypass.mjs`

- **Спека ни к чему не подключена в рантайме.** Валидация входа — независимый AJV
  (`backend/src/api/validate.js`). Спека и поведение могут разъезжаться молча и бесконечно.
- **Три схемы-сироты**, ни разу не `$ref`: `components/schemas/HydraulicsPipelineInput.yaml`,
  `UfhCollectorTransit.yaml`, `UnderfloorHeatingAssemblyPreset.yaml`.

**Почему это важно именно для A6.** Весь сценарий 2–3 монетизации (дилеры, аукцион) — это

но не задал вопрос, годен ли контракт как контракт для третьей стороны.

**Что добавить.** `S1-нов-03`, категория ДОЛГ / БЛОКЕР-B: `npx @redocly/cli lint` в корневой
`verify` и в CI — **20 минут**, окупается сразу; `git rm` трёх сирот — 5 минут; строка
в §4.3 о том, что соответствие 25 путей рантайму не проверялось никем, кроме `R3` из QA.

### КП-7. Справочники `backend/data/` никто не открывал — а в них 27 из 30 труб каталога считаются стальными

**Что пропущено.** Карта покрытия: `backend/data/` — 4 файла, 747 строк, прочитан один
(`appliances.json`), три остальных (`recommendations.json` 36 КБ, `water_norms.json`,
`underfloor_heating_presets.json`) не упомянуты в аудите ни разу. Их **структуру и качество**
не смотрел никто ни на одной оси.

**Что там оказалось.** `backend/data/appliances.json:134` задаёт таблицу шероховатости
тремя ключами:

```json
"roughnessMmByMaterial": { "pex": 0.007, "metal_plastic": 0.007, "steel": 0.15 }
```

`backend/src/hydraulics/pipeHydraulics.js:81-89` резолвит по ней **подстрокой**, с молчаливым
падением в сталь:

```js
export function resolveRoughnessMm(material, roughnessMap) {
  const key = String(material ?? '').toLowerCase();
  if (roughnessMap[key] != null) return roughnessMap[key];
  if (key.includes('pex')) return roughnessMap.pex ?? 0.007;
  if (key.includes('metal') || key.includes('pex-al')) return roughnessMap.metal_plastic ?? 0.007;
  return roughnessMap.steel ?? 0.15;          // ← сюда попадает почти весь каталог
}
```
