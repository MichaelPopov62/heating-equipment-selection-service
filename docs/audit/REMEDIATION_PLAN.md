# План работ

Версия 2.0 — переписана вместе с `TECH_AUDIT.md` после обратной связи владельца.
Содержание сохранено, изложение сжато; описания самих проблем не дублируются — они
в `TECH_AUDIT.md`, раздел 4, по тем же ID.

**Три документа и их роли.** `CHECKLIST.md` — что делать, по шагам, с командами.
`TECH_AUDIT.md` — почему это проблема. Этот документ — в каком порядке, что от чего
зависит и как не сломать работающее.

---

## Три факта, определяющие весь порядок

**1. Собственный гейт качества сломан.** Корневой `npm run verify` падает на четвёртом
шаге у всех и всегда. Пока это не починено, любая проверка «до и после» ничего не значит.
Поэтому починка гейта — первое действие плана, хотя сама по себе она не блокер продукта
(CI гоняет проверки бэкенда и фронтенда отдельно, сетка безопасности есть).

**2. У расчётного ядра нет числовых тестов.** Пока не появится эталонный слепок расчётов
(работа плана QA, блок A-3a, 4–8 часов), любая правка в физике неотличима от новой ошибки.
Две находки — ограничение температуры пола и шероховатость труб — ждут этого слепка.

**3. Часть работ необратима.** Ротация токенов публичных ссылок, миграция каталога,
первая начисленная платная единица. Их нельзя делать «на пробу» — решение принимается
до начала, а не после.

## Пакеты работ

Сгруппированы по корневым причинам (узлы К-1…К-7 из `TECH_AUDIT.md`, раздел 5),
а не по осям аудита: одна правка гасит ветку симптомов.

### П1 — Оживление гейта · узел К-2 · 35 мин + резерв 0–2 ч · волна 1

Починить корневой `verify` (S1-02), подключить проверку прав администратора (S1-08)
и забытый скрипт проверки теплопотерь (S1-44).

Резерв заложен на случай, если ожившие шаги покажут красное. По результатам прогона
рецензентом резерв, скорее всего, не понадобится — все четыре шага зелёные при прямом
запуске.

**Проверка:** `npm run verify` доходит до конца цепочки и зелёный; в бэкенде стало
52 шага вместо 50.

**Зависимость наружу:** этот пакет — предусловие блока A-0 плана QA. Пока скрипт падает,
добавление корневых проверок в CI сделает сборку красной.

### П2 — Границы публичного расчёта · узел К-6 · волны 1 и 2

**П2a (волна 1, 1.5–2.5 ч):** ограничение размера входа `maxItems: 60` (S1-01), сброс
кэша неудачного запроса погоды (S1-40, часть).

**П2b (волна 2, 1–2 ч):** опциональная авторизация перед ограничителем частоты (S1-15) —

**Проверка:** расчёт на 61 комнате отвечает внятной ошибкой; сохранение проекта
на 50 комнат по-прежнему проходит.

### П3 — Замок администратора и периметр · узел К-5 · волны 1 и 2

**П3a (волна 1, 4–7 ч + ≈$9/мес):**

1. **Первым делом, 15 минут** — проверить настройки Clerk глазами. От результата зависит,

2. Определять администратора по неизменяемому идентификатору вместо email (S1-03).
3. Проверить настройки бэкапов в Atlas, включить снапшоты, **один раз восстановить**
   в пустую базу (S1-07).
4. Аптайм-монитор (S1-09) и ограничение PDF (S1-14) — из быстрых побед.

**Заполнить production-checklist:** Atlas, Render, Clerk, GitHub — каждая строка с датой,
ссылкой и отметкой «проверено». Это закрывает разрыв между «в репозитории не описано»
и «на самом деле не настроено» — разные вещи, которые аудит различает.

### П4 — Источник истины состояния анкеты · узел К-3 · 2.5–3 ч · волна 1

он остался 55/45.

Три шага, ни один не требует писать биллинг:

1. Платёжная ссылка у провайдера — настраивается в его кабинете, ноль строк кода.
2. Один фильтр, проверяющий тариф при выгрузке документа. Образец уже написан в коде —

## Критический путь

Восемь жёстких зависимостей, остальное параллельно.

```
П1 (гейт) ──► всё остальное имеет смысл проверять
   │
   └──► блок A-0 плана QA (добавление проверок в CI)

П4 шаг 1 (не удалять черновики) ──► П4 шаги 2–3
эталонный слепок QA (A-3a) ──► П13 (S1-79) ──► П5b ──► П7
П6 (типы) ──► П5b (контракт сметы)
П14 (корпус старых данных) ──► П5b, П7
П5b ──► П8 (мультивендорность), если она вообще понадобится
```

**Что можно делать за один вечер:** все быстрые победы, П1, П2a, первый шаг П4.
**Что требует непрерывного блока:** П4 целиком, П6, П5b, П7.

**Критический путь волны 2 — ветка «деньги»,** и он упирается в эталонный слепок расчётов,
которого пока нет. Это единственная внешняя зависимость плана.

## Как не сломать работающее

### Ритуал для любого пакета

**До правки:**

```bash
git switch -c fix/<пакет>
npm run verify && npm run verify --prefix backend
npm run e2e:personas && npm run e2e:regressions
```

**Запишите результат «до»** в текст коммита или в блокнот. Без записанного «до» вы
не отличите «я сломал» от «оно и так было красным». Это и есть главная причина, по которой
П1 стоит первым.

**После правки** — те же команды. Зелёное «после» при неизвестном «до» ничего не доказывает.

**Что откатывать первым, если пошло не так:** последний коммит пакета, а не «сейчас дочиню».
Поиск причины бага по истории в этом репозитории бесполезен — 61 % коммитов имеют вид
«add changed <файл>», 18 коммитов трогают более 50 файлов. Единственная дешёвая стратегия —
маленькие коммиты внутри пакета и откат по одному.

### Что нельзя делать «на пробу»

Три работы необратимы — решение принимается до начала:

1. **Ротация токена публичной ссылки при повторной публикации** (S1-58). Уже разосланные
   ссылки перестанут открываться. Поведение правильное, но клиенты монтажников получат
   битые ссылки — предупредить в интерфейсе до, а не после.
2. **Миграция каталога на стабильные идентификаторы** (S1-19). Откат равен второй миграции.
3. **Первая начисленная платная единица.** Как только начислено первое право, схема данных
   перестаёт быть черновиком. Идемпотентность закладывать сразу — через уникальный индекс
   на идентификатор платёжного события.

И одно, чего нельзя делать вообще: **переписывать историю git**. Живых секретов в ней нет
(три независимые проверки), а переписывание сломает все ссылки на коммиты из документов
плана тестирования и отчётов аудита.

### Четыре правила для расчётного ядра

Ядро — самое ценное архитектурное свойство проекта: ноль обращений к базе, к вебу
и к настройкам сервера на весь домен. **Это свойство надо защищать, а не улучшать.**
При этом числовых тестов у ядра нет.

**Правило 1. Структурные правки ядра — только после эталонной базы.** Разрез функции,
смена сигнатуры, перенос логики, замена алгоритма запрещены, пока нет эталона «как есть
сегодня». Самая дешёвая форма такого эталона уже спроектирована планом QA (блок A-3a,
4–8 часов вместо 80–150 часов ручных кейсов). Не изобретайте свой формат снапшотов — он
уже описан там же, вместе с процедурой осознанной приёмки изменений.

**Правило 2. Резать при сериализации, никогда при вычислении.** Сборка отчёта вызывается
и при сохранении проекта; урезанный отчёт сохранится в базу и в публичный снапшот.

**Правило 3. Не «улучшать» механизмы, которые уже правильные.** Кэш справочников закрыт
от лавины запросов, имеет откат на устаревший снимок и защиту от гонки при инвалидации.
Любая правка здесь может внести гонку туда, где её сейчас нет. Добавление флага возраста
данных — это добавление поля, а не переделка механизма. То же касается устойчивости
к отказу модуля: чинить нужно отсутствие признака неполноты, а не сам механизм.

**Правило 4. Не резать главную сборочную функцию, пока не сделан П6.** Её формальная
сложность — не находка, а измеритель другой находки: функция линейна, ноль циклов
на 507 строк, а сложность создают защитные проверки данных, которые компилятор не может
подтвердить, потому что они нетипизированы. Резать сейчас — зафиксировать защитный шум
в новых границах. Сначала типы, потом замерить заново, потом решать.

### Наблюдение, которое стоит держать в голове

Защита размеров документов в этом проекте продумана заранее, до первого инцидента: три
уровня ограничений. Дыра ровно одна — массив комнат — и она пропущена не по незнанию,
а потому что там просто не сработала та же привычка автора.

Ищите не «где автор не умеет», а **где не сработала его собственная привычка**. Таких мест
мало, и они дорогие.

## Чего в плане намеренно нет

62 позиции с обоснованиями — в `TECH_AUDIT.md`, раздел 6. Коротко, по группам:

**Крупные переписывания, которых не будет:** переход на другой язык программирования;
разрез пяти больших файлов; очереди и фоновые обработчики; полный контракт сметы
до первых денег; собственный платёжный контур до подтверждённого спроса; мультивендорность
для первого способа заработка.

**Процесс и инструменты, которых не будет:** автообновление зависимостей ботом; стек
метрик и трассировки; проверка сообщений коммитов и автоматические релизы; файлы для
приёма внешних участников; приведение к одному языку комментариев; автоформатирование
всего дерева; переписывание истории git; чистка скриншотов исследования пользователей.

**Механизмы, которые выглядят подозрительно и работают правильно:** кэш справочников;
устойчивость к отказу модуля; отдельный процесс браузера на каждый PDF; флаг отключения
песочницы; энтропия токена публичной ссылки; отсутствие транзакций базы данных;
модели-дискриминаторы, помеченные анализатором как недостижимые.

**Три рекомендации, вычеркнутые независимым ревью как вредные:** бэкап через артефакт
GitHub Actions (в публичном репозитории это публикация базы персональных данных);
общий лимит тела запроса (не защищает, но ломает импорт проектов); увеличение таймаута
очереди PDF (длина очереди не ограничена — увеличение таймаута копит висящие соединения).

**Чего нет, потому что это зона плана QA:** дефекты физики и подбора оборудования,
проходимость анкеты, покрытие расчётного ядра тестами, тестовая инфраструктура.
Мы на них ссылаемся, но не переоткрываем и не планируем — это `docs/qa/`.
