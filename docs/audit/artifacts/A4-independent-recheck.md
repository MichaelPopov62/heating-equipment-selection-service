# Независимая перепроверка замеров A4 (оркестратор, 2026-08-24)

**Зачем.** Критик C1 заявлял в плане перепрогнать замеры A4, но его суб-агент
для этого упал на лимите сессии. C1 проверил числа A4 **аналитически** (якоря, отличие
замера от модели), но **не воспроизводил их**. До этой проверки все числа оси A4 стояли
на одном прогоне одного агента — самое слабое место любого аудита.

Оркестратор перепрогнал их лично, теми же сохранёнными скриптами.

## 1. `buildReport` — воспроизведено

Команда: `LOG_LEVEL=error node --expose-gc docs/audit/artifacts/A4-bench-buildReport.mjs`
Окружение: node v26.7.0, darwin/arm64 (то же, что у A4).

| помещений | A4 (медиана, мс) | перепроверка (медиана, мс) | расхождение |
|---|---|---|---|
| 1 | 0.25 | **0.24** | 4 % |
| 10 | 17.7 | **17.58** | 0.7 % |
| 50 | 113 | **113.96** | 0.8 % |

**Вывод: подтверждено.** Расхождение в пределах шума. Числа `A4-01` и производные
(ёмкость инстанса, стоимость запроса) стоят на воспроизводимом замере.

Побочно зафиксировано (у A4 этого нет): нелинейность на 3 помещениях —
0.24 мс на 2 комнатах против 7.94 мс на 3 (×33 на одно помещение). Это порог включения
тёплого пола в сгенерированном профиле, а не аномалия расчёта; на вывод не влияет,
но объясняет, почему «мс на помещение» не монотонна.

## 2. Cold start Render free — воспроизведено ХУЖЕ заявленного

Команда: `curl -w 'ttfb=%{time_starttransfer}s' --max-time 120 https://heatcalc-api-mp62.onrender.com/api/v1/health`
(путь отдаёт 404 — для замера пробуждения это не важно: инстанс всё равно обязан проснуться,
чтобы ответить. Правильный путь health см. `backend/src/api/systemRoutes.js`.)

| | A4 | перепроверка |
|---|---|---|
| холодный TTFB | 21.7 с | **32.4 с** |
| тёплый TTFB | 0.25–0.66 с | **0.65 с** |

**Вывод: подтверждено и усилено.** Cold start — величина переменная; по двум независимым
замерам диапазон **21.7–32.4 с**. Вывод `S1-13` (вебхук платёжки не переживает пробуждение;
таймауты провайдеров 5–15 с) от этого только крепнет. В документах корректно указывать
**диапазон 21.7–32.4 с по двум замерам**, а не единственное число.

## 3. Что осталось невоспроизведённым

- **PDF в 512-МБ cgroup (512/512 МБ, `S1-14`)** — требует Docker-прогона на 10+ минут,
  не перепрогонялось. Артефакты исходного замера: `A4-pdf-512mb-*.txt`, `A4-pdf-in-512mb.mjs`,
  `A4-pdf.Dockerfile`. Претензия codex #2 (это не прогон двух реальных HTTP-запросов
  через Render) остаётся в силе — предписан staging-тест до смены env.
- **14.7 с на 1600 помещениях (`S1-01`)** — не перепрогонялось; механизм (отсутствие
  `maxItems`) проверен по схеме и сомнений не вызывает.
- **~100 одновременных пользователей** — модель, а не замер; переформулировано по C1-С10.
